Storage and release catalogue design

Preview.4 includes the named remote definitions, file-history formats and explicit local snapshot recovery documented below. Historical slice notes retain their original verification scope. See verified delivery.

Preview.4 includes named remotes, local tree/flat CAS and explicit verified recovery. The final sections describe implemented local CSV/JSON history. Earlier dated codec sections record the initial library slices. Automatic snapshot lookup and optional DVC remain separate work. Ordinary local/GitHub flat history is implemented in the final sections. These additions are included in preview.4.

Standalone ordinary use

proj must work with its own native backend without installing DVC. DVC must not become the mandatory manifest engine or a dependency of ordinary proj use. Existing interpreter and renderer requirements still apply to selected analyses.

Optional DVC-backed directories

Future integration may let users opt individual directories into DVC backing. Only users selecting that integration need DVC. proj should automatically delegate the appropriate operations at the agreed lifecycle points.

proj retains its logical directory labels/roles and path abstraction regardless of backend. Integration must preserve label resolution so analysis code does not depend on DVC-specific physical paths.

DVC remains authoritative for its own tracking and cache state. proj references the corresponding versions rather than maintaining a second authoritative copy of DVC’s data/cache inventory. Projects should be able to mix native and DVC-backed directories. Missing DVC, unavailable data and delegation failures need explicit handling; proj must not silently install DVC.

The directory configuration, supported restore/build/store operations, exact hook timing and failure/recovery boundaries still need design. This note does not adopt old command recipes or decide a provider contract.

A curated release catalogue

The intended release catalogue is a curated, linear history on the main branch, presented as a readable changelog. A general catalogue of every run on every branch is not the product goal. This direction does not change current build or Git branch policies, or remove the need to report failed attempts honestly.

Attempt/release identity, allocation, sealing and how failures relate to this catalogue remain open. Temporary legacy CSV is approved below. Durable recording architecture, remote-only discovery, retention and Git-tracking policy remain open; this note does not claim M2 completion.

See the behavior contract, current lifecycle and compatibility log for implemented behavior and limits.

Compatible CSV inventory

Status: this CSV implementation is included in published preview.3. The user approved temporary projr-compatible CSV while broader recording design continues. This supersedes deferring every manifest implementation.

The root manifest.csv contains quoted string columns in this order: label,fn,version,hash. The filename is relative to its declared directory with slash separators, version includes v, and hash is the lowercase MD5 of file bytes. An empty or absent declared directory has one row with blank filename and hash. MD5 provides legacy comparison compatibility, not authenticity or security.

Production captures hash-enabled raw/cache directories before analysis, after start hooks and preparation. Cache capture excludes its framework-owned projr subtree. After successful output promotion it captures hash-enabled output/docs, then writes those snapshots followed by prior history. Exact duplicate rows are omitted; different versions retain records. With no eligible cache the pre-state stays in memory; otherwise it is also saved at <selected-cache>/projr/<release-version>/manifest.csv. No mapping is invented. Explicit empty analysis can inventory existing artifacts without claiming analysis ran.

Existing history must have the four columns in order and valid rows; corruption fails before hooks instead of being discarded. New CSV writes use guarded same-directory replacement, preserving hard-link aliases. Failure before publication restores root CSV bytes/presence with managed state. Publication failure retains the successful local release and CSV. Cache residue may remain. Previews do not produce production records.

This is an inventory at two lifecycle points, not sealing, environment capture, immutable attempt identity, concurrent snapshot or complete provenance. End hooks run later and may change artifacts. The codec is isolated from build capture for later replacement. CSV has no dependency on CAS. The existing plural .projr/manifests.csv CAS index and remote JSON/objects remain separate, unchanged.

Remote layout direction

projr separates provider configuration from latest/archive layouts. Local providers use path[/label] and path[/label]/v<version>. Store planning includes inspection, cues and sync strategies; restore selects available label versions and copies into final paths. Compatibility includes more than copying a manifest.

Working interpretation: retain ordinary latest/archive and add CAS as a third remote structure, with versioned snapshots and content-addressed objects. CAS can provide archive storage without becoming the manifest format. Current Rust runtime now includes ordinary local and GitHub latest/archive publication, inspection and staged configured restore, plus the older local flat-CAS ingestion and integrity APIs. Those delivered transfers are not new M3 work. M3 adds the missing CAS recovery/safety and the now-approved versioned flat/tree metadata; the first codec slice below does not yet wire new configuration or transfer APIs. There is no DVC dependency, destructive migration, garbage collection or performance claim. Ordinary root manifest.csv remains separate from the legacy CAS lookup ledger .projr/manifests.csv.

Pinned reference: manifest, hashing, build capture, defaults, layouts, store, restore.

Existing opt-in Git commit behavior still stages eligible project files, including root CSV unless ignored. This adds no automatic Git requirement or ignore rule. All regular files, including dotfiles, are inventoried; exact R enumeration parity beyond the stated schema/capture comparison remains unverified.

Approved M3 direction and current source boundary

There is one project per store for this milestone. A remote’s existing flat CAS manifest already contains its label, version and all file paths/hashes. The project-local plural ledger is a lookup shortcut, not the sole holder of that metadata. Explicit snapshot selection can read remote metadata directly; a label/version lookup must report missing or conflicting candidates instead of silently picking one. Automatic discovery improvements and performance tuning are deferred rather than treated as proof that metadata is absent.

Four choices remain distinct:

Choice Meaning Approved direction
Provider How bytes travel Existing local filesystem or GitHub Releases.
Layout Where payload bytes live Preserve latest/archive; CAS is an additional structure.
Manifest style How a snapshot’s names/content identities are described flat or recursive tree; defaults flat for GitHub/non-CAS local, tree for CAS; explicit per-remote override.
Manifest placement Where recovery metadata is retained auto/project/remote/both; auto uses remote for CAS and existing latest/archive behaviour. A small Git root reference can remain even with remote metadata.

The remotes registry and build.dest selection are approved integration work. Omitting a selected remote’s directory subset means all eligible directories; removing it from upload targets must not remove it as a restore source. These new fields are not accepted by the current parser in this codec-only slice. Legacy configurations and data are not silently converted.

Versioned codecs in development source

The Rust snapshot_format module introduces three explicit JSON schemas:

  • projcli.flat-snapshot.v1: one complete snapshot, with shared version/date metadata once and complete file lists grouped by logical label.
  • projcli.directory-tree.v1: one directory’s direct child name/type/hash entries. A child is a file or another tree; no logical label or release metadata is in this content object.
  • projcli.tree-snapshot.v1: the small version/date and label-to-root associations, separate from the directory content IDs.

New file rows name BLAKE3 as their algorithm. Existing ordinary manifest.csv keeps its four-column MD5 semantics. Existing flat CAS manifests retain their old label/version-bearing JSON and raw-byte identities; a bare legacy ID is never automatically interpreted as a new directory tree. This slice adds codecs, not a destructive conversion or a replacement of either legacy reader.

Flat JSON prints each complete path/hash entry and empty-directory leaf on its own line. Empty logical roots remain visible even with no files. Other directory parents are visible in their paths. There are no cross-version deltas or hidden references needed to inspect the complete flat file list. JSON grouping does not make this a recursive tree and does not promise smaller files than CSV.

Directory trees bind direct names, file/tree types and child hashes. Changing a label, build version or supplied date changes snapshot metadata, not the directory root. A new file changes its content hash and relevant ancestors; independent unchanged subtrees can retain their IDs. Permissions, ownership and filesystem timestamps are not part of this byte/name identity.

All new IDs use BLAKE3 derive-key mode with their exact schema string as context, over compact canonical UTF-8 JSON. Struct fields have fixed order; labels, file paths, empty-directory leaves and tree children are sorted by UTF-8 bytes. A supplied RFC3339 date is normalized to UTC; none means unknown and never queries the clock. Version/date metadata is part of snapshot identity, while pretty spacing/line endings and input ordering are not. New format versions must not silently change this canonical encoding.

Readers reject unknown schemas/fields, invalid hashes, duplicate or portable case/normalization aliases, traversal, device names and conflicting file/empty directory shapes. Bounds are 16 MiB JSON, 8 MiB text, 100,000 flat entries or direct children, 4,096 logical labels, 4,096-byte paths with at most 64 components, and 1,024-byte names/labels. Flat prefix expansion has its own global 16 MiB work budget checked before allocating derived prefixes.

Not yet delivered by these codecs: source ingestion, immutable tree-object publication, graph traversal/deep verification, restore installation, registry selection, manifest placement or automatic Git root-reference writes. Those consumers must verify every object’s canonical identity before following references, bound both graph work and expanded output paths, and publish snapshot references last. Equal canonical identities must never authorize overwriting different stored bytes without verified semantic equivalence. Ordinary transfer and the M2 managed recovery pipeline remain unchanged.

Targeted lessons, without importing another tool’s contract

Git’s objects documentation illustrates the separation between file contents, named tree edges and commit metadata. This is an engineering lesson, not Git-object-format compatibility: proj’s algorithms, encoding and filesystem metadata scope are stated above.

DVC’s cache documentation shows content deduplication and a directory descriptor containing relative path/hash entries. Deduplication is independent of whether a manifest is flat or recursive; grouped JSON alone is not a recursive tree. DVC remains optional future integration, not a runtime dependency.

Packit’s primary description of outpack packets separates analysis files from associated metadata. Existing M2 attempt/provenance records serve that different purpose; a content root is not a scientific result, a complete run catalogue or proof of reproducibility.

Local tree-object APIs in development source

The cas_tree library now connects the codecs to explicit local storage roots. This is not new configuration activation or a claim that the CLI can restore tree snapshots yet. Callers choose a file-content base and a metadata base; equal bases keep recovery metadata with the content, while different bases permit project-side metadata without changing content-root IDs.

For a 64-character digest beginning ab, paths are:

Object Path below its selected base
Raw file bytes, shared with the old CAS objects/ab/remaining-62-hex
V1 directory object trees/v1/ab/remaining-62-hex.json
V1 snapshot reference tree-snapshots/v1/ab/remaining-62-hex.json
Existing legacy flat manifest manifests/full-64-hex.json, unchanged

The legacy flat lookup ledger is still project .projr/manifests.csv. New explicit tree reads do not require it or a working project copy: remote references and their tree graph contain version/label/name/hash information. The old public flat verifier remains a separate legacy reader. A missing/empty legacy manifest directory now fails rather than claiming an archive was verified; an explicit empty snapshot is valid. Deep legacy errors distinguish missing/nonregular objects from corrupt bytes.

ingest_directory pre-scans the selected source and rejects links, special files, unsafe names, source/storage overlap and project control aliases before store publication. It rechecks each file at open and hashes the same stream that is copied. It returns an immutable content root, not a published successful snapshot. It does not silently filter hidden files or produce an atomic consistent image of a concurrently edited dataset.

publish_snapshot verifies every referenced directory ID and actual file bytes before atomically installing the immutable reference. Identical supplied metadata is idempotent. Existing JSON with harmless formatting differences is validated against the same canonical ID and reused without rewriting it. Concurrent equal references may converge safely; there is no mutable latest index or implicit clock in these APIs. Errors can leave unreferenced immutable objects, not a successful reference to an incomplete graph. No cleanup/GC or cross-location transaction is promised.

verify_snapshot is read-only and takes an explicit snapshot ID. It checks typed schemas, object identity, regular/no-link paths and file hashes, and returns complete observed file/empty-directory membership per label. A small reference file alone is not sufficient proof that an archive is intact. Metadata is bounded to 16 MiB per object and 64 MiB unique graph metadata; traversal also caps depth 64, expanded entries 100,000 and expanded path text 16 MiB. DAG reuse does not bypass the expanded-output limits. Permission/ownership/timestamp restoration and live-dataset consistency are outside this byte/name observation.

A caller can request a complete readable JSON inventory export, subject to the separate flat-view bounds. It never substitutes a truncated list. This export does not select the stored flat catalogue policy.

Revised flat catalogue direction: CSV and JSON

The later user decision keeps both CSV and JSON. Default csv/json catalogues will deduplicate complete inventories at the logical artefact/version level: an unchanged later version directly references an earlier complete inventory. This is distinct from flat/tree structure and raw file-object CAS deduplication.

Optional csv-dedupe-file and json-dedupe-file modes are off by default. Their dictionary representation must retain every current path membership, resolve to full verified hashes, and not become omitted-file deltas. CSV must remain a rectangular Excel-filter-friendly table. A reference row will identify the earlier complete version; filtering only that later row does not magically expand the earlier file list.

Those catalogue serializers/reference rules are not wired by this tree-object slice. The existing complete JSON codec is a full inventory/view primitive; it is not a JSON-only default or a decision to drop legacy CSV. Existing root ordinary manifest.csv, old flat CAS data and their readers remain compatible.

Version-reference catalogue codecs in development source

The new catalogue library keeps CSV and JSON and provides four explicit serialization modes: csv, json, csv-dedupe-file and json-dedupe-file. These codecs do not yet select a remote’s write format, change active configuration, replace the root projr manifest.csv or migrate existing flat CAS snapshots.

Default csv/json append an unchanged logical artefact as a direct reference to the earliest complete same-label inventory already in that catalogue. A changed version has a complete inventory. Reverting to old bytes can reference that older complete version; references never target other references. Existing records are not overwritten. Record append order expresses history; no lexical version/date ordering is inferred. Duplicate label/version records, forward/dangling/cross-label references and digest mismatches fail.

Inventory equality binds canonical sorted portable paths, entry kinds, full file BLAKE3 digests and explicit empty-directory leaves. Version, date, logical label and physical root are outside that inventory digest; reference lookup still requires the same logical label. The identity domain is projcli.artefact-inventory.v1 over compact fixed-field JSON containing files and empty_directories, after the existing flat-path validation. Raw file hashes, directory-tree IDs and snapshot/reference IDs retain their different domains.

JSON has an explicit projcli.flat-catalogue.v1 schema, format and hash_algorithm. Each record contains label, version, optional normalized created_at, inventory_hash and an inventory tagged as complete or reference. A reference has ref_version and cannot mix in file rows.

CSV has one rectangular header:

schema, format, hash_algorithm, record, record_index, label, version, created_at, inventory_hash, path, hash, ref_version, file_id.

The record column distinguishes catalogue metadata, inventory, file, empty_directory, reference and dictionary rows. Explicit inventory rows represent empty roots too. File membership rows repeat label/version metadata deliberately: an Excel table filter on a complete artefact/version shows all its file paths. A reference row names the earlier version to filter; filtering only the later version does not expand its referenced inventory. record_index keeps append order explicit even if a spreadsheet sorts rows. CSV quoting preserves commas, quotes and Unicode rather than changing the recorded path. Import text columns as text in spreadsheet software; CSV does not control its formula interpretation.

The opt-in file-dedupe modes bundle one dictionary of distinct full file digests. They retain every path membership row, replacing only repeated hashes with document-local integer file_id values. IDs are assigned deterministically by sorted full digest for each export; they are not persistent global identities. Parsing resolves them to full hashes, verifies complete inventory digests and rejects duplicate/unused/dangling dictionary entries or mixed hash/ID membership. Exports contain their own dictionary, not references to another database.

These are bounded metadata codecs, not proof that physical objects exist. Documents cap at 16 MiB, text at 8 MiB, and complete membership/history/dictionary rows at 100,000; existing path/depth/alias checks still apply. No size or speed advantage is claimed. Catalogue publication dependency ordering, immutable remote integration and no-code expanded listing remain integration work.

Independent review tightened the catalogue-wide limits: dictionary plus membership rows count before JSON expansion, derived path-prefix work shares one 16 MiB budget across history, and CSV/JSON output stops at the byte limit while writing. A transient earliest-complete lookup avoids rescanning all history for each new selected label; it adds no persistent index.

Verified local tree recovery APIs

The restore_label library API accepts explicit content/metadata bases, a v1 snapshot ID, one exact logical label and an absolute destination whose parent already exists. It does not infer latest/history candidates or require the old project ledger. It deeply verifies the full snapshot, materialises selected bytes into owned private staging, hashes the copied stream and verifies actual private stage bytes/membership again before replacing the destination.

Recovery reuses the ordinary guarded directory installer and its bounded rollback. With clear=false, destination-only files survive; matching selected files receive the selected bytes, and selected empty directories may retain destination-only children. With clear=true, final membership matches the selected inventory, including explicit empty directories. The result reports clear and the selected snapshot/version/label. No project VERSION or source/store bytes are updated.

Project authorities/control aliases, linked/special destinations and overlap with CAS objects/tree/reference namespaces fail. Empty snapshots need no objects directory. Remote metadata supports recovery into a fresh empty working project; project-side metadata remains supported when that metadata still exists.

A new internal installer verification callback runs on its private next-stage before retaining the previous destination. Existing ordinary local/GitHub paths use the same installer with their previous behavior. No hard-linked external file inode is edited in place.

The recovery API remains explicitly selected. Named registry and configured tree publication/placement are described below; automatic snapshot selection and flat catalogue publication integration remain pending. Explicit configured verification/recovery is described below. It is not a crash-atomic transaction or arbitrary concurrent-writer sandbox. Permissions/ownership restoration is not a CAS guarantee. As with the ordinary installer, cleanup failure can report an installed destination and retained private backup rather than pretending rollback after successful installation.

Source review added explicit legacy manifests namespace protection: a tree restore cannot target the old flat manifests directory either. Merge validation compares actual directory-entry spelling, including selected empty directories, so native case aliases cannot widen an existing private directory’s modes.

Both private staging levels are explicitly closed. If a pre-replacement callback rejects a copied tree, cleanup may unlock only owned copies, never the installed destination or a retained previous original. Primary and cleanup failures remain visible together; a tree that cannot be safely removed is retained with its path. The ordinary installer’s existing post-install backup-cleanup limitation remains.

Configured local CAS tree publication (unreleased)

New local CAS definitions can select recursive tree publication through the named registry. Directory selection is independent of full metadata placement:

remotes:
  local:
    snapshots:
      path: ../snapshot-store
      structure: cas
      manifest: auto
      manifest-style: tree
build:
  dest:
    snapshots:
      content: [raw, output]

Omitted content selects eligible non-cache declared labels. Explicit null, false or an empty list selects none; build subsets cannot enable excluded labels. auto means remote for this CAS writer. remote stores complete tree objects and snapshot metadata beside file objects; project stores that metadata under the project; both requires both copies. File objects always remain in the configured store. A small project reference is retained for every successful publication, including remote placement. That reference is not itself a complete archive.

Raw objects, directory objects and snapshot/reference records use first-two- characters/rest-of-hash fan-out. Identical directory contents share a root across labels and versions. Snapshot version associations are separate immutable records. There is no inferred timestamp or mutable discovery index. Existing blobs are verified before reuse. Required graphs precede full references; the small project reference is written last. Errors after provider entry retain the local release and distribution evidence. both is not a cross-location atomic transaction: partial references/objects may remain and errors say so. Nothing is garbage- collected or rolled back from a published store automatically.

Previously accepted path/structure/content/inspect CAS definitions keep their legacy flat JSON identities and plural .projr/manifests.csv ledger. Name-list selection still works; mapping subsets preserve legacy label spelling. To opt into new trees, remove the legacy inspect field and explicitly select tree if desired. No old manifest is reinterpreted or moved.

The first publication slice added tree storage. Explicit named-ID recovery and local CAS flat CSV/JSON histories are described below. Automatic snapshot lookup remains deferred. Legacy inspect belongs only to the old definition; new manifest-format choices are validated against style. Ordinary local/GitHub flat histories are also implemented below, alongside compatible CSV/VERSION metadata; Ordinary local and GitHub tree metadata are described below.

Explicit configured tree readers

Named v1 snapshot verification and single-label restore now consider the full remote and project metadata namespaces independently of current write placement or style. Current upload content does not hide an explicit historical snapshot. All present full copies must verify; absence is distinct from corruption. Readers do not need the old project ledger, root CSV or small project reference.

Selection remains exact title/ID/label, not an automatic newest-version policy. Existing graph limits and guarded installation are reused. Legacy flat IDs are not recast as v1 tree IDs; the compatibility reader below restores their original format. Local CAS flat runtime is described below; ordinary/GitHub flat histories are implemented below; Ordinary local and GitHub tree metadata are described below.

Recover existing flat CAS snapshots

The explicit remote verify / remote restore –snapshot commands also read the original flat JSON snapshots in manifests/<id>.json. Their IDs remain BLAKE3 of the original JSON bytes; they are never reinterpreted as pure content-tree IDs. Responses identify snapshot_kind as legacy-flat or tree-v1.

The reader validates metadata, portable names and every referenced object before using the same guarded staging/installer as trees. Old snapshots remain usable after the remote’s current write style changes, without a project CSV or legacy ledger. Stored metadata, IDs, objects, VERSION and history are never rewritten.

Legacy snapshots record files but not empty directories or permissions. Recovery does not invent that missing history. Unsafe path aliases, traversal, corrupt or missing content and conflicting same-ID namespace entries fail explicitly before destination changes. Metadata is bounded at 16 MiB and 100,000 file entries, with the existing portable path bounds. Ordinary root manifest.csv remains separate.

Automatic snapshot discovery remains deferred; ordinary local and GitHub tree metadata are described below; ordinary/GitHub flat formats are implemented below; this is compatibility recovery, not a format conversion or migration.

Flat history in local CAS

New local CAS remotes can save a readable CSV or JSON history instead of a directory-tree manifest:

remotes:
  local:
    snapshots:
      path: ../snapshot-store
      structure: cas
      manifest-style: flat
      manifest-format: csv
      manifest: remote
build:
  dest:
    snapshots:
      content: [raw, output]

The labels must already be declared. For flat style, csv is the default; json is also available. Both automatically reuse an earlier complete inventory for the same logical folder when later contents are identical, including a reversion to older contents. The later version points directly to that earlier complete version, never a chain. A changed version records all current file memberships, including additions, removals and renamed paths.

CSV is one rectangular table with a header and repeated label/version columns. In Excel, filtering a reference version shows the earlier ref_version to inspect; it does not automatically expand that earlier listing. All earlier complete rows remain in the same history file. Plain CSV/JSON retains literal full file hashes. Optional csv-dedupe-file/json-dedupe-file modes replace repeated hashes with a bundled file dictionary while retaining every file path. These modes are off by default. They are not omitted-file deltas, and no size/speed advantage is promised.

Files are stored once by their BLAKE3 content hash regardless of manifest format. Full history files live under catalogues/v1/manifest.csv or manifest.json; opt-in dictionary files use manifest-dedupe-file.csv/json. Existing root manifest.csv keeps its separate projr-compatible MD5 schema and is unchanged.

auto means remote for CAS. project/remote/both selects full history placement; a small project snapshot binding is always retained. Flat bindings connect the version and selected labels to inventory hashes, independently of serialization or dictionary IDs. They are not directory-tree object IDs. Full immutable refs use flat-snapshots/v1/<first2>/<rest62>.json; small project refs use references/flat-v1/<first2>/<rest62>.json. No unnecessary tree objects are written.

History replacement is atomic per file. Decoded previous label/version contents are never overwritten; divergent histories or conflicting same-version retries fail. Identical per-label retries do not duplicate rows, and missing labels can resume a partial write. Switching format preserves older files/readability and uses the longest compatible decoded history; dictionary IDs do not define it. Codec limits fail explicitly rather than truncating history.

The authoritative history read through replacement/reference publication holds the existing cooperative claim at <store>/.proj/build.lock. Unknown/stale claims fail closed and only an owned claim is removed; there is no automatic process killing or stale-claim cleanup. Raw immutable objects may be copied before that claim. Required history copies precede full snapshot refs, then the small project ref. both is not a cross-location transaction: errors can leave objects or an updated first history copy. Retry can finish the remaining copy.

Explicit verify/restore resolves version references/dictionaries, checks inventory hashes and actual raw bytes, and uses the existing guarded installer. The result reports snapshot_kind: flat-catalogue-v1. Old tree and legacy-flat IDs stay distinct and readable, regardless of the current write style. A small binding alone is not a backup. Empty directories are recorded by this new format, unlike legacy flat.

These manifest-format controls apply to local CAS and the ordinary local/GitHub flat histories described below. Ordinary providers retain compatible CSV/VERSION metadata alongside the new histories. CAS trees default to fixed v1 JSON; explicit manifest-format: json is valid there, while CSV/dictionary choices require flat style. Null/unknown modes fail instead of silently choosing a default.

Ordinary local history integration (development source)

Ordinary latest/archive data keeps its existing directory layout; new flat catalogues do not copy files into objects. A distinct versioned local binding records each logical folder’s inventory hash, relative physical payload path, empty flag and existing VERSION advertisement. Its ID is a snapshot binding, not a pure content root. Small project references persist with remote-only full metadata. One archive payload may serve several build-version observations. Mutable latest storage cannot promise recovery of older overwritten content.

GitHub flat history integration (development source)

GitHub full catalogue/history and snapshot bindings share the versioned projcli-manifests-v1.zip asset; data stays in the ordinary ZIP layout. Bindings include frozen repository/tag and the actual payload asset, separate from the build-version inventory. Exact prepared ZIP observations preserve existing packaging semantics rather than inventing empty directories. Disk-backed private records avoid retaining full metadata buffers for every target at once.

Every required HTTP write and full project copy precedes small project references. Original asset-ID checks protect against replacing an already changed history; they do not establish cross-writer or crash atomicity. No CAS objects, new credential mechanism, live user-data test or broad snapshot discovery is introduced.

Flat CAS placement continuity

Configured flat CAS separates known history read locations from selected full-copy destinations. Project/store histories must be compatible prefixes before hooks, and publication rereads them under the existing store claim. Only selected copies change; old files/IDs remain. The public explicit-bases flat publication API keeps its signature/scope. Tree and legacy formats are unchanged.

Ordinary local directory trees (development source)

Tree metadata and storage structure remain independent. Ordinary local tree style keeps normal folder/archive data and stores only content-derived directory objects under the selected metadata roots. The exact existing DirectoryTree v1 codec and sharded path convention are reused; native CAS over identical payload membership yields the same root.

The readable catalogue is a companion lookup/inspection projection, excluded from pure root identity and checked against graph membership. It deliberately duplicates names/hashes; no speed/size improvement is claimed. The new ordinary tree binding schema carries tree alongside the distinct inventory_hash, physical path, empty flag and existing VERSION advertisement. Earlier flat bindings do not gain fields or change IDs. No legacy reinterpretation, GC or raw object-store conversion is performed.

GitHub tree metadata integration

Ordinary GitHub data remains latest/archive ZIP assets. Tree metadata reuses the v1 pure directory codec and first-two/rest sharding, with a distinct projcli.github-tree-snapshot.v1 binding. A readable JSON catalogue deliberately duplicates membership for inspection and existing immutable-version lookup; its inventory hash must equal the graph’s expanded membership. No raw CAS object path is followed for ordinary payload bytes.

The existing bounded metadata bundle now allowlists directory objects as well as histories/bindings. Validate all object identities before controlled graph reads; missing, corrupt or contradictory metadata fails before HTTP mutation. Private disk-backed graphs are prepared before uploads and copied to selected full project locations only after all required HTTP succeeds. Small references remain last. Flat IDs and earlier nodes survive style changes. No compression/performance, multi-target atomicity or new snapshot-discovery guarantee is implied.

Bounded M3 release evidence

The final pinned gate retains actual native CAS stores and exact recovered files after a two-build analysis plus ordinary backup. It recovers by explicit snapshot ID into a fresh project, then probes missing/corrupt content and malformed metadata without modifying good targets. A separate Rust witness checks retained snapshots against recovered bytes and ordinary CSV hashes. Broader discovery and performance work remains deferred; complete platform suites cover writer, interruption, retry and all format/placement boundaries. Passing this gate is source evidence; release/install verification remains separate.

Legacy lookup publication coordination

Raw-JSON legacy IDs and the headerless four-column .projr/manifests.csv lookup remain readable and writable. Publication now owns cooperative claims for both the physical store and project legacy-ledger root, with sorted/deduplicated physical coordination roots.
