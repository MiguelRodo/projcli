Projr remote compatibility inventory

Source audit, 23 October 2026. Pinned R source: SATVILab/projr 90be50132d16aee33e39c0f7f35ef906c35f5397. Rust audit baseline: 41cd7b2f; current delivery is listed below, including the separate CSV slice PR175. This inventory was checked against dispatch, config parsing/defaults, store/restore code, shipped template, documentation and test sources. R tests and live provider operations were not executed for this audit. A test file is evidence of coverage intent, not proof of a passing integration run.

Released in preview.3: explicit local latest/archive listing and staged download, file-inspected store strategies, native GitHub Release asset/ZIP transfer and explicit replacement, and configured single-label local/GitHub restore are implemented. Automatic ordinary publication and metadata-history/cue integration are implemented for latest/archive; default multi-label restore and complete credential-helper parity remain gaps. The published and installed preview.3 packages these features. CSV capture does not complete remote parity or M2. CAS is an additional third structure, not the replacement manifest format or the only archive layout.

Store, inspection and metadata

Production/output builds only enter send; previews skip it. GitHub releases can be prepared/created before analysis when configured. Destination parameters and YAML are resolved per title, then labels are processed in content order. Source files for a send come from the project’s current-version manifest, not an unqualified directory listing. The last label also triggers changelog writing. Preparation, send, planner.

Plan execution, ZIP helpers, hashing, listing/path filters.

Local metadata is ordinary manifest.csv, VERSION and CHANGELOG.md at the remote pre-root. GitHub uses manifest.zip, VERSION.zip and CHANGELOG.zip containing those files. VERSION has per-label release entries and optional trailing * indicating untrusted state. These files are distinct from CAS JSON and the plural Rust .projr/manifests.csv index. Metadata.

There is no all-or-nothing remote transaction: local copying/removal can be partial, GitHub whole-asset replacement deletes an old asset before uploading, and metadata is written after content. Metadata-download failures may become empty/unavailable state; some unzip errors are swallowed. Rust should retain its approved safety boundaries, surface errors and never claim rollback of remote side effects. HTTP replacement, GitHub transfer.

Credentials and dependencies

GitHub lower helpers accept explicit token/api_url. Otherwise token lookup is GITHUB_PAT, optional R gh::gh_token, optional gitcreds, GH_TOKEN, GITHUB_TOKEN. API base is explicit override, GITHUB_API_URL, public API. Enterprise gitcreds lookup strips /api/v3; public lookup uses https://github.com. Requests carry an Authorization header and may be unauthenticated without a token. Repository inference prefers origin then first Git remote, using available gh R helpers or system Git/gert. Explicit Enterprise overrides are not forwarded by every wrapper. Authentication, repo inference, HTTP.

These are source mechanisms, not authorisation to obtain new credentials, change permissions or install dependencies. Rust should use supported existing access, mock HTTP for fixtures, redact secrets and never store tokens in CSV/URLs. Current Rust transport accepts explicit API/token inputs; configured restore uses GITHUB_API_URL and existing GITHUB_PAT/GH_TOKEN/GITHUB_TOKEN values. Explicit repository selection avoids Git; inference currently uses origin only and checks its host against the API. R gh/gitcreds fallback and first-other-remote inference remain missing. R helper auto-install behaviour is not adopted. Real Git remains an optional installed dependency; GitHub CLI is separate and need not be mandatory for an API implementation. Optional managed Git is not planned by default.

Source defects and documentation-only surfaces

These are source-review findings, not executed reproductions or requirements to copy bugs. Keep claims bounded until fixture evidence exists.

  • Default source selection passes an inner mapping where the next helper expects the provider mapping; explicit provider selection can call a title-specific helper with a null title. Selection.
  • GitHub existence checks hard-code label/version names, ignoring some custom path/append-label settings; local archive discovery assumes a label directory. GitHub existence, version paths.
  • Title send-check reads top-level cue while defaults populate send.cue; the cue setter also writes a different level. Send, defaults.
  • get/conflict fields are validated but no effective execution consumer was found. wrapper docs mention never/version and OSF, outside actual enums.
  • GitHub unzip failures can be swallowed, clone restore ignores partial failure, and low-level asset deletion can infer the current repo despite a repo argument. GitHub, HTTP, clone.
  • Content option sets, wrapper checks and boolean auto-content helpers differ; special code/package labels alone do not prove working end-to-end export.

Critical configuration assessment, separate from compatibility

This assessment excludes the agreed temporary CSV choice. Examples use the existing R inline build configuration, not a newly approved Rust schema. Findings are source-backed; unless stated otherwise they are not executed reproductions. Proposed fixes are review candidates, not silent semantic changes.

Rank/type Example and user impact Smallest proposed fix
High: ineffective accepted setting A destination with send: {conflict: skip} passes allowed-value checks, but store execution never reads conflict. get: {strategy: upload-missing, conflict: error} similarly has no restore consumer. Users can believe a non-overwrite policy is enforced. Checks, execution. Reject ineffective combinations until implemented, or implement and test them explicitly. Do not silently ignore a safety control.
High: colliding-target combination build.local.shared with content: [raw-a, raw-b], structure: latest, path-append-label: false, send: {inspect: file, strategy: sync-diff} gives both labels one physical directory. File inspection can classify the other label’s files as extras. Custom archive/pre-root paths also assume layouts not uniformly supported. Layout, planner, versions. Resolve all target identities before mutation and reject collisions; verify supported custom-prefix/append combinations rather than accepting untested layouts.
High: destructive restore ordering A normal configured restore source plus projr_content_update(clear=TRUE) clears the destination before source resolution/download. A missing release or failed network call can leave data gone. clear defaults FALSE; this is an unsafe opt-in ordering, not an unsafe default. Restore. Download into private staging, validate, then apply guarded promotion. Preserve current data on lookup/download failure.
Medium: surprising default synchronisation build.local.shared: {path: backup, structure: latest, content: [output]} defaults to sync-diff, so remote-only files can be removed. A user expecting an additive backup may be surprised. Default archive keeps prior version directories, which narrows the risk. Defaults, planner. Clearly expose adds/removes and the resolved strategy before applying; require deliberate review before changing defaults. This is a usability/policy concern, not evidence that sync-diff itself is defective.
Medium: profile cannot disable with null Base build.github.archive selects output; a local/profile build.github.archive: null inherits the base mapping. Removing one active-profile destination also does not remove its base definition. Merge. Explain merged effective destinations and provide a deliberately designed disabling/empty-selection mechanism. Do not reinterpret null without an approved compatibility change.
Medium: argument precedence surprise YAML build.local.archive: {content: [raw-a], path: backup} means archive_local=c(‘raw-b’) does not replace that archive definition. always_archive also defers to explicit archive YAML. Dispatch. Document this as YAML authority and display the resolved content; avoid presenting these arguments as ordinary overrides. Whether arguments should override is a design choice.
Medium: two cue locations send: {cue: always} is completed and used per label, while title-level send checking and the setter reference top-level cue. This invites inconsistent getter/setter behaviour; nested cue is not simply unused. Send, defaults. Use one canonical nested location and test the public setter through an actual store plan; treat an alias only through explicit conflict rules.
Medium: provider-dependent identity build.github.nightly: {id: another-tag, content: [output]} validates an id, but completion resets it to nightly. Local id instead becomes path. Title is cosmetic locally and functional on GitHub. Completion. Reject or clearly deprecate ignored id values; document title/tag/path meanings. A larger unified identity design is separate.
Medium: source-selection defects directories.raw-data.source: {github: archive}, as shipped in the template, meets default helper paths that pass the wrong mapping level or an absent title into a title-specific branch. Template, selection. Fix source selection with explicit/default provider/title fixtures; do not require users to discover accidental nesting workarounds.
Medium: unsupported documentation send.cue: never and structure: version are mentioned in wrappers but excluded by current enums; old OSF prose outlives implementation. Wrappers, enums. Correct docs and errors. Implement new values only if separately requested, not to make stale prose true.
Already recorded design Removing a build destination can remove a historical restore source because definitions and upload selection share the same location. The original registry proposal is issue706. Named definitions and independent ordinary upload/source lookup are now implemented in PR211; further per-remote format integration remains in progress. The source audit itself did not implement it.
Low: naming preference dest versus destinations changes readability, not provider or safety behaviour. Choose during the existing registry discussion; no new alias or migration silently introduced.

Credential lookup also deserves explicit presentation: ambient R gh/gitcreds resolution precedes GH_TOKEN/GITHUB_TOKEN, and repository inference may choose origin or the first remote. A supplied environment token or repository can therefore differ from a user’s expectation. The smallest safe improvement is clear resolved host/repository diagnostics without secrets, plus tests for explicit overrides; no new credential permissions are implied.
