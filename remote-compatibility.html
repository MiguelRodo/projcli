Projr remote compatibility inventory

Source audit, 23 October 2026. Pinned R source: SATVILab/projr 90be50132d16aee33e39c0f7f35ef906c35f5397. Rust comparison: 41cd7b2f, plus the separate CSV slice PR175. This inventory was checked against dispatch, config parsing/defaults, store/restore code, shipped template, documentation and test sources. R tests and live provider operations were not executed for this audit. A test file is evidence of coverage intent, not proof of a passing integration run.

Current boundary: local CAS export is implemented in Rust. Ordinary projr latest/archive store/restore and GitHub Release-asset transport are still gaps. CSV capture does not complete them or M2. CAS is an additional third structure, not the replacement manifest format or the only archive layout.

Store, inspection and metadata

Production/output builds only enter send; previews skip it. GitHub releases can be prepared/created before analysis when configured. Destination parameters and YAML are resolved per title, then labels are processed in content order. Source files for a send come from the project’s current-version manifest, not an unqualified directory listing. The last label also triggers changelog writing. Preparation, send, planner.

Policy Implemented operation Required Rust fixture
upload-all Add every current source-manifest file; no removal of destination-only names. Existing destinations can be marked untrusted. Existing extra file retained; source overwrite and empty-label cases.
upload-missing Add names absent remotely; retain existing remote bytes, including changed same-name content. Same-name different bytes retained; missing names added.
sync-diff Add missing/changed files, remove remote-only files; compare via chosen inspection. Add/change/delete transitions and no-change cue.
sync-purge Clear/recreate destination content then upload full selected set when plan says needed. Disposable fixture only; never user dataset destructive tests.

inspect:manifest Compare recorded rows/version trust. If unavailable/untrusted, planner may fall back to file hashes. Matching/missing/stale/corrupt metadata and trust markers.
inspect:none No comparison evidence; default upload-all and untrusted existing-state handling. Never label unchecked remote bytes verified.

Hidden files, nested names, exclusions and empty-after-exclusion; no regex/pathspec interchange assumption.

Plan execution, ZIP helpers, hashing, listing/path filters.

Local metadata is ordinary manifest.csv, VERSION and CHANGELOG.md at the remote pre-root. GitHub uses manifest.zip, VERSION.zip and CHANGELOG.zip containing those files. VERSION has per-label release entries and optional trailing * indicating untrusted state. These files are distinct from CAS JSON and the plural Rust .projr/manifests.csv index. Metadata.

There is no all-or-nothing remote transaction: local copying/removal can be partial, GitHub whole-asset replacement deletes an old asset before uploading, and metadata is written after content. Metadata-download failures may become empty/unavailable state; some unzip errors are swallowed. Rust should retain its approved safety boundaries, surface errors and never claim rollback of remote side effects. HTTP replacement, GitHub transfer.

Credentials and dependencies

GitHub lower helpers accept explicit token/api_url. Otherwise token lookup is GITHUB_PAT, optional R gh::gh_token, optional gitcreds, GH_TOKEN, GITHUB_TOKEN. API base is explicit override, GITHUB_API_URL, public API. Enterprise gitcreds lookup strips /api/v3; public lookup uses https://github.com. Requests carry an Authorization header and may be unauthenticated without a token. Repository inference prefers origin then first Git remote, using available gh R helpers or system Git/gert. Explicit Enterprise overrides are not forwarded by every wrapper. Authentication, repo inference, HTTP.

These are source mechanisms, not authorisation to obtain new credentials, change permissions or install dependencies. Rust should use supported existing access, mock HTTP for fixtures, redact secrets and never store tokens in CSV/URLs. R helper auto-install behaviour is not adopted. Real Git remains an optional installed dependency; GitHub CLI is separate and need not be mandatory for an API implementation. Optional managed Git is not planned by default.

Source defects and documentation-only surfaces

These are source-review findings, not executed reproductions or requirements to copy bugs. Keep claims bounded until fixture evidence exists.

  • Default source selection passes an inner mapping where the next helper expects the provider mapping; explicit provider selection can call a title-specific helper with a null title. Selection.
  • GitHub existence checks hard-code label/version names, ignoring some custom path/append-label settings; local archive discovery assumes a label directory. GitHub existence, version paths.
  • Title send-check reads top-level cue while defaults populate send.cue; the cue setter also writes a different level. Send, defaults.
  • get/conflict fields are validated but no effective execution consumer was found. wrapper docs mention never/version and OSF, outside actual enums.
  • GitHub unzip failures can be swallowed, clone restore ignores partial failure, and low-level asset deletion can infer the current repo despite a repo argument. GitHub, HTTP, clone.
  • Content option sets, wrapper checks and boolean auto-content helpers differ; special code/package labels alone do not prove working end-to-end export.

Critical configuration assessment, separate from compatibility

This assessment excludes the agreed temporary CSV choice. Examples use the existing R inline build configuration, not a newly approved Rust schema. Findings are source-backed; unless stated otherwise they are not executed reproductions. Proposed fixes are review candidates, not silent semantic changes.

High: ineffective accepted setting A destination with send: {conflict: skip} passes allowed-value checks, but store execution never reads conflict. get: {strategy: upload-missing, conflict: error} similarly has no restore consumer. Users can believe a non-overwrite policy is enforced. Checks, execution. Reject ineffective combinations until implemented, or implement and test them explicitly. Do not silently ignore a safety control.
High: colliding-target combination build.local.shared with content: [raw-a, raw-b], structure: latest, path-append-label: false, send: {inspect: file, strategy: sync-diff} gives both labels one physical directory. Medium: source-selection defects directories.raw-data.source: {github: archive}, as shipped in the template, meets default helper paths that pass the wrong mapping level or an absent title into a title-specific branch. Credential lookup also deserves explicit presentation: ambient R gh/gitcreds resolution precedes GH_TOKEN/GITHUB_TOKEN, and repository inference may choose origin or the first remote. Explicit GitHub Release asset transport

The source candidate adds native HTTPS REST asset listing, new uploads and staged downloads through remote github assets/upload/download. It preserves Enterprise API base paths and exact Release tags, lists paginated assets, and strips authentication from binary redirects. Uploads require an existing token; duplicate asset names fail without deleting the old asset. Release creation is explicit. Downloads require an explicit byte limit and protect project authority files, links and special entries, preserving old bytes on incomplete transfers. Network failures after upload may leave an uncertain remote result; inspect it before retrying. No credential installation or live-data test is authorised.

Tokens use GITHUB_PAT, then GH_TOKEN, then GITHUB_TOKEN. GITHUB_API_URL selects the API base. Git credential helpers and gh-token fallback remain unported here. Listing/downloading public assets can be anonymous. Literal loopback HTTP is accepted for disposable fixtures; ordinary service URLs require HTTPS.

This is the actual transport prerequisite for existing projr GitHub latest/archive support, not complete configured publication/restore. ZIPs are opaque in this slice; packaging, projr names, VERSION/manifest/CHANGELOG ZIP metadata, replacement policy and configured restore remain subsequent work. No registry/CAS redesign. Pinned comparison: remote-github-httr.R REST transport and remote-github.R ZIP transfer at 90be50132d16aee33e39c0f7f35ef906c35f5397.

Ponytail full: one concrete HTTP client and an established synchronous HTTPS crate rather than a provider trait, GitHub CLI dependency or custom TLS. Reuse existing path guards and tempfile replacement. Mocked local HTTP fixture tests exercise real requests/bodies and CLI JSON without live GitHub writes. No local compilation/tests run; remote exact-head compilation, locked/API/docs/acceptance and independent review are still required. Source candidate is not installed.

The CLI does not initialise HTTP wire logging and its own error messages omit tokens, response bodies and signed redirect URLs. Library embedders must avoid ureq DEBUG/TRACE logging for sensitive requests because dependency logging is not redacted. Redirects remove Authorization but do not confine network access to a provider host; this transport is not a network sandbox.

GitHub ZIP packaging and explicit directory transfer candidate

This candidate extends the native Release transport with projr flat names: prefix-label-vVERSION.zip for archive, prefix-label.zip for latest, and -empty before .zip for empty variants. With no prefix, the label is always used, including path_append_label=false. Metadata assets remain shared and unprefixed: manifest.zip contains manifest.csv, VERSION.zip contains VERSION, and CHANGELOG.zip contains CHANGELOG.md. Directory ZIP entries are relative to the selected source, without an enclosing folder. Nonempty parent-directory entries retain Unix permission modes; empty directory entries remain omitted. Empty sources contain the single zero-byte projr-empty sentinel; empty subdirectories are not archived.

The CLI adds remote github upload-directory (label/structure/remote-version, optional prefix/path-append-label), upload-metadata (kind manifest/version/ changelog and a source directory), and download-directory (exact asset name, destination, max-bytes, max-expanded-bytes, optional clear/empty). Uploads remain new-name-only; metadata is packaged byte-for-byte rather than silently merged. Download stages extraction privately and uses the existing guarded merge/clear installer. Explicit empty requires exactly the sentinel and consumes it before installation. Destination-only files survive unless clear is requested.

Safety changes from R’s direct utils::unzip: bounded expanded bytes and100000 members, CRC validation, reject links/special/encrypted entries, traversal, backslashes, device names, native aliases, duplicate members and parent/file collisions before project installation. Retain existing installer rollback and Windows backup-cleanup limits; no crash/concurrent-writer guarantee is added.

Ponytail full: one ZIP crate with only Deflate enabled, existing MD5 inventory, HTTP client and guarded installer. No backend interface, registry or new YAML policy. Independent tests cover exact metadata/Unicode/hidden/empty members, malicious names, CRC/expanded limits and mocked actual ZIP upload/download merge/clear. No local heavy tests; remote lock resolution, exact-head platform/ pinned/docs acceptance and independent review are pending.

Pinned sources: flat names, ZIP layout, empty sentinel, metadata assets. Configured source selection/restore, historical metadata merging, latest asset replacement, credentials-helper fallback and CAS remain outstanding. This source candidate does not update the published/installed preview.

Review amendments share the existing native directory-entry alias guard with file-policy transfers, validate empty-directory CRC with a bounded probe, and never persist an expanded-byte probe beyond each member’s advertised size. Directory modes apply deepest-first after extraction; an existing destination’s modes still follow the previously documented merge policy. File-only ZIPs from other writers have no directory privacy metadata to restore. Source root modes are not encoded as a new manifest field. No ACL/ownership/xattr claim follows. Temporary paths are created beneath the physical canonical system temp directory; macOS /var aliases are not an excuse to weaken external path guards.

Extraction also checks actual directory spelling immediately after creation, rejecting filesystems that rewrite it rather than merging distinct Unicode members. The extracted-tree owner restores directory owner access for cleanup; explicit close reports a retained path on cleanup failure. The directory-transfer command checks extraction and transfer cleanup on success and failure and distinguishes installed output from failed transfer. Readonly/zero-mode owned directory cleanup is exercised unprivileged in the pinned gate.

Explicit GitHub asset replacement

The source candidate adds –replace to upload, upload-directory and upload-metadata, and GithubReleaseClient::replace_asset. Default uploads still reject existing names. Explicit replacement follows the working projr delete-then-upload sequence: remote-github-httr.R554-662.

Before deletion, validate the regular source, stage its complete bytes privately, resolve the Release/unique asset and validate its trusted upload endpoint. An absent name uploads normally. A successful delete is followed by one upload; errors after deletion explicitly state that the previous asset was deleted. An interrupted deletion reports an uncertain old-asset state and does not start the upload. This is not atomic publication, backup retention or remote rollback. There is no automatic retry, new history/sealing policy or changed YAML default.

Ponytail full reuses the existing client and request/body fixtures, with a private file snapshot only for explicit replacement. Mocked end-to-end witnesses cover staged bytes despite source mutation after delete, exact DELETE/POST ordering, denied/interrupted delete, failed/malformed upload, untrusted endpoints, ambiguous names, unsafe sources and machine CLI output. These are mocked REST operations, not actual GitHub Release mutations. No live user data/credentials or local heavy tests. Remote exact-head gates and independent review remain required. Configured restore/source selection and full automatic publication remain next.

Configured single-label restore candidate

remote restore –label LABEL –max-bytes N –max-expanded-bytes N resolves one declared final directory from merged active configuration. Optional –position source/dest, –provider local/github and –title restrict lookup; –profile follows existing earlier-profile/local precedence. –remote-version selects an exact archive version; otherwise numeric newest is selected. GitHub latest reads canonical VERSION.zip, then downloads its label ZIP. –repository owner/repo avoids requiring Git; otherwise origin is inspected locally and its host must match the API. GITHUB_API_URL and existing environment tokens retain the explicit transport contract. No credentials are installed.

Existing per-directory source.local/source.github title references or named inline definitions precede eligible build.local/build.github destinations. A shared referenced definition may be refined inline through the existing deep merge (null still inherits). Destination source:false excludes it; true or a matching label preference beats the first eligible fallback. content:null/false selects nothing, true selects declared non-cache roles, and lists select declared labels. Source/provider/title declaration order is preserved. No retry switches to another configured source after lookup/download fails.

A valid root manifest.csv is required, matching projr’s prior-build gate. Labels with no recorded files and advertised empty variants skip without clearing. CSV history is not used as an integrity/trust proof. Full sources stage before the existing merge/clear installer; –clear never removes files before a source has been found and copied. Default merge preserves destination-only files. Machine results disclose restored/skipped, selected provider/title/version and destination; failures stay structured and do not print tokens or raw config.

This deliberately fixes R source-selection indexing/inline-definition bugs and clear-before-lookup data loss. It does not add R’s implicit hard-coded archive fallback: undeclared remotes/paths are errors under the agreed explicit mapping contract. Nonempty get policy mappings fail explicitly rather than pretending that R’s ineffective get.strategy/get.conflict controls work. Send policy is not executed by restore. Definitions retain local path versus GitHub title/tag id semantics, including spaces and @version tag normalization.

Boundary: ordinary inline remote/source fields are accepted by this command’s read-only configuration projection only. Normal build validation still rejects unsupported ordinary publication fields, preventing silently ignored uploads. Configured automatic publication, cue/history policy integration, all-label default restore, complete credential-helper fallback and the issue706 registry remain subsequent work. Installed preview remains unchanged.

Filesystem and mocked REST actual CLI fixtures cover source priority, references/inline/profiles, destination preference, numeric archives, VERSION ZIP latest, clear/merge/empty and corrupt failure preservation.
