Preview release checks

The review and delivery sequence, with verified preview.2 evidence.

Verified preview.2

0.4.0-preview.2 is now published and installed in the checked WSL user-local location. Its exact source is 768da1bf1b83be83b657b36219f299f37130ba03. See delivery evidence for actual-main, exact-tag, public-byte and installed-binary checks. The sequence below remains the release checklist.

What preview.2 adds

Change What it means for this release
Keep one project context A child command keeps the selected project, configuration and run version when a script changes folder.
Separate trial results from released files Generated-output path queries default to a folder under the selected cache for that run’s version. A successful production build can copy declared results to their final folders.
Use familiar working folders Scripts inherit the folder from which the build was launched; document tools keep their native rules. An explicit project-folder option remains available.
Control output cleanup The default keeps other final output files. You can opt into clearing immediately before analysis or after successful analysis. Preview does not clear released outputs. Document-output replacement has its own documented rules.
Handle R package data explicitly output-r-data resolves to the project’s data folder for final lookup. Only an explicit declaration, or a normalized legacy data declaration, opts that folder into ordinary build management.
Share supported HTML reports Individual Quarto/R Markdown HTML and modeled Quarto projects default to embedding resources when unspecified. Explicit and inherited false values remain respected.
See useful results and failures The acceptance fixtures produce a CSV and an HTML report, preserve prior final/archive bytes on preview or supported failure, and return structured success/failure results. Git credentials are not required for these local workflows.

The selected R/Python/report example has a verified order. A renderer can handle several documents as one project; this does not promise arbitrary mixed-language targets always execute one by one in the order written.

Limits that stay in place

  • The existing R package and its helpers are unchanged. The acceptance examples call the CLI through small test adapters; they do not prove RStudio, Knit or direct R API parity.
  • Bookdown’s site renderer keeps its native resource policy. This slice does not add its embedding fallback. Do not treat its linked site as a portable single-file HTML report.
  • Individual rendering still rejects unsupported inherited/external metadata and unsupported layouts. Quarto project metadata remains a separate supported path; nested Quarto projects are rejected.
  • Project fallback requires modeled text inputs and temporarily prepares only unspecified HTML options. It restores original source bytes. Changing a prepared source or native input set before rendering is rejected; other input types need explicit renderer embedding settings.
  • Explicitly nonembedded HTML may need its original resources. Literal Markdown and LaTeX references keep their native meaning; no resource URLs are rewritten.
  • Preview recovery covers recorded managed paths. It does not isolate arbitrary script effects, handle every concurrent change, or provide crash/power-loss atomicity.
  • Complete provenance, durable attempt/release records, analysis-free publication retry and M2 remain unfinished.
  • Delivery remains Linux/WSL and Windows x86-64. macOS/ARM binaries are not supplied.

Use sample data or an independently backed-up disposable copy while evaluating this development preview. Read the build reference and lifecycle before production use.

Review status and evidence

The source slices, version change and actual integrated gates are complete for preview.2. The delivery evidence links exact source, remote acceptance and tagged assets. The checklist is retained for subsequent candidates; a branch preparation pass alone is never delivery evidence.

Final integrated acceptance

  1. Finish independent review and integrate the source slices, then the acceptance driver. Record the exact resulting source commit. Resolve documentation and workflow overlaps without changing reviewed behavior; report any new head.
  2. Run the existing pinned-image workflow on that exact integrated tree. Require complete locked Rust regressions, documentation examples, warning-free API documentation, actual R/Python/rendering acceptance and the combined M1 driver. Retain host-platform, installer and website checks and the existing native-browser documentation witness.
  3. Inspect the JSON and downloadable files from both acceptance drivers. Confirm configured/no-init and actual local directory initialization; ordered Python/R/report steps; computed CSV value 84; four relocated embedded reports; structured deliberate failures; unchanged prior ordinary generated-output/archive bytes under none; prior docs preserved on preview/failure and replaced on successful document finalization; and exactly two expected-role local archive manifests for each successful production case, with object bytes matching the CSV/report witnesses and index/manifests identifying release1.2.4. Require the final project VERSION to be next-dev1.2.4.1. Preview/failure cases must create no archive manifests. Require the corruption probes, immediate init-directory checks and failing Git-call witness as well.
  4. Require the R-data undeclared/explicit/legacy activation matrix and embedding unspecified/explicit/inherited-false matrix on the same integrated source. A previous green branch is supporting evidence, not a substitute.
  5. Reconcile the website’s behavior, feature and compatibility descriptions with the actual supported CLI behavior and deferred limits. Record independent clearance before release work advances.

Preview.2 delivery satisfies the accepted M1 local CLI scope documented in feature status. For future candidates, record the accepted scope, exact integrated source and remaining limits; a preparation-only pass is never a release or installation guarantee.

Release and WSL installation sequence

  1. Prepare a separate reviewed version change. Cargo.toml and the root package entry in Cargo.lock must agree. The CLI package version is distinct from an analysis project’s VERSION; do not change users’ project versions.
  2. Prepare release notes for the chosen version and exact source. Keep the public README/install download commands and downloaded-binary documentation checks pinned to the previously published preview throughout tagging, draft asset checks and publication. Their CI fetches public downloads and source-commit.txt, so an unpublished pin cannot pass those checks.
  3. Only after the source/version gates pass, tag the exact reviewed commit and run the existing preview release workflow. It creates a draft prerelease. Inspect both actual platform assets, source-commit.txt, version.txt and the exact checksum entries. Run the remote binary and installer checks.
  4. Publish only the verified draft, then confirm public downloads match the checked assets. Only after public-byte verification, make a separate post-publication documentation change updating README/install pins, version wording, source-commit links and downloaded-binary check expectations together. Run those public-download checks before merging that documentation change. Keep the instructions in plain language, with platform/deferred limits visible; never silently substitute GitHub’s older stable Latest.
  5. Inside WSL Ubuntu, preserve the previous user-local binary, download the explicit published version, verify its checksum and install into the existing user-writable directory. No local Rust compilation, administrator access or persistent authentication changes are needed. Do not disturb thesis containers, the existing R package or the Windows Codex process.
  6. Check the installed binary by its full path for version, help and machine capabilities, then run a tiny disposable configured preview and deliberate failure. Confirm the shell resolves the expected command. Record the actual installed version and verification evidence before saying installation is done.

This checklist does not perform release operations; completed preview.2 delivery is recorded above.
