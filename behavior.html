Project and execution behavior

This is the product behavior contract. Confirmed decisions below guide implementation; they are not claims that the current CLI already implements them. Proposals require review before they become requirements. The compatibility log records pinned projr comparisons, decisions, actual test evidence, Ponytail reviews and remaining gaps; update it with each PR.

Confirmed decisions

  • A project is one analysis/build unit anchored at a selected root directory. It has settings, version information and named resource paths where applicable. Resource paths may be outside the root; a project need not be a Git repository.
  • Explicit project selection overrides discovery and selects that exact directory.
  • Automatic discovery walks upward from the invocation directory. The nearest recognized project root wins, including when projects are nested. Discovery does not search downward for projects.
  • Retain existing projr root markers, including standalone VERSION and README, VCS roots, R-package/RStudio/renv/Quarto project markers, and extend recognition for pyproject.toml, Project.toml and JuliaProject.toml. Proj configuration files _proj.yml / _projr.yml also identify a root. requirements.txt and Manifest.toml alone do not. Recognition must no longer require VERSION before considering the other markers.
  • _proj.yml is the primary base configuration. Accept _projr.yml as a legacy alias and fail clearly if both base files exist; do not silently merge them.
  • Configuration precedence follows projr: local overrides profiles, profiles override base, and earlier-listed profiles win conflicts with later ones.
  • Missing dev.scripts falls back to build.scripts. An explicit empty list in either selects no analysis scripts and never triggers fallback/discovery. Hooks still run; production version/publication/export behavior remains available for upload-only workflows. Development previews never publish. Analysis cleanup and promotion are skipped when no analysis is selected, preserving upload inputs.
  • With no recognized marker, discovery falls back to cwd. This does not waive build validation: builds require an active root-level proj configuration. The agreed _proj.yml / legacy _projr.yml names apply; explicitly activated profile files may supply configuration, but inactive profile files alone do not. No-config build assumptions from the initial roadmap are superseded.
  • Every framework/resource directory used at runtime must be explicitly declared. Initialization may write familiar projr defaults into configuration; runtime must not synthesize missing directory mappings or unknown subpaths.
  • Unsupported behavior-affecting configuration fails before mutations.
  • Failed supported builds must restore pre-build state except permitted cache residue. This is required behavior, not an implemented transaction guarantee.
  • Storage/publication retries must have an upload-only route without rerunning analysis or falsely recording a new analysis. Explicit-empty analysis supports hooks/publication, but full retry identity/transaction semantics are separate.
  • The existing R package is entirely off limits in this effort. Direct R frontend integration is later work; no existing helper changes or parity claims follow from these Rust changes.
  • Default script/document enumeration is shallow at the selected project root. Subdirectory targets require explicit selection or renderer project configuration.
  • Scripts execute relative to the project root by default. Selecting a script in a subdirectory does not, by itself, select a different project or execution root.
  • The resolved root is captured for the run. Path helpers, including a future frontend’s projr_path_get(), resolve against that root even if a renderer or user script changes its working directory.
  • A supported Quarto project’s root must equal the proj root. Nested Quarto projects beneath that root are unsupported for now. Nested document files are distinct from nested Quarto projects.
  • QMD rendering through projr, quarto::quarto_render(), and RStudio QMD Render must agree on evaluation directory and root-helper semantics. R Markdown Knit is a distinct entrypoint and must be verified separately. Shared project configuration and direct-entry root resolution are required; CLI-only flags or a parent process environment cannot establish this parity.
  • Direct rendering does not imply the build, version, commit or archive/export side effects of a proj-managed build.
  • Renderer evaluation roots must use supported renderer controls. Setting only the parent process cwd is insufficient. Root identity and evaluation cwd remain separate concepts; document asset/reference resolution is not redefined here.

The project root is the analysis workspace’s top-level directory, not the user’s operating-system home directory. Resolving a named resource path is also distinct from changing cwd or selecting a new root.

Proposals and open decisions

  • Apply the base filename compatibility rule consistently to profile/local files and define the effective profile-list source once for config and environment.
  • Evaluate Quarto execute-dir and R Markdown knit_root_dir / knitr root.dir for root-relative execution. Define the shared persistent configuration and direct-entry initialization before broad renderer changes; do not add nested Quarto project support or rely only on flags passed by proj.
  • Frontend transport/bindings and remaining environment/YAML compatibility details must be explicit. Familiar projr directory defaults belong in init-generated configuration only; Rust’s _raw and synthesized raw/data runtime paths are not acceptable substitutes for undeclared directories.

Implementation gaps and verification

The core root finder implements nearest-recognized-ancestor discovery without a VERSION prerequisite. Its marker tests cover the retained projr patterns and deliberate Python/Julia/proj-config extensions and cwd fallback. Builds now require active configuration and typed validation rejects unsupported fields. Explicit directory mappings are enforced without runtime path defaults; full failure restoration remains open; historical passing fixtures do not demonstrate those new requirements. Individual scripts currently start in their parent directory. Captured-root stability is implemented for core CLI child queries after cwd changes, including independent simultaneous roots; direct R frontend/renderer parity remains unimplemented. Base-file aliases and first-wins profile merging use one merged typed configuration for validation and build script/hook selection. Profile/local filenames retain their existing _projr- form for now. Explicit empty script selection now skips analysis while preserving hooks and production publication; its tests cover production archive bytes and preview nonpublication without invoking real renderers.

Verify nested projects, explicit selection, paths containing spaces, shallow default enumeration, explicit subdirectory scripts, changed cwd, and each supported renderer’s evaluation root. Compare the same nested QMD through projr, quarto::quarto_render(), and RStudio QMD Render; test R Markdown Knit separately. Reject a nested Quarto project clearly. Verify that direct rendering leaves proj-managed release/version/export state alone. Use tiny fixtures and remote CI where practical. Subprocess execution is not a security sandbox, and path hashes alone do not establish scientific correctness or a reproducible environment.

Future R distribution and tests

The R wrapper/CRAN design note records separate CLI installation, unconditional R-only tests, conditional CRAN executable tests and mandatory pinned/checksummed executable integration in our CI. It is future design, not a shipped wrapper, CRAN approval or automatic-download permission.

Managed destructive destinations

Production builds and direct cleanup helpers reject project-root/ancestor write destinations, resource/staging overlaps, selected-input containment, VCS metadata, path separators in labels and symlinked write destinations. Empty analysis still runs hooks and must validate managed destinations. Disjoint external resource paths remain supported. Generic directory moves require an existing source and disjoint destination with resolved parents; symlink aliases are rejected.

Project renderers are conservatively rejected when managed cleanup trees contain recognized source-like documents or linked entries; this is not exact renderer input discovery and can reject generated Markdown. Individual outputs must use portable leaf filenames and may not replace framework configuration/state. Concrete cache/output/asset paths are checked before VERSION or ignore writes. Literal project roots are escaped for explicit include/exclude globs so brackets in a root cannot hide selected inputs from safety checks.

These checks do not establish atomic promotion, full rollback, protection against concurrent filesystem replacement, or undo arbitrary external script effects.

Build environment context

Builds resolve one environment snapshot and pass it to their child commands and configuration-profile selection. Environment files do not mutate the parent process on this path. Inherited OS values win over local, earlier environment profiles and base assignments; explicit build profiles override inherited PROJR_PROFILE. The same values reach dependency probes, scripts/hooks/renderers and existing Git helpers. Direct public legacy EnvGuard APIs and CLI startup guards still mutate process state and are not concurrent environment APIs. This change does not approve credential injection policy or establish a sanitized/sandboxed environment.

Captured execution root and bounded individual render layouts

Script and hook subprocesses start in the captured project root, retaining explicit selected input paths. Quarto receives --execute-dir with that root; individual R Markdown uses knit_root_dir and passes the input/root as data arguments to fixed R code. This implements CLI defaults, not direct R/IDE parity or a changed resource link resolution policy. The existing R package remains untouched.

Nested Quarto project metadata is rejected for selected documents and conservatively scanned implicit source trees. Individual rendering models one document-local format: HTML, PDF, Word, or supported native presentation/EPUB variants. Unknown/multiple formats, inherited individual metadata, custom R Markdown output filenames, dynamic R Markdown runtime and document-rendering hooks fail before controlled writes. Project-render validation remains conservative fresh-tree validation, not a complete renderer output manifest. Unsupported layout rejection does not assert renderer parity.

clear_output accepts only pre, post, or never; directory ignore accepts all, git, rbuild (case-insensitive), or an empty list. Invalid values fail before analysis, ignore synchronization or cleanup, including direct cleanup APIs.

Bounded CAS integrity

Ingestion requires an existing directory, disjoint from its CAS storage and project index. Reject linked/unsupported source entries, non-UTF-8 filenames and ambiguous logical paths; logical identities use slash-separated components and case-sensitive names. Digests are canonical 64-character lowercase hexadecimal BLAKE3 values. Copy and hash the same stream; verify existing objects before reuse. Publish complete objects/manifests without replacing conflicting content. Replace project index bytes through a same-directory temporary file, escaping CSV metadata fields.

Manifest inspection validates structure and manifest byte identity; file inspection also hashes referenced object bytes. This does not provide a stable snapshot across concurrent source changes, multi-writer serialization, power-loss durability or one transaction across remote manifest and project index. Failure may leave valid orphan objects or an unindexed complete manifest; errors propagate and old index bytes stay intact. No source file is modified by ingestion. Symlink-alias paths remain unsupported under the conservative path guards; callers should supply resolved physical paths.

Explicit Git operations

Git commits, pushes and network/upstream checks default off even when Git metadata exists. Only the resolved configured actions execute. Commit-enabled builds require clean initial Git state to avoid sweeping in unrelated edits; no-op commits succeed. Push captures the current branch’s configured upstream remote/reference before build writes. Missing upstream and unmodeled custom push-only routing fail early. Native authentication is the default. An explicit token-helper opt-in uses fixed host-scoped code and ephemeral environment data, never secret argv/source or persistent credentials. Local build success remains distinct from publication failure.

Versioned machine boundary

Opt-in --machine emits protocol-v1 results/errors on stdout, with capability version negotiation independent of project discovery. Static error codes avoid reflecting credentials/config/argv. Queries return typed values; other existing commands reuse the CLI through a noninteractive worker whose logs use stderr. See machine interface for supported shapes and limits. This is a transport boundary over existing anyhow errors, not a second domain-error overhaul.
