Project and execution behavior

This is the product behavior contract. Confirmed decisions below guide implementation; they are not claims that the current CLI already implements them. Proposals require review before they become requirements. The compatibility log records pinned projr comparisons, decisions, actual test evidence, Ponytail reviews and remaining gaps; update it with each PR.

Confirmed decisions

  • A project is one analysis/build unit anchored at a selected root directory. It has settings, version information and named resource paths where applicable. Resource paths may be outside the root; a project need not be a Git repository.
  • Explicit project selection overrides discovery and selects that exact directory.
  • Automatic discovery walks upward from the invocation directory. The nearest recognized project root wins, including when projects are nested. Discovery does not search downward for projects.
  • Retain existing projr root markers, including standalone VERSION and README, VCS roots, R-package/RStudio/renv/Quarto project markers, and extend recognition for pyproject.toml, Project.toml and JuliaProject.toml. Proj configuration files _proj.yml / _projr.yml also identify a root. requirements.txt and Manifest.toml alone do not. Recognition must no longer require VERSION before considering the other markers.
  • _proj.yml is the primary base configuration. Accept _projr.yml as a legacy alias and fail clearly if both base files exist; do not silently merge them.
  • Configuration precedence follows projr: local overrides profiles, profiles override base, and earlier-listed profiles win conflicts with later ones.
  • Missing dev.scripts falls back to build.scripts. An explicit empty list in either selects no analysis scripts and never triggers fallback/discovery. Hooks still run; production version/publication/export behavior remains available for upload-only workflows. Development previews never publish. Analysis cleanup and promotion are skipped when no analysis is selected, preserving upload inputs.
  • With no recognized marker, discovery falls back to cwd. This does not waive build validation: builds require an active root-level proj configuration. The agreed _proj.yml / legacy _projr.yml names apply; explicitly activated profile files may supply configuration, but inactive profile files alone do not. No-config build assumptions from the initial roadmap are superseded.
  • Ordinary framework/resource directories used at runtime must be explicitly declared. Built-in project and R-package data lookup are bounded exceptions described below. Initialization may write familiar projr defaults into configuration; runtime must not synthesize missing directory mappings or unknown subpaths.
  • Unsupported behavior-affecting configuration fails before mutations.
  • Explicit script and hook patterns, including exclusions, must have valid glob syntax. Invalid exclusions must fail preflight rather than silently select unintended code. Valid exclusion-only lists may select no files; an empty list still disables analysis.
  • Failed supported builds must restore pre-build state except permitted cache residue. This is required behavior, not an implemented transaction guarantee.
  • Storage/publication retries must have an upload-only route without rerunning analysis or falsely recording a new analysis. Explicit-empty analysis supports hooks/publication, but full retry identity/transaction semantics are separate.
  • The existing R package is entirely off limits in this effort. Direct R frontend integration is later work; no existing helper changes or parity claims follow from these Rust changes.
  • Default script/document enumeration is shallow at the selected project root. Directory and entry inspection failures must be reported; they must not silently become an empty or incomplete selection. Only regular root files are enumerated; links are not followed, and hidden/Git-ignored regular scripts remain eligible. Subdirectory targets require explicit selection or renderer project configuration.
  • Native runner working-directory behavior is the default; provide an explicit project-root execution override. Rscript/Python inherit launch cwd, source() normally inherits caller cwd, and QMD/Rmd document execution has its own native defaults. Selecting a nested file does not redefine project identity.
  • Resolve logical role targets from captured root/config/profiles/run version. Safe output/data roles use declared versioned cache; configured final destinations are separate. Auto path representation is caller-relative ordinarily and absolute in explicitly supplied render context; explicit absolute/relative bases override.
  • Embedded HTML is the supported target. Default embedding only when effective settings are unspecified; preserve explicit/inherited false. Literal Markdown/ LaTeX retain native resource meaning. Linked portability is deferred.
  • The resolved root is captured for the run. Path helpers, including a future frontend’s projr_path_get(), resolve against that root even if a renderer or user script changes its working directory.
  • A supported Quarto project’s root must equal the proj root. Nested Quarto projects beneath that root are unsupported for now. Nested document files are distinct from nested Quarto projects.
  • QMD rendering through projr, quarto::quarto_render(), and RStudio QMD Render are a future frontend parity goal, outside the bounded Rust M1 completion gate. Evaluation-directory/root-helper parity is not currently established. R Markdown Knit is a distinct entrypoint and must be verified separately. Shared project configuration and direct-entry root resolution are required; CLI-only flags or a parent process environment cannot establish this parity.
  • Direct rendering does not imply the build, version, commit or archive/export side effects of a proj-managed build.
  • Renderer evaluation roots must use supported renderer controls. Setting only the parent process cwd is insufficient. Root identity and evaluation cwd remain separate concepts; document asset/reference resolution is not redefined here.

The project root is the analysis workspace’s top-level directory, not the user’s operating-system home directory. Resolving a named resource path is also distinct from changing cwd or selecting a new root.

Proposals and open decisions

  • Apply the base filename compatibility rule consistently to profile/local files. The effective proj profile-list source is now defined below; renderer-native profile settings are not silently rewritten.
  • Evaluate Quarto execute-dir and R Markdown knit_root_dir / knitr root.dir for root-relative execution. Define the shared persistent configuration and direct-entry initialization before broad renderer changes; do not add nested Quarto project support or rely only on flags passed by proj.
  • Frontend transport/bindings and remaining environment/YAML compatibility details must be explicit. Familiar projr directory defaults belong in init-generated configuration only; Rust’s _raw and synthesized raw/data runtime paths are not acceptable substitutes for undeclared directories.

Implementation gaps and verification

The core root finder implements nearest-recognized-ancestor discovery without a VERSION prerequisite. Its marker tests cover the retained projr patterns and deliberate Python/Julia/proj-config extensions and cwd fallback. Builds now require active configuration and typed validation rejects unsupported fields. Explicit directory mappings are enforced without runtime path defaults; full failure restoration remains open; historical passing fixtures do not demonstrate those new requirements. Individual scripts currently start at project root; changing to native runner defaults with an explicit override is pending. Captured-root stability is implemented for core CLI child queries after cwd changes, including independent simultaneous roots; direct R frontend/renderer parity remains unimplemented. Base-file aliases and first-wins profile merging use one merged typed configuration for validation and build script/hook selection. Profile/local filenames retain their existing _projr- form for now. Explicit empty script selection now skips analysis while preserving hooks and production publication; its tests cover production archive bytes and preview nonpublication without invoking real renderers.

Verify nested projects, explicit selection, paths containing spaces, shallow default enumeration, explicit subdirectory scripts, changed cwd, and each supported renderer’s evaluation root. Compare the same nested QMD through projr, quarto::quarto_render(), and RStudio QMD Render; test R Markdown Knit separately. Reject a nested Quarto project clearly. Verify that direct rendering leaves proj-managed release/version/export state alone. Use tiny fixtures and remote CI where practical. Subprocess execution is not a security sandbox, and path hashes alone do not establish scientific correctness or a reproducible environment.

Future R distribution and tests

The R wrapper/CRAN design note records separate CLI installation, unconditional R-only tests, conditional CRAN executable tests and mandatory pinned/checksummed executable integration in our CI. It is future design, not a shipped wrapper, CRAN approval or automatic-download permission.

Managed destructive destinations

Production builds and direct cleanup helpers reject project-root/ancestor write destinations, resource/staging overlaps, selected-input containment, VCS metadata, path separators in labels and symlinked write destinations. Empty analysis still runs hooks and must validate managed destinations. Disjoint external resource paths remain supported. Generic directory moves require an existing source and disjoint destination with resolved parents; symlink aliases are rejected.

Project renderers are conservatively rejected when managed cleanup trees contain recognized source-like documents or linked entries; this is not exact renderer input discovery and can reject generated Markdown. Individual outputs must use portable leaf filenames and may not replace framework configuration/state. Concrete cache/output/asset paths are checked before VERSION or ignore writes. Literal project roots are escaped for explicit include/exclude globs so brackets in a root cannot hide selected inputs from safety checks.

These checks do not establish atomic promotion, full rollback, protection against concurrent filesystem replacement, or undo arbitrary external script effects.

Build environment context

Builds resolve one environment snapshot and pass it to their child commands and configuration-profile selection. Environment files do not mutate the parent process on this path. Inherited OS values win over local, earlier environment profiles and base assignments; explicit build profiles override inherited PROJR_PROFILE. The same values reach dependency probes, scripts/hooks/renderers and existing Git helpers. Direct public legacy EnvGuard APIs and CLI startup guards still mutate process state and are not concurrent environment APIs. This change does not approve credential injection policy or establish a sanitized/sandboxed environment.

Captured execution root and bounded individual render layouts

Script and hook subprocesses inherit invocation cwd by default, retaining explicit selected input paths. Quarto and individual R Markdown retain native execution directory settings. Explicit --execution-dir project passes the captured root via supported renderer controls. Input/mode/root remain data arguments to fixed R code. This does not imply direct R/IDE parity or a changed resource URL policy. The existing R package remains untouched.

Nested Quarto project metadata is rejected for selected documents and conservatively scanned implicit source trees. Individual rendering models one document-local format: HTML, PDF, Word, or supported native presentation/EPUB variants. Unknown/multiple formats, inherited individual metadata, custom R Markdown output filenames, dynamic R Markdown runtime and document-rendering hooks fail before controlled writes. Project-render validation remains conservative fresh-tree validation, not a complete renderer output manifest. Unsupported layout rejection does not assert renderer parity.

clear_output accepts only pre, post, or never; directory ignore accepts all, git, rbuild (case-insensitive), or an empty list. Invalid values fail before analysis, ignore synchronization or cleanup, including direct cleanup APIs.

Bounded CAS integrity

Ingestion requires an existing directory, disjoint from its CAS storage and project index. Reject linked/unsupported source entries, non-UTF-8 filenames and ambiguous logical paths; logical identities use slash-separated components and case-sensitive names. Digests are canonical 64-character lowercase hexadecimal BLAKE3 values. Copy and hash the same stream; verify existing objects before reuse. Publish complete objects/manifests without replacing conflicting content. Replace project index bytes through a same-directory temporary file, escaping CSV metadata fields.

Manifest inspection validates structure and manifest byte identity; file inspection also hashes referenced object bytes. This does not provide a stable snapshot across concurrent source changes, multi-writer serialization, power-loss durability or one transaction across remote manifest and project index. Failure may leave valid orphan objects or an unindexed complete manifest; errors propagate and old index bytes stay intact. No source file is modified by ingestion. Symlink-alias paths remain unsupported under the conservative path guards; callers should supply resolved physical paths.

Explicit Git operations

Git commits, pushes and network/upstream checks default off even when Git metadata exists. Only the resolved configured actions execute. Commit-enabled builds require clean initial Git state to avoid sweeping in unrelated edits; no-op commits succeed. Push captures the current branch’s configured upstream remote/reference before build writes. Missing upstream and unmodeled custom push-only routing fail early. Native authentication is the default. An explicit token-helper opt-in uses fixed host-scoped code and ephemeral environment data, never secret argv/source or persistent credentials. Local build success remains distinct from publication failure.

Bounded preview managed-state recovery

Preview captures managed root files/config/VERSION, selected inputs, declared output/docs trees, configured local publication stores and ordinary VCS metadata. Restore exact captured bytes/presence on both success and failure; restoration failure makes preview fail and reports retained recovery data when available. Declared cache is disposable and excluded from recovery; preview/cache artifacts remain there. No Git/publication operations execute in preview.

Recovery uses private temporary storage outside project cache. Unsafe linked or overlapping recovery paths fail before analysis; file-based/worktree VCS pointers are unsupported for this bounded metadata guarantee. This does not redirect arbitrary script writes, protect undeclared/external effects, prevent concurrent reads of temporary modifications, or provide sandbox/crash/concurrent-writer atomicity. New unmanaged files are not a whole-project snapshot. Automatic preview output isolation remains separate from post-run captured-state preservation.

Preview binary delivery

Release/install plumbing must verify version-bound platform assets/checksums before replacement and use locked remote tests/builds. The pipeline creates a draft prerelease only; publication and user-local WSL binary installation follow explicit artifact verification. See delivery boundaries. No local source compilation or production-readiness claim follows from installer CI.

Versioned machine boundary

Opt-in --machine emits protocol-v1 results/errors on stdout, with capability version negotiation independent of project discovery. Static error codes avoid reflecting credentials/config/argv. Queries return typed values; other existing commands reuse the CLI through a noninteractive worker whose logs use stderr. See machine interface for supported shapes and limits. This is a transport boundary over existing anyhow errors, not a second domain-error overhaul.

Captured run inputs (first path-contract slice)

One effective profile list is selected before config/environment reads: CLI, nonempty PROJR_PROFILE, nonempty QUARTO_PROFILE fallback, then base/local build.profile default. Earlier profiles still win; local config is highest. A profile’s own build.profile does not redirect an already selected run. Native QUARTO_PROFILE rendering settings remain distinct; no R helper bridge follows. The private per-run PROJ_RUN_CONTEXT snapshot carries only root, effective profiles, validated final directory mappings, active version and mode. Child path/version queries consume it after cwd/YAML/VERSION changes; explicit other-project selection discards it. Missing/invalid context fails clearly rather than rediscovering a root.

Preview retains an existing dev version, or uses dev1 from a release, without changing VERSION. Production uses the requested incremented release version from before hooks through rendering; success leaves dev1 of that release for subsequent development, and failure restores original bytes. Cache keys use v1.2.3-4 spelling; legacy version text APIs/files retain their accepted dotted representation. Final directory lookup remains unchanged in this slice; safe logical routing, render-context representation and native execution/embedding are subsequent work. Old-version renderer staging remains a known gap until the routing slice.

Explicit logical resource lookup

Safe output/data/docs-class lookup uses the selected eligible cache-class mapping, the captured active version and exact configured label. Final lookup preserves the physical mapping, including external paths. The later R-package data section defines the bounded output-r-data built-in; other generated labels must be declared. Directory insertion order is retained through configuration merging and the child snapshot. File fragments are relative and cannot replace/escape the role root. Queries never create directories. The CLI now defaults to safe lookup, integrated with captured-version consumers. Preview safe artifacts remain inspectable in cache and are not promoted.

Confirmed safe-cache selection

Within directories, one cache-class mapping with boolean safe: true selects the safe cache. Otherwise an eligible exact cache label wins, then the first eligible cache-class mapping in merged declaration order. safe: false excludes a candidate. Overrides retain existing key positions. Multiple explicit selections, non-boolean flags, flags on non-cache roles, or all declared caches excluded are validation errors before build mutations. A genuinely cache-free operation remains valid without any cache mapping. The effective selected label is frozen with the run context; children do not recompute it from subsequently changed YAML.

Legacy R data is package-generated output, not a generic input role. Its replacement/legacy normalization belongs to the separate output-r-data slice; this cache-selection change does not silently rename existing mappings.

Explicit path representation

Auto/absolute/relative are independent of safe/final target and execution cwd. Known managed renderer children receive an explicit bounded descriptor; no suffix or cwd-marker heuristics. Ordinary auto is caller-relative at query time; renderer auto is absolute. Relative bases are caller/project/known document/absolute custom directory. Explicit relative is strict across roots/drives; auto may fall back to absolute. Project renders without a single document reject document-relative base. The CLI now defaults to auto/safe. Merged settings may change representation, and explicit query flags override those defaults. Existing R helper/direct IDE parity remains unimplemented and outside Rust M1.

Native execution policy (supersedes earlier unconditional root-cwd wording): build and build-dev use merged settings.execution-directory, falling back to native; explicit --execution-dir overrides the configured policy. Plain scripts/hooks inherit the invocation cwd, not each source file’s parent; R source() normally inherits its caller cwd. Individual Rmd rendering leaves knit_root_dir unset and Quarto receives no execution-dir override, preserving native document/project settings. --execution-dir project explicitly requests captured-root execution for scripts/hooks, Quarto and individual Rmd. Project render drivers run from the selected project root to select the project, independently of chunk cwd. Project-wide Bookdown root override is currently rejected early because its render_site entrypoint does not expose the individual knit-root argument. Captured project/profile/version and logical path identity do not change with execution cwd. No existing R helper bridge or literal Markdown resource rewriting is implied.

Output lifecycle and runtime settings

This source slice wires output consumers to the captured active version and selected eligible cache; CLI lookup defaults are now safe/auto. settings is runtime policy, build selects actions, and parameters remain analytical data. settings.output-clear-stage is none (default), pre or post. Explicit --output-clear-stage wins over merged settings, then legacy build.clear_output YAML, then PROJR_CLEAR_OUTPUT, then none. Legacy environment/build never means none. Canonical settings uses none only; invalid values, explicit null and unsupported settings fail in their source layer. This deliberately changes R’s production fallback pre; R has no settings section.

After read-only validation/recovery setup, start hooks run first. Other preparation (ignore metadata, renderer staging and fresh native artifact isolation) follows. Pre-clear is immediately before analysis; post-clear is immediately after successful analysis, before restoration/staging/promotion/hooks. These clear configured final output/data roots, never the versioned cache and never preview final destinations. Output actions disabled by output_run:false also skip final-output clearing. An empty analysis selection remains upload-only and skips analysis-related clearing. Docs finalization is a separate fresh-document operation, not ordinary output clearing.

Fresh renderer artifacts are copied to selected-cache/projr/v/docs in previews and releases. Individual render source location is preserved for native resource semantics. Versioned cache files remain inspectable; failed renderer scratch is retained there too. Generic safe output trees are copied to configured final destinations only on release, respecting final-output clearing policy. Unrelated existing final files remain under none. No cache is synthesized. Unused cache-free script operations remain valid; a safe path query without eligible cache fails. Automatic old-cache removal is rejected for production until it has a bounded policy.

Local finalization completes before end hooks, which immediately precede the next development-version bump. With configured irreversible storage/Git publication, record the successful local release version first, then publish, then end hooks and next-dev bump. Publication/end-hook failure after this boundary preserves the local release and reports partial finalization; remote actions cannot be rolled back. Without publication, end-hook failure remains inside managed recovery. Preview never publishes or bumps VERSION. Arbitrary script effects/concurrent writers/power loss are outside the managed recovery guarantee; this is no sandbox or M2 provenance.

PR159 review amendments freeze selected renderer paths and prepared project metadata, revalidate immediately before each renderer, isolate its native artifacts at that boundary, and collect only the frozen outputs. Controlled VERSION, ignore and renderer-metadata writes share immediate path revalidation; promotion rejects links and special files. Notebook invocation retains native rmarkdown intermediate naming. An exact per-worktree Git record permits only the framework-created unstaged next-development VERSION change at the same committed HEAD; other dirty state still fails. Added remote regressions and real notebook acceptance await the amended-head CI and independent re-review. These checks do not establish concurrent-writer or power-loss atomicity.

Bounded HTML embedding fallback

Individual Quarto HTML/revealjs and R Markdown html_document/html_notebook rendering defaults to resource embedding only when the document leaves the effective option unspecified. Explicit false remains respected; embed-sources is a separate option. External metadata for individual rendering remains unsupported under the existing layout restrictions.

Quarto project preparation uses native quarto inspect results for each effective document format. Only an HTML/revealjs format with neither embed-resources nor legacy self-contained specified receives a temporary document-header default. Quarto owns profile, included-metadata, directory and document precedence. Both spellings of explicit false remain untouched, including mixed documents. Original source and project bytes are restored exactly on success/failure, before promotion. Prepared-source changes or a changed native input set fail at the launch boundary; automatic project fallback requires modeled text documents. Other input types need explicit renderer embedding settings. No literal Markdown/LaTeX resource rewriting or R helper/IDE parity follows. Nonembedded portability remains deferred.

The native Bookdown render_site driver is unchanged and has no new embedding fallback in this bounded slice; combined M1 acceptance must record that limitation. Remote exact-head evidence and independent review are required before shipment.

R-package data lookup and explicit activation

This supersedes earlier blanket requirements for declared data-class labels: output-r-data is the canonical built-in R-package data lookup, with fixed final target project/data even without YAML. Safe lookup derives /projr//output-r-data and requires an eligible declared cache and valid version. Lookup never creates or activates this role.

Only an explicit directories.output-r-data: {} declaration or normalized legacy data declaration activates managed cleanup, recovery, promotion and explicitly configured publication. Use ordinary output rules: none preserves other final files, pre/post clears at the configured lifecycle stage, preview never promotes, and supported failure restores final bytes. No special preservation policy applies. Ordinary ignore rules apply; explicit ignore: [] includes data in Git/R builds.

Normalize legacy _projr.yml and active _projr-*.yml aliases before profile/local merging; reject same-layer conflicts and any redirection in each original layer. Normalize legacy remote content labels too. Canonical _proj.yml rejects data; generic data-* labels are unsupported (use raw-* inputs or output-* outputs). Existing R helpers/packages remain untouched. Python/Julia outputs use ordinary mappings; inst is a project-relative fragment, not a special role.

Embedding preparation preserves the complete native effective format list/order, including an inherited non-HTML default. Only eligible HTML options change. Prepared sources use guarded same-directory replacement with original permissions, so hard-linked external aliases retain their original bytes. Inherited renderer profile/directory/included metadata is captured and rechecked at launch; changes are rejected rather than silently masked by a prepared default. Internal captured metadata is recovered; external metadata is observed only and is never rewritten. Literal metadata-files paths are required for this bounded dependency capture.

Failed document artifacts across a smaller retry

The existing managed-renderer contract must hold across successive builds: failed HTML/PDF artifacts cannot enter a later successful Git commit after selecting fewer documents. Restore prior final/native bytes on failure; preserve unselected native documents and retained failed cache scratch across the retry. Successful document finalization still replaces the configured final docs tree with its new selection. No new attempt identity, sealing, cache namespace or storage policy is introduced. The remote mixed_render_retry.py acceptance exercises this sequence with real renderers and actual committed bytes; M2 record design remains open.

Confirmed storage and catalogue direction

Ordinary proj use must remain standalone with a native backend and no DVC dependency. Future per-directory DVC backing is opt-in, with automatic delegation at agreed lifecycle points and DVC authoritative for its own tracking/cache. The intended release catalogue is a curated linear main-branch changelog. Storage design constraints separate these decisions from the still-open configuration, identity, sealing, manifest and backend contracts. This records design only; current runtime behavior is unchanged.

Real local Git publication acceptance

Real temporary Git repositories and a bare upstream now exercise the existing optional-publication contract: configured non-main/differently named upstream, explicitly disabled push, no-op provider commits, non-fast-forward rejection and an analysis-failure comparison. Check actual branch refs, committed/final/cache bytes and release/development versions. This adds acceptance evidence; current branch and publication order stay unchanged. Durable publication records, sealing and the future release catalogue are not implemented by these tests.

Inventory transition groundwork

Existing explicit CAS ingestion has a fixture for exact current path/hash sets and stored bytes across edits, additions, renames and deletions. The edit keeps file length and modified time unchanged, so verified content must still change. Past manifest bytes and their referenced objects remain valid across later ingestions in this sequence. These are full snapshots in the existing format, not newly defined rename events, tombstones, build records or retention rules. No lifecycle capture point or broader provenance completion is implied.

Temporary compatible CSV recording

User-approved projr-style manifest.csv is independent of CAS. Preserve the four-column inventory and production pre/post/history semantics; keep the codec replaceable. This does not decide attempt identity, sealing, retention, remote-only discovery or Git policy. The local candidate and bounded deviations are in storage design. CAS is an additional remote structure alongside latest and ordinary archive, with content-addressed versioned snapshots. Provider/store/restore compatibility remains distinct from CSV implementation.

Cooperative build ownership

Each build and preview takes an exclusive project-local claim at .proj/build.lock before capturing mutable build inputs. The claim contains only a fresh opaque attempt ID: no hostname, username, credentials or process arguments. A competing build fails before hooks, version changes or managed output writes. Read-only path/configuration queries do not acquire a claim.

The claim is released after ordinary success, failure and recovery. An existing claim is never stolen. A terminated process or machine failure can leave one: first confirm no build owns the project, then remove only the stale claim and retry. This is cooperative build exclusion, not a filesystem sandbox or a promise of crash recovery. Arbitrary scripts and other tools can still change files.

Managed caches, output/document destinations and ordinary publication targets cannot replace .proj. Optional Git integration excludes only reserved live .proj/build.lock paths at every repository depth from clean-state checks and staging, preserving the existing whole-repository staging scope. A tracked claim is rejected. This does not exclude .proj/log. The approved final Git receipt sequence is described below.

Ownership alone does not implement durable JSON logs or final Git receipts; the following development-source sections describe those additional slices. End-hook mutation enforcement remains deferred; existing hook ordering and failure recovery are unchanged.

Development source: publication-attempt evidence

Production builds with enabled ordinary/CAS publication or optional Git retain one JSON snapshot per attempt under .proj/log. The snapshot records the opaque attempt ID, UTC times, selected profiles, logical version transition, local-release completion and provider operation outcomes. It is a companion to the existing four-column CSV; it does not replace CSV or choose a new archive/CAS identity.

The framework records that distribution may have started before entering a provider or Git operation. A returned failure may have partial effects, including an uncertain push; it never means the remote remained unchanged. Once this boundary is reached, framework error handling retains the earlier evidence. A crash with only a pending snapshot remains unresolved, without automatic retry.

With Git enabled, the normal build commit includes the pre-Git snapshot. Final Git/end-hook/next-dev results go to a separate local outcome receipt, included in the next ordinary commit. There is no recursive log-only commit. Only an exact pending receipt, its unchanged snapshot in HEAD and its local ownership witness qualify for the narrowly scoped clean-worktree exception. Other dirty files, edited receipts and unowned version changes remain errors. Explicit user Git ignore rules still apply; managed ignore generation does not exclude these logs.

Normal standalone publication requires neither Git nor a cloud account. Records omit raw configuration, environment, URLs, credentials, command arguments and subprocess output. IDs are random rather than host/user names. Worktree-local Git witnesses contain opaque control hashes and never enter Git history.

Publication-enabled records start at the successful local-release boundary. Successful plain production builds also retain completed records as described below; previews and earlier failed builds still have no durable attempt record. Complete source/runner/dependency provenance, earlier stage records and cleanup/retention policy remain M2 follow-up work. End-hook mutation enforcement stays deferred; these records do not authenticate arbitrary scripts or provide a filesystem sandbox. The installed preview.3 is unchanged.

Development source: plain production records and inventory witnesses

Successful production builds now retain a completed .proj/log record even with Git and all publication disabled. It is installed only after end hooks and the next-dev transition succeed. Pre-distribution failures and previews still do not gain durable records; their retention policy remains undecided.

Attempt JSON references current inventory evidence from the existing manifest.csv: selected input rows captured before analysis, release-output rows after promotion, and an observation of outputs after finalization is attempted. Each fingerprint includes the release version, labels, row/file counts and BLAKE3 of the existing codec’s canonical CSV rows. File hashes remain MD5. These control fingerprints include paths, version and empty-directory markers; they are not a new content-only tree identity, authentication or a replacement manifest.

Detailed pre-analysis/release rows remain in the ordinary historical CSV. The JSON does not duplicate that potentially large table. End hooks may change files: the final observation can differ from the release inventory without enforcement. With Git enabled the immutable snapshot retains the release inventory; the later receipt holds the final observation. No rewrite of previously published data or CSV history follows. Final observation failure is distinct from an empty inventory and preserves earlier evidence and the original operation error where present.

Development source: bounded startup provenance

Production attempt records now include a startup observation captured after preflight and before start hooks:

  • Selected script/hook file names, observed byte lengths and BLAKE3 fingerprints. Names are relative to the physical project root; external, overlong or URL-like names are replaced with opaque ordinal names and explicitly marked redacted.
  • A Git revision when Git integration is enabled, with a state saying that its preflight gate was accepted. With Git disabled, Git is not queried and the revision is unknown. Neither state proves an unchanged execution tree.
  • A safe configuration projection of validated execution/path/clear flags, Git and output toggles, directory counts and whether a safe cache was selected. It deliberately excludes paths, arbitrary parameters, environment, credentials and remote definitions. Its fingerprint covers only this projection.
  • Numeric Python/Rscript/Quarto versions recognised from existing preflight responses. No extra runner probe is launched; raw vendor output is not retained.
  • Fingerprints of fixed root dependency declarations: renv.lock, DESCRIPTION, pyproject.toml, requirements.txt, requirements-dev.txt, poetry.lock, uv.lock, Pipfile.lock, Project.toml, Manifest.toml, Cargo.lock, environment.yml and environment.yaml. These are declarations, not proof of installed packages.

File observation limits are 256 selected unique source entries, 8 MiB per file and a shared 64 MiB read budget, with at most one lookahead byte. Missing, unavailable, linked/special and over-limit declarations have explicit states; they do not make a previously supported build fail. Long source names are capped at 256 UTF-8 bytes before redaction. The 16 KiB runner-response cap controls what metadata is accepted; existing preflight subprocess output buffering is unchanged.

These are startup observations, not frozen source bytes: a start hook can change a later script or dependency declaration. Implicit renderer-project source sets, imported code, effective renderer configuration, arbitrary parameters and installed dependency state are not fully captured. Unknown states must not be presented as complete provenance. That startup slice alone did not include detailed final rows or generated human history; the following section adds them. CSV/MD5 and failure-retention behavior are unchanged, as is the installed preview.3.

Development source: effective analysis-configuration fingerprint

Startup evidence now includes a bounded, versioned BLAKE3 fingerprint over the alias-normalized merged framework analysis configuration: parameters, directory declarations, scripts and pre/both/post hook choices. Object keys are sorted; arrays and directory declaration order remain significant. The final digest also binds the existing effective runtime-policy fingerprint, including CLI overrides. It is an observation before start hooks, not frozen executed config. Missing versus explicit-empty script selection keeps its established meaning.

No raw keys, parameters, paths or URLs are copied into this metadata. Sensitive parameter-key subtrees and credential-bearing or uncertain URL-like strings are replaced by a typed redaction token before hashing. The record exposes omission counts and observed_redacted status. Ordinary credential-free analysis URLs, including nonsecret query choices, remain distinguishable. Recognition covers token/password/secret/credential/signature suffixes and explicit auth/pass/bearer/ key aliases, userinfo, encoded query/fragment keys and signed-cloud credentials. It cannot infer secrets hidden in innocent keys or arbitrary path segments. A digest is not encryption, authentication or universal secret detection.

Traversal is bounded to 4 MiB of canonical tokens, 100,000 processed values and depth 64 before serialization/hashing. Limits produce explicit limit status with no partial digest, without failing an otherwise supported build. Publication/provider/auth configuration, dev-only choices and unrelated metadata are outside this analysis fingerprint. Native renderer metadata and installed environment state are not a merged framework configuration snapshot.

The remote integrated M2 gate now computes real bytes, changes input and analysis parameters, inspects record/CSV/history, deliberately fails and checks exact last-good version/output/CSV preservation, then retries successfully. Git is blocked by a failing shim to prove standalone operation. An independent Rust witness checks source/declaration BLAKE3 and actual input/final CSV bytes. This does not select pre-distribution failed-log retention or claim M2 closure.

Development source: local diagnostics before distribution

It omits raw exception text, command arguments, configuration, URLs, credentials and host/user identity. The original command still returns its normal failure and detailed stderr; those details are not copied into retained history.

The directory contains its own narrowly scoped .gitignore. Framework Git status and staging also exclude this reserved directory at every repository depth and reject already tracked diagnostics. Successful records, distributed-failure records and Git receipts retain their agreed Git behaviour. A diagnostic write failure preserves the original build error and reports the evidence failure. No automatic pruning is introduced. Previews and failures before writer ownership is acquired do not create diagnostics.

History lists these attempts as failed/local_only, with a null release_version and their coarse stage. They are not successful releases and have no final file rows. Recovery remains available until the first provider/Git action is entered, including preparation, no-action end-hook, observation and evidence failures. Saved intent alone does not release recovery.
