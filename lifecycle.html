Build lifecycle

What happens before, during and after a run—and which parts are still being built.

WarningReleased workflow, bounded recovery

The core figures describe the reviewed lifecycle introduced in 0.4.0-preview.2 and retained in preview.3. The ordinary-publication overlay below is released in preview.3. The exact source and executed acceptance are linked below. This is a bounded managed-path workflow, not whole-project rollback or a security sandbox. Use sample data or a disposable project copy.

An output build means the production proj build path. A preview means proj build-dev. Clearing here means final-output clearing, not arbitrary deletion of project files or preparation of a fresh cache.

The three stages

The key adjacency rules are deliberate: nothing runs between pre-clear and analysis, or between successful analysis and post-clear. Start hooks come after verified basic setup; end hooks come at the end, immediately before the output build’s transition to the next development version.

1. Pre-build details

NoteOpen: resolution, validation, context and start hooks
  • Root selection, effective profiles, merged configuration and environment must agree before analysis starts. The target assigns HOW choices to settings and WHAT is selected/run to build; this is not permission to add unknown fields to the installed preview.
  • The captured context fixes resource identity and the active run version. In the released implementation, preview retains an existing dev version or uses dev1 of a release without writing VERSION; an output run uses its requested release version throughout the run and leaves the subsequent dev1 only on success.
  • Validate declared paths, script/hook include and exclusion syntax, supported renderer plans, dependencies and explicitly enabled Git actions before controlled build writes. Probes can have their own effects: this is not a blanket read-only/environment sanitization guarantee. The malformed-exclusion correction is included in preview.3; it fails in this preflight stage, without changing stage order or recovery scope. Fallback directory/entry errors also stop here. The recovery capture stage reports its own enumeration phase and OS cause before controlled project writes. These diagnostics are included in preview.3; ordering is unchanged.
  • Start/end refer to the existing pre/both and post/both hook sets, not new hook types. Their placement follows the controlled lifecycle shown here.
  • Recovery capture must precede hooks and managed mutations. Cache/staging setup, supported renderer preparation and permitted metadata/ignore work finish before the final pre-clear gate. No new metadata/provenance record is implied here.
  • A script’s working directory is separate from project identity. Native cwd with an explicit project override, safe resource targets and render-context path presentation are included in preview.2.

2. Build details

NoteOpen: exact clearing position and selected execution

Preview skips both final-output clear operations, even if an output setting asks for them. With scripts: [], hooks can still run and an output build may export existing artifacts; that is not proof of complete analysis-free retry identity.

The target routes eligible safe output/data roles and rendered docs through an explicitly selected versioned cache, keeping configured final destinations separate. Inputs retain their declared meaning; no undeclared docs or cache mapping is invented. Ordinary scripts can still write elsewhere: path helpers and staging are not automatic isolation of every write.

The selected execution order must follow the supported plan. Do not infer arbitrary mixed-renderer ordering or RStudio/Quarto R API parity from this figure.

3. Post-build details

NoteOpen: promotion, end hooks, version and optional publication

The end-hook/next-dev adjacency is approved. The released implementation places enabled CAS export and Git commit/push before end hooks and the next-dev bump. Before publication it records the successful local release and gives up the managed recovery snapshot. Publication or later end-hook failure preserves that local release and skips the bump; partial external effects are not undone. Without publication, end-hook failure still uses bounded managed recovery. Preview runs end hooks, then restores captured managed state without a version transition. These are bounded managed-path guarantees, not whole-project or remote atomicity.

Promotion is output-only and conditional on selected analysis and enabled promotion. Explicit empty analysis preserves existing upload inputs instead; configured publication may still use them. Metadata means existing project/version operations, not finished attempt/release identifiers or complete provenance. The implemented storage path is configured local CAS export; Git commit/push and network checks are opt-in, not consequences of merely having a Git repository.

An analysis failure does not enter the success-only post-clear/promotion/end-hook/version path. This page does not introduce an always/finally-hook policy.

Failure and recovery boundaries

The local recovery figure describes the bounded captured-state rule. The separate publication figure adds the released local-publication boundary; it is not a whole-project or remote rollback guarantee.

The captured managed set is not a whole-project or filesystem snapshot. Cache results are deliberately retained. Arbitrary external script effects, concurrent writers, crashes and partial storage/Git effects are outside a transactional rollback guarantee. A preview restores its captured managed state on success and failure; this does not make it a security sandbox.

Durable attempt/release records, complete input/code/config/dependency provenance and safe analysis-free publication retries remain unfinished. Do not automatically rerun analysis or claim publication was undone after an external failure.

This includes settings precedence, hook/clearing order, context/version capture, output promotion and publication/failure boundaries. Link actual event-order and recovery tests; do not turn a target marker into a released marker merely because a branch compiles.

Keep the three-stage overview small. Put new detail in the relevant folded stage instead of expanding one unreadable graph. Render the site, exercise diagram export and verify the page links remotely; do not require local Quarto/R/Docker builds.

Failure followed by a smaller build

The controlled order above is unchanged. Remote acceptance now couples the failure branch to a subsequent successful Git build: real HTML and PDF are rendered before a later document fails, previous final/native state is recovered, then a smaller selection is published and its committed bytes are checked. Retained failed scratch stays in cache; it must not enter the later commit. Earlier final docs are preserved on failure and replaced only on successful docs finalization. This is bounded recovery evidence, not a new M2 record or sealing boundary. This recovery behavior is included in preview.3.

The storage design constraints reserve optional future per-directory DVC delegation. Its restore/build/store integration points and error boundaries are still undecided; no DVC step is added to the current lifecycle diagrams. Ordinary native use remains independent of DVC.

The real local-bare-upstream Git tests also check the existing publication-failure branch: a rejected push keeps the successful local release and skips the next-dev bump, while an analysis failure restores managed state without a release commit. This verifies the current boundary without changing lifecycle order, adding a seal or deciding durable attempt/publication records.

Inventory transition tests exercise explicit CAS calls independently of this lifecycle. They do not add automatic pre-analysis input or final-output provenance capture, choose sealing points or complete the unfinished build-record work.

Source CSV inventory: additional capture points

CSV capture is released in preview.3. Released diagrams above retain their status. Production with output_run enabled adds these points without changing clear/analysis adjacency; preview skips CSV capture.

CSV replacement remains inside managed local recovery. Publication failure preserves local release CSV; no remote rollback is implied. Later end-hook changes are outside inventory, so these records are not sealing.

Configured remote restore is a separate explicit operation, not an automatic stage in the build lifecycle above. It selects a source, stages a complete download and then invokes guarded merge/clear installation.

Configured ordinary publication in preview.3

Preview.3 publishes ordinary local archive/latest targets, then the bounded GitHub latest/archive publication path, before selected CAS export, Git publication, end hooks and next-dev bump. Configuration/planned names are checked and GitHub routing is frozen before hooks. Each provider stages every selected CSV snapshot before its first remote mutation; GitHub preparation additionally checks the remote catalog and shared metadata. This is not a transaction across providers. Failure preserves the local release and skips later stages, without rolling back already published destinations. Preview skips publication. Released diagrams above retain their version meaning.

The ordinary-local publication stage also supports explicit none comparison: source filenames are uploaded blindly according to the documented strategy interaction, after all-target staging and before CAS/Git. This does not change the staged lifecycle diagram or the release-preserving failure boundary.

Ordinary-local latest publication can use the default manifest comparison. History eligibility is resolved from the already captured metadata and project CSV; the staged publication position and failure boundary remain unchanged.

The ordinary-local publication stage now finalises archive or latest targets. Archive comparison eligibility is frozen during all-target preparation; old versions remain untouched and new versions are complete snapshots. Publication ordering and the release-preserving failure branch are unchanged.

The ordinary-publication overlay now stages configured GitHub latest/archive ZIPs after ordinary local finalisation and before CAS/Git. Routing freezes before hooks; all GitHub ZIPs prepare before uploads, data before metadata. External failure retains the local release and skips bump; there is no transaction across providers.

Existing canonical GitHub data is downloaded and merged during preparation. Full uploads precede removal of obsolete empty variants and shared metadata. Replacement DELETE/POST failures report partial or uncertain state; they do not roll back remote assets or the successful local release.

No-inspection GitHub strategies select their merge/purge actions during that same preparation phase. Nonempty purge changes the prepared replacement ZIP; it does not add an early remote deletion phase or change the release-preserving boundary.

File/manifest eligibility and archive history selection are now part of GitHub preparation in the current-source overlay. Current and eligible historical ZIPs materialize privately, then the ordinary local planner computes staged effects; only those current data effects become ZIP uploads/removals. All GitHub targets still prepare before the first external write. Metadata-only no-ops and reuse do not manufacture data uploads; failure retains the local release.

The current-source GitHub stages also have a real synthetic Release witness: five builds and two restores verified latest replacement, archive reuse/change, exact shared metadata and preservation of older data. See the live verification. No lifecycle order changed for this evidence addition. Preview.3 packages this ordinary-publication overlay; the earlier core lifecycle diagrams retain their existing meaning.

A focused regression candidate checks the existing Git boundary: missing push tracking fails in preflight, while a real commit-hook rejection after successful analysis retains the local release without advancing HEAD/upstream or bumping next-dev. It does not change stage order, invent a seal or promise index rollback.
