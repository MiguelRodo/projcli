What happens during a build

A build runs the analysis steps you selected, prepares the final results, then saves or uploads them as configured. Start with a preview when checking your scripts. Use a disposable copy before trying production settings on important work.

The stage-by-stage diagram shows the detailed order. This guide summarizes the supported workflow in preview.5. It does not promise that arbitrary scripts can be undone or that every original projr feature is supported.

Check the project and tools

projcli first selects the project folder and reads its configuration, including active profiles and local overrides. It checks the selected scripts, hooks, folder paths, storage destinations and required tools. An explicit scripts: [] means no analysis scripts; it does not trigger automatic discovery instead.

Each child command keeps the selected project identity, even if a script changes its working folder. The parent R console or terminal environment is not rewritten. Project identity and the folder where a script executes are separate choices.

These checks are not necessarily offline: Git checks can contact a remote, and optional package setup can require separate consent. A check is not a security sandbox. Reading configuration and looking up paths do not create directories or edit ignore files.

Prepare and run the analysis

Before changing managed files, projcli saves recovery copies outside the project’s disposable cache. The recorded set includes VERSION, managed configuration and ignore files, recorded inputs and final output/document folders. Declared output folders may be outside the project. Linked managed trees are rejected. If the recovery copy cannot be made, the controlled changes do not start.

The production build then performs the selected local steps: cleanup, hooks, analysis, document rendering and copying successful results to final folders. Optional build.r actions can snapshot renv, generate documentation and render README.Rmd. They are off by default; see R build tasks and the detailed lifecycle for their ordering. Temporary renderer configuration is restored, including comments and settings that were originally absent. VERSION is written after the local stages succeed. There is no pre-build Git commit.

If a local step fails, projcli attempts to restore the recorded files and folders, including removing recorded paths that did not previously exist. If recovery also fails, it reports both errors and retains the backup location. This cannot undo arbitrary writes outside the recorded set, other programs’ changes or a power failure. Always keep an independent backup.

Save results after local success

After the local work succeeds, projcli saves the selected folders to the locations chosen by build.dest. It uses the actual prepared files before any requested post-build output cleanup. Git integration can then make the configured build commit and push to the current branch’s upstream. It uses installed Git and your existing authentication; custom push-only routing is not supported.

If an upload, push or later cleanup fails, the analysis may already have succeeded and some files may already have been uploaded. The command reports failure while retaining the successful local release and version. It does not claim to undo completed external changes. Check the error and build records before retrying. A dedicated analysis-free publication retry command remains future work.

Successful builds and failures with distribution activity retain useful Git-eligible records when Git integration is enabled. Earlier failures retain local diagnostics excluded from Git. The pre-Git record is prepared for the normal build commit. After Git is attempted, its final outcome is saved locally for the next normal commit, even if that attempt failed. No extra bookkeeping commit is made. See the history reference for exact files and limits.

What a preview changes

proj build-dev

A preview runs the selected analysis and hooks, but skips production version changes, cleanup, Git commits and uploads. It restores recorded managed files after success or failure while leaving preview results in the cache. Your own scripts and hooks can still write elsewhere; preview is not an operating-system sandbox and does not automatically redirect every output.

By default, plain scripts and hooks use the folder from which you invoked the command. Individual R Markdown and Quarto documents keep their native working-folder rules. --execution-dir project explicitly requests project-folder execution. Bookdown project-wide root overrides are rejected because that renderer entry point cannot apply the same control. Selecting a project does not rewrite literal Markdown links or guarantee identical results from an IDE’s Render/Knit button.

Plain R analysis scripts use separate child sessions by default; config.r.session: shared selects one shared child for those scripts. This is separate from your live R console and does not combine hooks or document renderers into that session. The original projr package remains unchanged. See the build reference, R guide and compatibility record for the supported subset and remaining gaps.
