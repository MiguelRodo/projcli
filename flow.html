Proj Build Execution Flow

This page records the existing proj build / proj build-dev implementation. It is not a normative behavior specification. The behavior contract records confirmed decisions and known gaps; current defects do not override it. The build pipeline is designed to enforce structural integrity, version control, and reproducible execution environments. The process is strictly divided into three sequential stages: Pre-Build, Actual Build, and Post-Build.

1. Pre-Build Stage

The pre-build stage focuses on validation, environment auditing, and preparing the workspace state prior to executing any project code.

1.1 Config Audit

The _proj.yml configuration is parsed and validated based on the execution mode (development vs. production). The configuration audit also strictly evaluates arbitrary nested keys inside the parameters block and throws a validation error if multiple aliases (parameter, params, param) are found to prevent mapping conflicts.

1.2 Git Capability Audit

If the configuration mandates version control integration (git.commit is true): - The system resolves the GitProvider based on the configured engine (config.git.engine defaults to auto or system) and verifies that Git is installed and available on the system PATH. If remote operations like fetching or pushing are necessary and config.git.use_proj_cred_helper is enabled, the credential discovery engine attempts to resolve GitHub tokens. - A check is performed to ensure the Git profile (author identity) is properly configured for the workspace.

1.3 Target Resolution and Dependency Preflight

The engine resolves scripts and hooks and detects Quarto/Bookdown configuration before version initialization, cleanup, hooks or snapshots. Preflight then checks the production Git restrictions and the interpreters required by those targets.

  • Production Git checks inspect branch restrictions, tracking remotes and upstream state when configured.
  • Rscript and required rendering namespaces are checked when needed. The current implementation can offer or perform R package installation; this is existing behavior, not a statement of the future dependency policy.
  • Quarto availability is checked when needed.
  • The Python executable is resolved when Python targets are present.

1.4 Version Input

The current version is read from VERSION, with DESCRIPTION and a default version as fallbacks. Development previews do not persist a missing VERSION.

1.5 Production Workspace Clearing

Production builds clear pre-build caches and output directories according to clear_output (pre, post, or never) and may purge old cache versions. Development previews skip these CLI-managed cleanup stages.

1.6 Production Version Bump

Production builds apply --major, --minor or --patch, reset the development flag and write VERSION. Development previews do not bump or write VERSION.

1.7 Pre-Build Hooks

Configured pre and both hooks run after the preceding preparation, before the Git pre-snapshot. Failures propagate from these hooks.

1.8 Git Pre-Snapshot

When production Git commits are enabled, the engine commits the pre-build workspace with the “Snapshot pre-build” message.

2. Actual Build Stage

The actual build stage handles the isolation, resolution, and execution of scripts and documents. This entire stage is executed within a catch_unwind block to safely trap panics and allow for graceful recovery.

2.1 Workspace Evaluation

The system inspects the workspace for the presence of _quarto.yml and _bookdown.yml. - Mutual Exclusion Check: The presence of both configuration files simultaneously results in a fatal validation error if the build.scripts configuration is omitted or includes documentation targets (.qmd or .Rmd).

2.2 Script Resolution Strategies

The engine determines which scripts to execute based on two possible paths:

Path A: Explicit Configuration (build.scripts / dev.scripts)

During development builds (BuildMode::Dev), the dev.scripts configuration array overrides the standard build.scripts. Explicitly providing an empty array ([]) for dev.scripts causes a strict error to prevent silently running an empty development build.

If target scripts are defined in _proj.yml: - Glob patterns are resolved to absolute paths. - Exclusion patterns (prefixed with !) filter the matched lists. - Empty lists explicitly short-circuit the execution process (The Explicit Empty Exception). - Documentation files (.qmd, .Rmd) are segregated from standalone scripts (.R, .py). - Dynamic Configuration Updates: If documentation targets are specified, the respective project files (_quarto.yml or _bookdown.yml) are dynamically updated to only render the explicitly requested targets.

Path B: Fallback Automated Auto-Discovery

If no explicit scripts are defined: - The system determines if it should trigger an automated Quarto or Bookdown site render based on the presence of their configuration files. - If neither exists, a shallow directory sweep is performed, executing discovered files strictly in the order of: .qmd, .Rmd, .R, .py.

2.3 Execution and Reordering Constraint

The existing implementation starts interpreter subprocesses (for example, Rscript, python, quarto) with current_dir set to the target script’s parent directory. This is a known gap against the confirmed root-relative execution default, not a compatibility requirement. Renderer evaluation directories need their own supported controls. A subprocess does not provide a filesystem sandbox or guarantee a clean environment.

When Quarto or Bookdown configurations are active alongside explicit scripts, a strict reordering constraint is applied: 1. Pre-scripts: All .R or .py files listed before the first documentation file are executed. 2. Doc Clusters: The documentation project render engine (quarto render or rmarkdown::render_site) is triggered. 3. Post-scripts: All .R or .py files listed after the first documentation file are executed.

Otherwise, scripts are executed sequentially exactly as resolved.

3. Post-Build Stage

The post-build stage acts on the final status of the actual build stage, finalizing version control, syncing remotes, or safely rolling back the workspace.

3.1 On Build Success (Initial Commit)

If the entire build pipeline executes without error and Git integration is enabled (git.commit is true): - A final commit is generated capturing all build artifacts and modifications. - The commit message is formatted as Build v<VERSION> or includes an optional user-provided description (Build v<VERSION>: <DESCRIPTION>).

3.2 Post-Build Workspace Clearing

For production builds configured with clear_output: post, the engine cleans up post-build deployment folders. Additionally, temporary document rendering artifacts (docs/) are automatically cleaned up on successful completion of a single document rendering engine.

3.3 Post-Build Automation Hooks

After the actual build stage completes successfully and the final Git commit is generated, any configured post or both automation hooks (either build.hooks or overriding dev.hooks) are executed in isolated subprocesses.

3.4 Remote Export Pipeline

For production builds with targets in build.dest and remotes.local configured: - The system iterates over the defined build.dest targets. - Resolved content directories mapped to these targets are piped to the Content-Addressable Storage (CAS) engine. - The CAS engine handles deduplicated storage synchronization, exporting project files into the remote vault.

3.5 Remote Sync and Push

If Git integration is enabled (git.commit is true) and pushing is configured (git.push is true): - The GitProvider commits the automated workspace build update (capturing compiled asset tracking or CAS mutations). - The GitProvider pushes the local branch mutations to the remote host. - If remote authentication is required and the credential helper is enabled (config.git.use_proj_cred_helper), the CLI securely injects the discovered GitHub token.

3.6 On Build Failure or Panic

If the build pipeline returns an error or panics mid-execution: - Production Rollback: If the build was a production run (--major, --minor, or --patch), the version modifications performed in the Pre-Build stage are reversed. The system restores the pre-build version configuration and ensures the development flag (dev) is set to 1 to maintain safety. - The underlying error is propagated to the CLI output, terminating the process with a non-zero exit code.
