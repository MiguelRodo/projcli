Configuration _proj.yml

The _proj.yml file dictates the structural map of your project. It configures the foundational paths and mapping logic used by the CLI.

Schema Rules and Foundational Prefixes

Custom directory labels are strictly validated against a set of foundational prefixes: - cache - raw - output - docs

These prefixes are case-insensitive. Any label defined in the configuration must begin with one of these approved identifiers.

Explicit paths and local initialization

Ordinary declared directories need a nonempty path. The fixed R-package role output-r-data: {} is the exception: its final destination is project/data. Runtime does not insert other missing cache/raw/output/docs mappings or synthesize subpaths for undeclared labels. Canonical data/data-* labels are rejected; see the R-package data section for the legacy per-layer data alias. For example, declaring raw-data: {path: _raw_data} makes raw-data available; it does not create an undeclared raw or raw-data-extra resource. ASCII case is ignored and case-only duplicate labels are rejected.

proj --project . --non-interactive init directories creates a missing _proj.yml once with explicit raw-data: _raw_data, cache: _tmp, and output: _output paths. It preserves existing base/profile files, creates only declared resource directories, and does not invoke Git/GitHub or add an R code directory. The preset omits build.scripts, preserving shallow discovery; it never serializes an accidental empty analysis list. To render documents, declare a docs mapping too.

Production state and project-render staging require a declared cache directory. Framework version/staging children are derived inside that declared cache; this is distinct from inventing undeclared resource labels. Storage content labels must be declared and relative storage paths use the captured project root.

Selecting the safe cache

Each cache-class directory may include boolean safe. One explicit safe: true selects that cache; otherwise an eligible exact cache label wins, then the first eligible cache in merged declaration order. safe: false excludes a candidate. Profile/local overrides retain existing declaration positions. For example:

directories:
  cache:
    path: _tmp
  cache-analysis:
    path: _analysis_cache
    safe: true

This selects _analysis_cache for explicit safe logical output lookup. Multiple true selections, non-boolean values (including null), selection flags on non-cache roles, and all declared cache candidates excluded are validation errors. Each layer’s explicit values are checked before merging; null cannot inherit a previous boolean. Cache-free queries and operations that do not consume a cache remain valid. The chosen safe cache is frozen in child run context. Cleanup, safe lookup and renderer staging consume that same selected mapping; no literal cache label is required when another eligible cache is selected.

Strict Validation Error Behaviors

The system performs strict validation on _proj.yml: - If a defined directory label uses an unsupported prefix layout, a validation error string will be returned and execution will fail. - All references must resolve correctly; otherwise, the CLI will output an error detailing the structurally invalid labels or malformed content.

Top-Level Configuration

The _proj.yml file supports a top-level config block for project-wide settings:

  • config.git.engine: The Git execution engine to use. Can be auto (default) or system. This determines how the CLI interfaces with Git capabilities natively.
  • config.git.use_proj_cred_helper: Defaults to false: use existing native Git authentication. Explicit true permits an existing single-line GITHUB_PAT, GH_TOKEN or GITHUB_TOKEN for standard HTTPS github.com remotes through a temporary host-scoped helper. There is no automatic token discovery or GitHub CLI call during builds. Tokens are environment data, never argv or shell source; persistent auth settings are unchanged.

Parameters Configuration

The _proj.yml file supports a top-level parameters block for arbitrary nested parameter evaluation. This allows you to define custom metadata and deeply queried values throughout your execution environment.

The configuration engine also supports several aliases for this block: parameter, params, and param. However, multiple alias conflicts within the same configuration file are structurally rejected during validation to prevent mapping confusion.

Remotes Configuration

The _proj.yml file supports a top-level remotes block, which currently supports a local mapping of standalone storage vaults.

  • local: A mapping where keys represent remote titles and values configure the vault:
    • path: The physical absolute or relative path to the remote storage directory.
    • structure: Specifies the storage structure algorithm. Must be cas (Content-Addressable Storage).
    • content: An array of string tags (matching foundational prefixes or defined directories) specifying which project output directories to sync into the remote upon build completion.
    • inspect: manifest validates JSON, logical paths/digests and manifest filename/content identity; file additionally hashes every referenced object and compares actual bytes. Manifest-only inspection does not verify object bytes.

Build Configuration

The _proj.yml file can also contain a build block to configure the behavior of the proj build and proj build-dev execution engine. The build block supports the following sub-keys:

  • dest: An optional list of remote target strings. These targets must be mapped to explicit configurations within the remotes.local block. During post-build execution, resolved content directories matching these tags are piped to the CAS engine for deduplicated storage synchronization.
  • scripts: An optional list of explicit script paths or glob patterns to execute during the build pipeline.
    • Globbing patterns are supported.
    • Prefix a pattern with ! to exclude matching files from execution.
    • Current source rejects malformed inclusion or exclusion syntax before execution, including hook patterns. The exclusion correction is newer than preview.2; see the build reference.
    • When provided, this selects scripts instead of automatic discovery. Document targets may be grouped for rendering, so mixed script and document targets are not guaranteed to run in the exact listed order.
  • hooks: An optional map of lifecycle hook scripts to execute.
    • pre: Scripts executed before the actual build phase.
    • post: Scripts executed after analysis/promotion, before VERSION and publication.
    • both: Scripts executed during both pre and post phases.
  • profile: An optional environment profile identifier. When set, the system injects the PROJR_PROFILE environment variable into the isolated subprocess for all executed scripts and project rendering commands. This can be overridden at runtime via the --profile CLI flag.
  • git: An optional Git integration configuration. This can be a boolean toggle or an object mapping out detailed toggles:
    • commit: Defaults to false, including inside an existing Git repository. Explicit true requires initially clean Git state and commits once after successful local build; an unchanged staged index is a successful no-op.
    • push: Defaults to false. Explicit true publishes HEAD to the current branch’s configured upstream remote/reference. Missing upstream or custom push-only routing fails before build writes; origin/main is never invented.
  • restrictions: Configuration block to enforce Git checks specifically during production builds:
    • only_branches: A list of allowed branch names. Production builds will abort if the current branch is not in this list.
    • not_branches: A list of restricted branch names. Production builds will abort if the current branch is in this list.
    • not_behind: Omitted/false performs no fetch. Explicit true fetches the current configured upstream and compares its state. If enabled, production builds will verify that the local branch has an upstream tracking remote and is not behind it, aborting if the local branch needs to pull upstream changes.
  • clear_output: An optional string controlling workspace clearing routines for output directories. Can be set to "pre", "post", or "never". If omitted, defaults to evaluating the PROJR_CLEAR_OUTPUT environment variable.

Development Overrides

You can define a dev block to completely override specific configurations during development builds (proj build-dev).

  • scripts: A list of script paths or globs. During development builds, this array entirely overrides build.scripts. An explicitly empty array ([]) selects no analysis scripts. An absent dev.scripts inherits build.scripts. Hooks can still run.
  • hooks: A mapping identical to build.hooks. When specified, these completely replace build.hooks during a development build.
  • old_dev_remove: Retained configuration field. The current preview protections skip CLI cleanup of prior caches during development builds, even when this is true. Scripts and hooks still control their own writes.

Environment Variables

  • PROJR_AUTO_INSTALL: During the proj build pre-flight checks, if required R packages (like bookdown or rmarkdown) are missing, this environment variable controls remediation. If set to true, packages are automatically installed. If absent or set to false, the tool defaults to an interactive terminal prompt (if available) or fails hard.

Runtime settings and output clearing

build declares actions; settings controls how they run. Parameters are analysis inputs, not execution controls. This is an intentional extension beyond projr.

settings:
  output-clear-stage: none
  execution-directory: native
  path-representation: auto

Use none to preserve other existing final files, pre to clear immediately before analysis, or post to clear immediately after successful analysis and before output promotion/finalization. Preview never clears released outputs. Pre-hooks run before pre-clear; end hooks run after finalization immediately before the next-dev bump. The command’s explicit –output-clear-stage overrides merged settings; those override legacy build.clear_output, then PROJR_CLEAR_OUTPUT, then the new none default. Legacy never is accepted in the legacy field/environment. The canonical settings key accepts only none/pre/post, with invalid values/null rejected before merge or mutation. execution-directory accepts native/project; explicit --execution-dir wins over merged settings, then native is the fallback. Native scripts inherit launch cwd; native document execution remains renderer-defined. path-representation accepts auto/absolute/relative; explicit path-query --format wins over merged settings, then auto is the fallback. Auto is caller-relative ordinarily and absolute in a known managed renderer. Both settings reject null, booleans and unknown values in each active file before merging. Managed child queries retain the captured representation policy even if scripts change configuration, profiles or cwd. Safe is the default path target; final must be explicitly requested. Docs output handling and the R-data built-in remain separately modeled features.

R package data

The built-in output-r-data lookup has fixed final destination project/data, even without YAML. Querying never activates build management or creates directories. Safe lookup needs the selected declared cache and active version.

To opt into ordinary output clearing and success-only promotion:

directories:
  cache:
    path: _tmp
  output-r-data:
    ignore: []

An empty output-r-data mapping also activates the role, with ordinary default ignore rules. Explicit ignore: [] includes package data in Git and R builds. The path may be omitted; if present it must resolve to project/data. Redirection is forbidden. settings.output-clear-stage applies normally: pre/post clears old package data; the default none preserves other final files. Preview never promotes final data.

Legacy _projr.yml and active _projr-*.yml layers accept data as an alias and normalize it before merging, including legacy remote content labels. Defining both aliases in one layer is an error. Canonical _proj.yml requires output-r-data. Generic data-* labels are unsupported; use raw-* inputs or ordinary output-* mappings.

Existing archive inventory coverage

CAS ingestion records the current recursive file paths and content hashes for the explicitly selected directory. The transition fixture compares exact inventories and stored bytes after a same-size/same-modified-time edit, an addition, a rename and a deletion. Earlier snapshots remain inspectable across those later ingestions. A renamed file appears under its new path in the current snapshot; this does not create a rename-event format.

This verifies existing archive machinery only. It does not automatically record all build inputs, code, configuration or dependencies, select a future build record format, or decide content-only identity and retention policy. Complete M2 provenance remains unfinished.

Production file inventory

Current source adds directory boolean hash. It defaults to true for declared raw/output/docs labels and false for cache labels. Set hash: false to omit a directory, or hash: true to include a cache. Each active layer must use a boolean; null, numbers and strings fail validation before hooks.

directories:
  raw-data: {path: inputs}
  cache: {path: _tmp, hash: false}
  output: {path: results}

A successful output-enabled production build writes root manifest.csv, without requiring Git or a remote. Preview and build.output_run: false leave that CSV alone. See the inventory notes. This is newer than installed preview.2. See the compatibility log and PR175 for verification evidence.

Configured restore source fields

The current source’s explicit remote restore command reads the existing projr directories.LABEL.source and build.local/build.github definitions. See the remote command reference for lookup precedence, limits and safety. This does not enable automatic ordinary uploads in build; normal build validation still rejects unsupported publication fields. The future top-level registry proposal remains separate. _proj.yml and legacy _projr.yml discovery/conflict rules remain unchanged.

Configured restore uses the shared profile selection order: explicit profile, PROJR_PROFILE, QUARTO_PROFILE, then build.profile, with earlier profiles winning and local overrides last. Machine failures preserve installation/recovery details on stderr, including retained backup paths; stdout stays a structured failure. Legacy data CSV rows and remote data namespaces are read without rewriting history; ambiguous canonical/legacy namespaces fail before installation. One optional VERSION trust marker is accepted; it is not a byte-verification claim.

Review precision: VERSION.zip requires exactly the canonical VERSION member spelling, including on case-insensitive filesystems. Metadata transfer staging also closes explicitly and reports cleanup failure paths.

Configured local publication candidate

build.local.TITLE accepts selected latest destinations with explicit send.inspect:file. See the remote command reference for the complete example and tested/pending control matrix. content:false/null disables a destination, true selects declared non-cache roles, and a list retains its explicit label order. Each selected role must have CSV hash capture enabled. The existing if-change/sync-diff defaults remain; omitted inspect does not silently change the projr manifest default to file.

Archive, manifest/none inspection, path-append-label:false, title-level cue and nonempty get/conflict controls are not executable in this bounded slice. Selected unsupported policy fails before hooks. Registry706 remains design-only.
