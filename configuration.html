Configuration _proj.yml

Preview.4 includes the named remote definitions, file-history formats and explicit local snapshot recovery documented below. Historical slice notes retain their original verification scope. See verified delivery.

Use _proj.yml to name your project folders, choose the analysis steps to run, and decide where results are saved. The examples below describe preview.5; unmerged initialization and script-group proposals are not available yet.

Name your project folders

Directory names must start with one of these prefixes:

  • cache
  • raw
  • output
  • docs

These prefixes are case-insensitive. Any label defined in the configuration must begin with one of these approved identifiers.

Explicit paths and local initialization

Ordinary declared directories need a nonempty path. The fixed R-package role output-r-data: {} is the exception: its final destination is project/data. Runtime does not insert other missing cache/raw/output/docs mappings or synthesize subpaths for undeclared labels. Canonical data/data-* labels are rejected; see the R-package data section for the legacy per-layer data alias. For example, declaring raw-data: {path: _raw_data} makes raw-data available; it does not create an undeclared raw or raw-data-extra resource. ASCII case is ignored and case-only duplicate labels are rejected.

proj --project . --non-interactive init directories creates a missing _proj.yml once with explicit raw-data: _raw_data, cache: _tmp, and output: _output paths. It preserves existing base/profile files, creates only declared resource directories, and does not invoke Git/GitHub or add an R code directory. The preset omits build.scripts, preserving shallow discovery; it never serializes an accidental empty analysis list. To render documents, declare a docs mapping too.

Production state and project-render staging require a declared cache directory. Framework version/staging children are derived inside that declared cache; this is distinct from inventing undeclared resource labels. Storage content labels must be declared and relative storage paths use the captured project root.

Selecting the safe cache

Each cache-class directory may include boolean safe. One explicit safe: true selects that cache; otherwise an eligible exact cache label wins, then the first eligible cache in merged declaration order. safe: false excludes a candidate. Profile/local overrides retain existing declaration positions. For example:

directories:
  cache:
    path: _tmp
  cache-analysis:
    path: _analysis_cache
    safe: true

This selects _analysis_cache for explicit safe logical output lookup. Multiple true selections, non-boolean values (including null), selection flags on non-cache roles, and all declared cache candidates excluded are validation errors. Each layer’s explicit values are checked before merging; null cannot inherit a previous boolean. Cache-free queries and operations that do not consume a cache remain valid. The chosen safe cache is frozen in child run context. Cleanup, safe lookup and renderer staging consume that same selected mapping; no literal cache label is required when another eligible cache is selected.

Configuration errors

projcli checks the configuration before running the selected work:

  • An unsupported directory name stops the command with an explanation.
  • A reference to a missing directory or storage destination stops the command. The error identifies the setting that needs correcting.

Top-Level Configuration

The _proj.yml file supports a top-level config block for project-wide settings:

  • config.git.engine: The Git execution engine to use. Can be auto (default) or system. This determines how the CLI interfaces with Git capabilities natively.
  • config.git.use_proj_cred_helper: Defaults to false: use existing native Git authentication. Explicit true permits an existing single-line GITHUB_PAT, GH_TOKEN or GITHUB_TOKEN for standard HTTPS github.com remotes through a temporary host-scoped helper. There is no automatic token discovery or GitHub CLI call during builds. Tokens are environment data, never argv or shell source; persistent auth settings are unchanged.

Parameters Configuration

The _proj.yml file supports a top-level parameters block for arbitrary nested parameter evaluation. Use it for analysis inputs such as a model name, random seed or reporting date.

The configuration engine also supports several aliases for this block: parameter, params, and param. However, multiple alias conflicts within the same configuration file are structurally rejected during validation to prevent mapping confusion.

Remotes Configuration

Define named storage locations under remotes.local or remotes.github. Local locations can use ordinary latest/archive folders, shared whole-file storage (cas), or experimental shared-pieces storage (xet). GitHub supports ordinary latest/archive uploads and complete-store ZIPs for cas and xet.

Choose uploads with build.dest. Removing a destination from that selection leaves its definition available for restoring older data. The detailed examples below explain content, comparison/upload controls, and manifest options. See shared-file GitHub backups and experimental Xet for their additional requirements and limits.

Build Configuration

The _proj.yml file can also contain a build block to configure the behavior of the proj build and proj build-dev execution engine. The build block supports the following sub-keys:

  • dest: Select named destinations defined under remotes.local or remotes.github. Use a list of names, or the documented name-to-options mapping to narrow each destination’s content. The destination’s structure controls how files are saved. Removing a name from build.dest stops uploads without removing that remote as a restore source.
  • scripts: An optional list of explicit script paths or glob patterns to execute during the build pipeline.
    • Globbing patterns are supported.
    • Prefix a pattern with ! to exclude matching files from execution.
    • Current source rejects malformed inclusion or exclusion syntax before execution, including hook patterns. The exclusion correction is included in preview.3; see the build reference.
    • When provided, this selects scripts instead of automatic discovery. Document targets may be grouped for rendering, so mixed script and document targets are not guaranteed to run in the exact listed order.
  • hooks: An optional map of lifecycle hook scripts to execute.
    • pre: Scripts executed before the actual build phase.
    • post: Scripts executed after analysis/promotion, before VERSION and publication.
    • both: Scripts executed during both pre and post phases.
  • profile: An optional environment profile identifier. When set, the system injects the PROJR_PROFILE environment variable into the isolated subprocess for all executed scripts and project rendering commands. This can be overridden at runtime via the --profile CLI flag.
  • git: An optional Git integration configuration. This can be a boolean toggle or an object mapping out detailed toggles:
    • commit: Defaults to false, including inside an existing Git repository. Explicit true requires initially clean Git state and commits once after successful local build; an unchanged staged index is a successful no-op.
    • push: Defaults to false. Explicit true publishes HEAD to the current branch’s configured upstream remote/reference. Missing upstream or custom push-only routing fails before build writes; origin/main is never invented.
  • restrictions: Configuration block to enforce Git checks specifically during production builds:
    • only_branches: A list of allowed branch names. Production builds will abort if the current branch is not in this list.
    • not_branches: A list of restricted branch names. Production builds will abort if the current branch is in this list.
    • not_behind: Omitted/false performs no fetch. Explicit true fetches the current configured upstream and compares its state. If enabled, production builds will verify that the local branch has an upstream tracking remote and is not behind it, aborting if the local branch needs to pull upstream changes.
  • clear_output: An optional string controlling workspace clearing routines for output directories. Can be set to "pre", "post", or "never". If omitted, defaults to evaluating the PROJR_CLEAR_OUTPUT environment variable.

Development Overrides

You can define a dev block to completely override specific configurations during development builds (proj build-dev).

  • scripts: A list of script paths or globs. During development builds, this array entirely overrides build.scripts. An explicitly empty array ([]) selects no analysis scripts. An absent dev.scripts inherits build.scripts. Hooks can still run.
  • hooks: A mapping identical to build.hooks. When specified, these completely replace build.hooks during a development build.
  • old_dev_remove: Retained configuration field. The current preview protections skip CLI cleanup of prior caches during development builds, even when this is true. Scripts and hooks still control their own writes.

Environment Variables

  • PROJR_AUTO_INSTALL: During the proj build pre-flight checks, if required R packages (like bookdown or rmarkdown) are missing, this environment variable controls remediation. If set to true, packages are automatically installed. If absent or set to false, the tool defaults to an interactive terminal prompt (if available) or fails hard.

Runtime settings and output clearing

build declares actions; settings controls how they run. Parameters are analysis inputs, not execution controls. This is an intentional extension beyond projr.

settings:
  output-clear-stage: none
  execution-directory: native
  path-representation: auto

Use none to preserve other existing final files, pre to clear immediately before analysis, or post to clear immediately after successful analysis and before output promotion/finalization. Preview never clears released outputs. Pre-hooks run before pre-clear; end hooks run after finalization immediately before the next-dev bump. The command’s explicit –output-clear-stage overrides merged settings; those override legacy build.clear_output, then PROJR_CLEAR_OUTPUT, then the new none default. Legacy never is accepted in the legacy field/environment. The canonical settings key accepts only none/pre/post, with invalid values/null rejected before merge or mutation. execution-directory accepts native/project; explicit --execution-dir wins over merged settings, then native is the fallback. Native scripts inherit launch cwd; native document execution remains renderer-defined. path-representation accepts auto/absolute/relative; explicit path-query --format wins over merged settings, then auto is the fallback. Auto is caller-relative ordinarily and absolute in a known managed renderer. Both settings reject null, booleans and unknown values in each active file before merging. Managed child queries retain the captured representation policy even if scripts change configuration, profiles or cwd. Safe is the default path target; final must be explicitly requested. Docs output handling and the R-data built-in remain separately modeled features.

R package data

The built-in output-r-data lookup has fixed final destination project/data, even without YAML. Querying never activates build management or creates directories. Safe lookup needs the selected declared cache and active version.

To opt into ordinary output clearing and success-only promotion:

directories:
  cache:
    path: _tmp
  output-r-data:
    ignore: []

An empty output-r-data mapping also activates the role, with ordinary default ignore rules. Explicit ignore: [] includes package data in Git and R builds. The path may be omitted; if present it must resolve to project/data. Redirection is forbidden. settings.output-clear-stage applies normally: pre/post clears old package data; the default none preserves other final files. Preview never promotes final data.

Legacy _projr.yml and active _projr-*.yml layers accept data as an alias and normalize it before merging, including legacy remote content labels. Defining both aliases in one layer is an error. Canonical _proj.yml requires output-r-data. Generic data-* labels are unsupported; use raw-* inputs or ordinary output-* mappings.

Existing archive inventory coverage

CAS ingestion records the current recursive file paths and content hashes for the explicitly selected directory. The transition fixture compares exact inventories and stored bytes after a same-size/same-modified-time edit, an addition, a rename and a deletion. Earlier snapshots remain inspectable across those later ingestions. A renamed file appears under its new path in the current snapshot; this does not create a rename-event format.

This verifies existing archive machinery only. It does not automatically record all build inputs, code, configuration or dependencies, select a future build record format, or decide content-only identity and retention policy. Complete M2 provenance remains unfinished.

Production file inventory

Current source adds directory boolean hash. It defaults to true for declared raw/output/docs labels and false for cache labels. Set hash: false to omit a directory, or hash: true to include a cache. Each active layer must use a boolean; null, numbers and strings fail validation before hooks.

directories:
  raw-data: {path: inputs}
  cache: {path: _tmp, hash: false}
  output: {path: results}

A successful output-enabled production build writes root manifest.csv, without requiring Git or a remote. Preview and build.output_run: false leave that CSV alone. See the inventory notes. This CSV capture is included in preview.3. See the compatibility log and PR175 for verification evidence.

Configured restore source fields

The current source’s explicit remote restore command reads the existing projr directories.LABEL.source and build.local/build.github definitions. See the remote command reference for lookup precedence, limits and safety. This does not enable automatic ordinary uploads in build; normal build validation still rejects unsupported publication fields. The future top-level registry proposal remains separate. _proj.yml and legacy _projr.yml discovery/conflict rules remain unchanged.

Configured restore uses the shared profile selection order: explicit profile, PROJR_PROFILE, QUARTO_PROFILE, then build.profile, with earlier profiles winning and local overrides last. Machine failures preserve installation/recovery details on stderr, including retained backup paths; stdout stays a structured failure. Legacy data CSV rows and remote data namespaces are read without rewriting history; ambiguous canonical/legacy namespaces fail before installation. One optional VERSION trust marker is accepted; it is not a byte-verification claim.

Review precision: VERSION.zip requires exactly the canonical VERSION member spelling, including on case-insensitive filesystems. Metadata transfer staging also closes explicitly and reports cleanup failure paths.

Configured local publication candidate

build.local.TITLE accepts selected latest destinations with explicit send.inspect:file. See the remote command reference for the complete example and tested/pending control matrix. content:false/null disables a destination, true selects declared non-cache roles, and a list retains its explicit label order. Each selected role must have CSV hash capture enabled. The existing if-change/sync-diff defaults remain; omitted inspect does not silently change the projr manifest default to file.

Archive, manifest/none inspection, path-append-label:false, title-level cue and nonempty get/conflict controls are not executable in this bounded slice. Selected unsupported policy fails before hooks. Registry706 remains design-only.

For configured ordinary local latest publication, explicit send.inspect: none selects blind source-file planning and defaults send.strategy to upload-all. Explicit upload-missing/sync-diff then overwrite source filenames while retaining remote extras; sync-purge only purges when the source is nonempty. See the remote control matrix before choosing these combinations. Omitted inspection retains the projr manifest default, using matching recorded history or falling back to physical file comparison.

Configured ordinary build.local publication now follows the archive default when structure is omitted; latest remains explicit. The existing manifest inspection and sync-diff/if-change defaults apply. See archive publication for historical reuse, complete snapshots and unsupported append-label:false.

The first build.github upload subset requires explicit send.inspect: none and upload-all (the none default), with archive as the existing structure default. Other decision combinations and existing current-version data fail explicitly. See the remote CLI page for credentials, metadata bounds and partial failure.

Ordinary named remotes and upload selection

Ordinary local latest/archive and GitHub Release definitions can now live under top-level remotes rather than build. A definition remains available to restore even when the build no longer uploads to it. These use the same executable definition/send fields already accepted by inline ordinary publication.

remotes:
  local:
    historical:
      path: ../historical-store
      structure: archive
      content: [raw-data]
    current:
      path: ../current-store
      structure: latest
      send:
        cue: if-change
        inspect: manifest
build:
  dest:
    current:
      content: [output]
  scripts: []
  git: false

A selected destination’s content list limits that build to declared labels allowed by the remote’s content, if specified. Omit the destination’s content to use all remote-eligible labels; if the remote also omits content, ordinary content:true selection applies (declared non-cache labels, with existing hash requirements). Explicit content:[] selects no labels. build.dest:{} selects no registered uploads. Registry membership alone does not upload or load GitHub credentials.

Normal builds now accept and validate the existing directory source metadata:

directories:
  raw-data:
    path: data
    source:
      local: historical

This does not automatically restore during a build. Use the existing remote restore command with –label, optionally –title/–provider and explicit version/clear choices. Source lookup uses the registry independently of build.dest. Directory-specific references keep priority. Existing legacy preferred sources win first; an explicitly preferred registered source can win over an unpreferred legacy fallback. Otherwise legacy fallback order remains ahead of newly available registry fallback definitions.

Unknown names, duplicate/portable-aliased registered names, invalid/excluded label subsets and conflicting registry/inline definitions fail before hooks or writes. The new mapping selection cannot be mixed with inline build.local/build.github; move those definitions to remotes first. Empty/omitted subsets are distinct from null; explicitly null/malformed mapping entries are rejected. Remote-level content:null retains its existing disabled/no-label meaning and cannot be overridden by a build subset.

Legacy inline ordinary builds and legacy CAS name-list destinations retain their existing path. Purely legacy CAS name lists do not acquire new case-folding rules. The new registry also accepts an ordinary name list for all eligible content, while mapping form is required for per-build label subsets.

Named ordinary local destinations now support flat CSV/JSON history and metadata placement, described below. GitHub flat/tree metadata is also implemented below. Configured CAS tree mapping publication is described below. The existing CAS name-list route retains its legacy flat encoding when using legacy definitions. Previously stored snapshots and the explicit tree APIs remain unchanged.

Configured local CAS tree publication

New local CAS definitions can select recursive tree publication through the named registry. Directory selection is independent of full metadata placement:

remotes:
  local:
    snapshots:
      path: ../snapshot-store
      structure: cas
      manifest: auto
      manifest-style: tree
build:
  dest:
    snapshots:
      content: [raw, output]

Omitted content selects eligible non-cache declared labels. Explicit null, false or an empty list selects none; build subsets cannot enable excluded labels. auto means remote for this CAS writer. remote stores complete tree objects and snapshot metadata beside file objects; project stores that metadata under the project; both requires both copies. File objects always remain in the configured store. A small project reference is retained for every successful publication, including remote placement. That reference is not itself a complete archive.

Raw objects, directory objects and snapshot/reference records use first-two- characters/rest-of-hash fan-out. Identical directory contents share a root across labels and versions. Snapshot version associations are separate immutable records. There is no inferred timestamp or mutable discovery index. Existing blobs are verified before reuse. Required graphs precede full references; the small project reference is written last. Errors after provider entry retain the local release and distribution evidence. both is not a cross-location atomic transaction: partial references/objects may remain and errors say so. Nothing is garbage- collected or rolled back from a published store automatically.

Previously accepted path/structure/content/inspect CAS definitions keep their legacy flat JSON identities and plural .projr/manifests.csv ledger. Name-list selection still works; mapping subsets preserve legacy label spelling. To opt into new trees, remove the legacy inspect field and explicitly select tree if desired. No old manifest is reinterpreted or moved.

The first publication slice added tree storage. Explicit named-ID recovery and local CAS flat CSV/JSON histories are described below. Automatic snapshot lookup remains deferred. Legacy inspect belongs only to the old definition; new manifest-format choices are validated against style. Ordinary local/GitHub flat histories are also implemented below, alongside compatible CSV/VERSION metadata; Ordinary local and GitHub tree metadata are described below.

Restore from a saved tree after changing upload choices

The explicit CAS restore/verify commands use a named remotes.local definition and saved snapshot ID. They do not run build.dest selection or require the current write style/placement to match the older snapshot. The destination label must still be declared. Existing full remote and project metadata are checked; no root manifest.csv or mutable index is required. Normal directory-source preference remains the ordinary restore selection contract when no snapshot ID is supplied.

Existing flat CAS snapshots can also be checked and restored by exact ID without converting them. See the remote reference. Their older file lists do not record empty folders, so those cannot be restored from that format. Local CAS CSV/JSON history is described below; ordinary/GitHub flat publication is also implemented below; Ordinary local and GitHub tree metadata are described below.

Flat history in local CAS

New local CAS remotes can save a readable CSV or JSON history instead of a directory-tree manifest:

remotes:
  local:
    snapshots:
      path: ../snapshot-store
      structure: cas
      manifest-style: flat
      manifest-format: csv
      manifest: remote
build:
  dest:
    snapshots:
      content: [raw, output]

The labels must already be declared. For flat style, csv is the default; json is also available. Both automatically reuse an earlier complete inventory for the same logical folder when later contents are identical, including a reversion to older contents. The later version points directly to that earlier complete version, never a chain. A changed version records all current file memberships, including additions, removals and renamed paths.

CSV is one rectangular table with a header and repeated label/version columns. In Excel, filtering a reference version shows the earlier ref_version to inspect; it does not automatically expand that earlier listing. All earlier complete rows remain in the same history file. Plain CSV/JSON retains literal full file hashes. Optional csv-dedupe-file/json-dedupe-file modes replace repeated hashes with a bundled file dictionary while retaining every file path. These modes are off by default. They are not omitted-file deltas, and no size/speed advantage is promised.

Files are stored once by their BLAKE3 content hash regardless of manifest format. Full history files live under catalogues/v1/manifest.csv or manifest.json; opt-in dictionary files use manifest-dedupe-file.csv/json. Existing root manifest.csv keeps its separate projr-compatible MD5 schema and is unchanged.

auto means remote for CAS. project/remote/both selects full history placement; a small project snapshot binding is always retained. Flat bindings connect the version and selected labels to inventory hashes, independently of serialization or dictionary IDs. They are not directory-tree object IDs. Full immutable refs use flat-snapshots/v1/<first2>/<rest62>.json; small project refs use references/flat-v1/<first2>/<rest62>.json. No unnecessary tree objects are written.

History replacement is atomic per file. Decoded previous label/version contents are never overwritten; divergent histories or conflicting same-version retries fail. Identical per-label retries do not duplicate rows, and missing labels can resume a partial write. Switching format preserves older files/readability and uses the longest compatible decoded history; dictionary IDs do not define it. Codec limits fail explicitly rather than truncating history.

The authoritative history read through replacement/reference publication holds the existing cooperative claim at <store>/.proj/build.lock. Unknown/stale claims fail closed and only an owned claim is removed; there is no automatic process killing or stale-claim cleanup. Raw immutable objects may be copied before that claim. Required history copies precede full snapshot refs, then the small project ref. both is not a cross-location transaction: errors can leave objects or an updated first history copy. Retry can finish the remaining copy.

Explicit verify/restore resolves version references/dictionaries, checks inventory hashes and actual raw bytes, and uses the existing guarded installer. The result reports snapshot_kind: flat-catalogue-v1. Old tree and legacy-flat IDs stay distinct and readable, regardless of the current write style. A small binding alone is not a backup. Empty directories are recorded by this new format, unlike legacy flat.

These manifest-format controls apply to local CAS and the ordinary local/GitHub flat histories described below. Ordinary providers retain compatible CSV/VERSION metadata alongside the new histories. CAS trees default to fixed v1 JSON; explicit manifest-format: json is valid there, while CSV/dictionary choices require flat style. Null/unknown modes fail instead of silently choosing a default.

File lists for ordinary local destinations

Development source supports the four flat manifest formats for named local latest/archive destinations:

remotes:
  local:
    backup:
      path: ../backup
      structure: archive
      manifest: both
      manifest-style: flat
      manifest-format: csv
build:
  dest:
    backup:
      content: [raw, output]

Here csv is the default; json, csv-dedupe-file and json-dedupe-file are also supported. Identical complete inventories for the same logical folder reference the earlier complete version. Optional dictionaries retain every path row. The build version identifies the observation; its file hashes describe the actual final destination, including older files retained by upload-missing or upload-all. This is separate from the project’s source CSV.

manifest:auto defaults to both for ordinary local destinations. project stores complete new history only in the project; remote stores it only under the remote’s .projcli-manifests directory; both stores both. Complete catalogue files use the same catalogues/v1 filenames as local CAS. A small project binding is always written last under .proj/remotes and records the physical folder, empty marker and verbatim legacy VERSION entry. The binding alone is not a complete file list.

Unchanged archive data may stay in an older physical version directory; the new build record points there. Latest records describe what was observed, without making older overwritten bytes recoverable. An asterisk in legacy VERSION still means source agreement is untrusted; hashing actual destination bytes does not remove it. Root MD5 manifest.csv, VERSION and CHANGELOG.md remain the existing compatibility metadata regardless of the new manifest placement.

Pure legacy inline build.local definitions keep their old behavior unless an explicit manifest/style/format field opts in. Null or unknown options fail. Ordinary local tree metadata and GitHub flat formatting are described below; GitHub tree metadata is described below. Switching formats retains old files and reads compatible earlier history; conflicting retries or histories fail rather than overwrite recorded inventory.

A cooperative destination claim covers history reads through publication. Required full catalogues precede immutable full bindings and the small project binding. Multiple copies are not a transaction: failure may leave earlier data or metadata installed, and is reported as partial publication.

Changing ordinary local placement reads compatible history from both fixed known locations, but writes complete history only to the newly selected locations. Old unselected files remain intact; changing placement or format cannot silently start a disconnected history.

File lists for GitHub Release destinations

Development source uses flat CSV by default for named GitHub Release destinations:

remotes:
  github:
    analysis-files:
      structure: archive
      manifest: both
      manifest-format: json
build:
  dest:
    analysis-files:
      content: [raw, output]

The same four flat formats and auto/project/remote/both placements as ordinary local destinations apply. auto means both. The format default remains csv; Tree style is available for ordinary local destinations; GitHub tree style is also described below. Legacy inline build.github without new metadata fields retains its old behavior.

Complete new remote history is a separate projcli-manifests-v1.zip Release asset, containing versioned catalogue files and immutable snapshot bindings. Existing manifest.zip, VERSION.zip and CHANGELOG.zip retain their compatibility purpose. Project full history, when selected, lives under the provider-separated .proj/remotes name; a small project binding is always kept. Names, not upload selection, still determine which registered remotes remain available sources.

Recorded inventories describe exact prepared ZIP payloads or a physically downloaded reused archive. They never describe an empty catalog placeholder. Bindings retain the frozen repository/tag, actual asset filename, empty variant, inventory hash and existing VERSION advertisement separately from the build version. The ZIP writer’s omitted empty child folders are not falsely recorded. Legacy root MD5 manifest.csv and VERSION* meanings remain unchanged.

History is read from the two fixed known locations across format/placement changes. Old files remain readable and are not silently migrated or deleted. Bundles reject unknown members, conflicting/corrupt histories and unsafe paths; compressed and expanded limits are 128 MiB, individual metadata files 16 MiB, and native ZIP member count at most 100,000 including directory entries. Generated bundles must pass the same reader before uploads.

All targets prepare before HTTP writes. Data and legacy metadata precede each new bundle. Replacing a bundle requires its asset identity to match the original observation; a newer asset fails without deleting it. This is optimistic protection, not distributed locking or a remote transaction. All required target HTTP writes and project full metadata writes precede small project references. Later failures preserve local release and honest partial-publication evidence, without automatic rollback or retry. Ordinary restore continues the compatible metadata path.

Changing local CAS flat-history placement

For configured flat CAS, both fixed known metadata locations are guarded/read regardless of selected write placement. Changing project to remote to both, even while switching CSV/JSON modes, preserves the longest compatible complete history. Only selected full locations are written; old unselected files remain intact. A conflicting known copy fails before hooks rather than silently discarding it. Reads are rechecked under the store writer claim before publication. Existing exact-ID snapshots remain recoverable. This is fixed-location continuity, not automatic snapshot discovery or a migration.

Tree metadata for ordinary local backups

Ordinary local data keeps its latest/archive folder layout while directory metadata can use the same v1 content identities as native CAS:

remotes:
  local:
    backup:
      path: ../backup
      structure: archive
      manifest-style: tree
      manifest: remote
      # Optional for tree style; JSON is the fixed representation.
      manifest-format: json
build:
  dest:
    backup:
      content: [raw, output]

Defaults remain flat for ordinary local/GitHub destinations and tree for modern local CAS. Ordinary local tree metadata uses JSON; CSV/file-dictionary choices require flat style. GitHub tree metadata is also supported as described below. Legacy inline definitions opt in by specifying new metadata fields.

Directory objects live at trees/v1/<first2>/<remaining62>.json inside the selected full metadata location. Each child’s name/type/content hash determines its directory ID; labels, build versions, physical paths and catalogue serialization are excluded. No ordinary data is copied into a CAS objects directory.

The complete JSON catalogue remains a readable companion and immutable-version lookup, with the existing direct references to earlier complete inventories. Tree roots are derived independently and checked against that exact membership. This duplicates some metadata deliberately; neither reduced size nor speed has been established. Old flat bindings remain unchanged; a distinct projcli.ordinary-local-tree-snapshot.v1 binding adds each payload’s tree root, separate from inventory_hash and its physical data location.

Placement chooses full directory-object/history/binding copies. A small project reference still records the root when full metadata is remote. Required directory objects and full histories precede full bindings and the small project reference. Changing style/format preserves old files and compatible history.

Each final private payload is checked before replacing its existing directory, including Tree representability; the complete selected forest is checked again at metadata publication. Bounds include 100,000 inferred records including roots, 64 path components, 4,096 path bytes, 16 MiB cumulative expanded path work and 64 MiB unique directory metadata per forest. Each object retains the existing 16 MiB document bound. Node IDs are checked before following them; links and special files fail. Multi-label/multi-location publication is not a transaction: later failure may leave earlier effects and preserves local release/evidence.

Ordinary restore remains the compatible CSV/VERSION operation. Its file data is still the normal backup folder. The separate exact-ID CAS recovery commands do not reinterpret these ordinary bindings as CAS file-object snapshots.

Tree metadata for GitHub Release backups

GitHub Release destinations keep their ordinary data ZIPs and flat default. To opt into directory-based fingerprints, set tree style on the named remote:

remotes:
  github:
    backup:
      structure: archive
      manifest-style: tree
      manifest: remote
      # Optional; tree metadata has a fixed JSON representation.
      manifest-format: json
build:
  dest:
    backup:
      content: [raw, output]

The Release receives projcli-manifests-v1.zip containing the readable JSON history, directory objects at trees/v1/<first2>/<remaining62>.json and immutable snapshot bindings. The project retains a small root reference even with remote placement. Project/both placement additionally saves full selected metadata under the existing provider-separated project location. Auto retains ordinary both behavior. Tree style requires JSON; CSV and dictionary formats require flat.

Roots depend only on names, kinds and file hashes of the exact prepared or downloaded retained data ZIP. Build version, label, Release repository/tag/asset and legacy VERSION advertisement bind separately in projcli.github-tree-snapshot.v1. No ordinary file data is stored as CAS objects. The complete readable history is deliberately retained beside the graph; this is a metadata trade-off, without a size or speed claim.

All bundle members are bounded and allowlisted. Every directory object’s ID is verified, and each tree binding must reconstruct the recorded inventory hash. Missing/corrupt nodes fail before HTTP publication. Existing flat bindings remain readable with unchanged IDs; switching styles retains compatible history and old nodes. New snapshots never destructively reinterpret an earlier format.

Prepare required graphs, history, bindings and data ZIPs before HTTP writes. Upload data and compatibility metadata, then the new metadata bundle. After all required target HTTP operations succeed, write all selected project full copies, then small references. Failures may leave earlier remote/full metadata effects; there is no atomic multi-target transaction. Ordinary restore still uses its compatible CSV/VERSION path and data ZIP, rather than treating these bindings as native CAS snapshots.

Preserved legacy CAS writer

Legacy CAS name-list definitions keep their existing encoding and index schema. Their writer now claims the store and the separate project .projr lookup scope. Exact repeated version/label/digest rows are not appended again; earlier bytes and differing rows remain intact. No new configuration key, same-version conflict rule or automatic migration is introduced. Busy/stale claims fail rather than guessing ownership. Modern named format/placement defaults are unchanged.

R processes and executable

The M4 draft adds an R block under config (not settings):

config:
  r:
    session: isolated
    # Optional: a native executable file, not a shell command with arguments.
    # rscript: "tools/R installation/bin/Rscript"

session accepts isolated (default) or shared. Isolated starts a fresh Rscript for each plain R script. Shared lazily starts one child R process for the selected plain R analysis scripts in that build, preserving their objects, options, working directory and library changes across scripts, even with Python/document steps between them. It is not the R frontend caller’s live session. Source or shared-process shutdown failures stop the build; later scripts and end hooks do not run. Ordering is unchanged.

rscript is an optional path resolved against the captured project root; absolute paths also work. Omission uses Rscript on PATH. Spaces are literal path data, not shell quoting. Missing files, nonexecutables and Windows non-.exe files fail preflight. The selected executable serves plain R scripts, R hooks and Rmd/Bookdown R drivers. Quarto chooses its own engine; this setting does not rewrite its setup.

Hooks stay in separate processes, including in shared mode. Renderers retain native execution settings and do not receive the shared analysis workspace. The child starts with the existing controlled run environment, active libraries and captured root/profile/version context; later R state changes do not modify the Rust driver or other processes. The initial cwd follows execution-directory policy. Shared mode uses source(…, local=.GlobalEnv, chdir=FALSE), so Rscript commandArgs and stdin are worker controls, not per-script arguments or interactive input. Startup files/renv activation retain normal R behavior at worker launch; there is no automatic dependency restore, clean-room or sandbox guarantee.

Optional R project setup and build maintenance

These features are included in preview.5. They were added after preview.4; use the matching command and separately installed R task dependencies. Plain Markdown remains supported. To create an R Markdown README without replacing README.md:

proj init readme --rmd --title "My project"

This creates README.Rmd only. To start an empty renv project deliberately, with renv already installed in the selected R:

proj init renv

The command uses renv::init(bare=TRUE, restart=FALSE), then an initial snapshot(type=‘all’, prompt=FALSE) of its installed project library to create renv.lock. It does not discover/install missing analysis dependencies during init. It does not install renv, restore project packages, or run as part of normal init. Existing renv, renv.lock or .Rprofile is preserved by refusing this command; manage an existing project directly with renv. Failure restores the fixed project setup paths, including ignore files; effects in package caches or arbitrary startup code are not reversible. config.r.rscript chooses R for this command too.

Choose production build tasks independently under build, rather than config:

config:
  r:
    session: isolated
    # rscript: "tools/R installation/bin/Rscript"
build:
  r:
    document: true
    readme: true
    renv-snapshot: true

All three default to false, preserving existing projcli builds. document requires DESCRIPTION and R/ and runs devtools::document(). readme requires README.Rmd and renders it to root README.md using rmarkdown’s md_document format. renv-snapshot requires an existing renv.lock and runs renv::snapshot(prompt=FALSE); it never means restore. Missing packages are errors, with no framework dependency install. These are production actions; build-dev skips them even when selected.

Before start hooks, preflight checks fixed inputs/outputs and installed packages. After managed recovery is captured, snapshot runs before start hooks, matching original projr. Then start hooks/preparation, input inventory and analysis proceed. After successful analysis, post-clear, restoration of native artifacts and output promotion, snapshot runs again, followed by documentation and README. Then output inventory/history and distribution proceed. No housekeeping action runs between pre-clear and analysis, analysis and post-clear, or end hooks and the next development version. End hooks remain last.

The post actions share one short-lived R child rooted at the project. Preflight and the pre-analysis snapshot use separate children. This reuses package loads within the post batch, not across all build stages. It is not a daemon or the shared analysis session, and it does not inherit caller R objects. Normal project startup/renv activation still runs in each child. A persistent housekeeping worker would require a separate lifecycle/state-leakage design and is not implemented.

Fixed man/, NAMESPACE, DESCRIPTION, README.md, README_files/ and renv.lock effects join existing bounded build recovery, before distribution. Linked/special paths are rejected before launch; Unix additionally rejects multiply linked fixed files. Native R code, package loading/compilation, custom README output hooks and user-defined roxygen extensions can write elsewhere: there is no whole-project sandbox or rollback guarantee, and no new Windows hard-link guarantee. No citation generation or citation metadata update is included.

The existing named R build/version helpers retain their M4 DESCRIPTION restriction. Package projects can invoke these CLI tasks through proj_cli(“build”, “–patch”). This slice does not synchronize DESCRIPTION’s Version with VERSION or add legacy package-version authority; generated package documentation may reflect its existing DESCRIPTION. Use the original R backend when that broader behavior is required.

When migrating from projr, set renv-snapshot explicitly if you relied on its automatic snapshots for an existing renv project. Select document/readme explicitly if you want those maintenance tasks. Merely creating README.Rmd or initializing renv does not enable any build task.

Experimental Xet storage

Available in preview.5. Set structure: xet on a named local or GitHub remote. Both use the same optional, pinned local helper; GitHub transfers the complete store as a ZIP. Existing default storage choices do not change. The helper is qualified on Linux/WSL; macOS is unqualified and native Windows Xet is rejected. Initialization, queries and previews do not open or install the helper.

Use manifest: auto or remote for complete records in the store, with manifest-style: tree and fixed JSON records. Other placement and format choices are rejected before a build. This remains experimental, with no inherited promise of long-term upstream archival support. See the Xet guide for installation, examples, format limits and the actual corruption-test results.

Complete stores on GitHub

remotes.github.<name>.structure: xet uses one long-running storage release for whole-store ZIPs. Select uploads with build.dest. Exact snapshot restore and verification require --max-bytes, --max-expanded-bytes and the trusted Git-tracked project records identifying the uploaded ZIP. Old exports are retained.

remotes.github.<name>.structure: cas shares whole files instead of file pieces and needs no Xet helper. Set manifest-style: tree or flat explicitly. Flat accepts csv, json, csv-dedupe-file and json-dedupe-file; tree has fixed JSON records. This transport initially supports only manifest: auto or remote. See the shared-file GitHub guide for commands, placement and recovery limits. A complete CAS-store ZIP differs from an ordinary latest/archive folder ZIP.

Both are included in preview.5 and completed a real synthetic GitHub round-trip. That bounded test does not establish full projr compatibility or savings for your data. Neither backend automatically finds missing project records or deletes older exports.

VERSION and DESCRIPTION synchronization (source candidate)

VERSION remains the version authority. By default, writing it also updates only the Version field of an existing DESCRIPTION. Other fields, continuation text and line endings are preserved. No DESCRIPTION is created by a build or version update.

settings:
  sync-description-version: true

Set false to leave DESCRIPTION untouched. Active profile/local layers apply normally; null, strings and numbers are rejected for this switch. If the two versions differ, the command explains that VERSION wins. Previews report the mismatch without changing either file. Production release and next-development writes synchronize both, and pre-distribution failure restores their exact prior bytes, including dev counters. Duplicate/continued Version fields or invalid DESCRIPTION field syntax fail before hooks. Two file replacements are recoverable on ordinary errors, not crash-atomic.

Named R build/version helpers accept these projects under this VERSION-authoritative contract; an explicit legacy backend retains its original authority rules. Bookdown and arbitrary legacy arguments remain separate unsupported mappings.
