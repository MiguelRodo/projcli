Configuration _projr.yml

Preview.4 includes the named remote definitions, file-history formats and explicit local snapshot recovery documented below. Historical slice notes retain their original verification scope. See verified delivery.

Use _projr.yml to name your project folders, choose the analysis steps to run, and decide where results are saved. The examples describe published preview.6. Older previews lack the new initialization and script-group options. Current source (unreleased) uses projr’s file layout and profile key, described next; preview.6 and earlier read _proj.yml.

Configuration files and profiles

projcli reads projr 0.9’s layout (SATVILab/projr@5f915ef R/yml.R:308-359, R/profile.R:223-270). There is one base file, _projr.yml; projcli’s earlier _proj.yml name is no longer read.

Layer Root file Also accepted in .projr/config/ (or _projr/config/)
base _projr.yml _projr.yml or default.yml
profile <name> _projr-<name>.yml _projr-<name>.yml or <name>.yml
local _projr-local.yml _projr-local.yml or local.yml

For each layer the root file wins, then .projr/config/, then _projr/config/. Having both spellings of one layer in the same configuration directory (for example .projr/config/_projr.yml and .projr/config/default.yml) is an error: Both _projr.yml and default.yml exist in .projr/config/. Keep one. A .projr/config/default.yml (or _projr.yml) also marks the surrounding folder as the project root, as in projr. Local files take precedence over profiles, earlier profiles over later ones, and profiles over the base file.

Choosing profiles

Profiles are chosen in this order:

  1. --profile on the command line;
  2. a nonempty PROJR_PROFILE environment variable;
  3. the profile key in the local file;
  4. the profile key in the base file.

The profile key takes a name, a list of names, or a mapping with projr and quarto entries:

profile:
  projr: [analysis]
  quarto: print

Each kind comes from the first of the local and base files that names it, so a local file that sets only quarto keeps the base file’s projr profiles. profile.renv is an error (“not supported yet”, as in projr), and named profile files cannot contain the key. QUARTO_PROFILE no longer selects projr profiles (it, or profile.quarto, still selects _environment-<profile> files, as in projr); Quarto reads it itself. When it is unset, a build records the configured Quarto profiles in its frozen run context before hooks. Gap: renderers do not apply them yet (planned for the engines slice); set QUARTO_PROFILE meanwhile.

Starter configuration

When no base file exists, proj build and proj build-dev first write projr’s starter _projr.yml (R/build.R:289-310), never overwriting a file:

directories:
  raw-data:
    path: _raw_data
  cache:
    path: _tmp
  output:
    path: _output
  docs:
    path: docs
build:
  git: false   # only outside a Git repository

Inside a repository without a tracking upstream the build block is git: {push: false}; with an upstream it is omitted. The starter omits build.scripts, so the first build runs automatic discovery. It is written before the build’s recovery snapshot and kept if the build fails, as in projr. Like projr, the build (preview included) also seeds .gitignore (and, in a package, .Rbuildignore) with projr’s starter lines and an empty managed block. Without any configuration above it, the starter goes in the current directory, not in an ancestor with VERSION, Git or package files (a deliberate difference from projr’s build fallback).

Name your project folders

Directory names must start with one of these prefixes:

  • cache
  • raw
  • output
  • docs
  • scripts or scripts-<name> (added in preview.6)

These prefixes are case-insensitive. Ordinary labels begin with cache, raw, output or docs. Source groups use exactly scripts or scripts- followed by a nonempty name.

Explicit paths and local initialization

Ordinary declared directories need a nonempty path. The fixed R-package role output-r-data: {} is the exception: its final destination is project/data. Runtime does not insert other missing cache/raw/output/docs mappings or synthesize subpaths for undeclared labels. projr’s data label is an alias of the fixed output-r-data role (see the R-package data section); other data-* labels are rejected. For example, declaring raw-data: {path: _raw_data} makes raw-data available; it does not create an undeclared raw or raw-data-extra resource. ASCII case is ignored and case-only duplicate labels are rejected.

proj --project . --non-interactive init directories creates a missing _projr.yml once with projr’s starter: explicit raw-data: _raw_data, cache: _tmp, output: _output and docs: docs paths. It preserves existing base/profile files, creates only declared resource directories, and does not invoke Git/GitHub or add an R code directory. The starter omits build.scripts, preserving shallow discovery; it never serializes an accidental empty analysis list. Because it declares docs: docs, an existing hand-written docs/ folder becomes the managed documents destination that later production builds replace; move it first or change the mapping.

General proj init writes the same starter directories in _projr.yml (through the directory initializer) when no base or active profile file exists, as projr’s projr_init does, without the build’s Git adjustments, and never overwrites an existing configuration.

Production state and project-render staging require a declared cache directory. Framework version/staging children are derived inside that declared cache; this is distinct from inventing undeclared resource labels. Storage content labels must be declared and relative storage paths use the captured project root.

Selecting the safe cache

Each cache-class directory may include boolean safe. One explicit safe: true selects that cache; otherwise an eligible exact cache label wins, then the first eligible cache in merged declaration order. safe: false excludes a candidate. Profile/local overrides retain existing declaration positions. For example:

directories:
  cache:
    path: _tmp
  cache-analysis:
    path: _analysis_cache
    safe: true

This selects _analysis_cache for explicit safe logical output lookup. Multiple true selections, non-boolean values (including null), selection flags on non-cache roles, and all declared cache candidates excluded are validation errors. Each layer’s explicit values are checked before merging; null cannot inherit a previous boolean. Cache-free queries and operations that do not consume a cache remain valid. The chosen safe cache is frozen in child run context. Cleanup, safe lookup and renderer staging consume that same selected mapping; no literal cache label is required when another eligible cache is selected.

Configuration errors

projcli checks the configuration before running the selected work:

  • An unsupported directory name stops the command with an explanation.
  • A reference to a missing directory or storage destination stops the command. The error identifies the setting that needs correcting.

Top-Level Configuration

The _projr.yml file supports a top-level config block for project-wide settings:

  • config.git.engine: The Git execution engine to use. Can be auto (default) or system. This determines how the CLI interfaces with Git capabilities natively.
  • config.git.use_proj_cred_helper: Defaults to false: use existing native Git authentication. Explicit true permits an existing single-line GITHUB_PAT, GH_TOKEN or GITHUB_TOKEN for standard HTTPS github.com remotes through a temporary host-scoped helper. There is no automatic token discovery or GitHub CLI call during builds. Tokens are environment data, never argv or shell source; persistent auth settings are unchanged.

Parameters Configuration

The _projr.yml file supports a top-level parameters block for arbitrary nested parameter evaluation. Use it for analysis inputs such as a model name, random seed or reporting date.

The configuration engine also supports several aliases for this block: parameter, params, and param. However, multiple alias conflicts within the same configuration file are structurally rejected during validation to prevent mapping confusion.

Remotes Configuration

Define named storage locations under remotes.local or remotes.github. Local locations can use ordinary latest/archive folders, shared whole-file storage (cas), or experimental shared-pieces storage (xet). GitHub supports ordinary latest/archive uploads and complete-store ZIPs for cas and xet.

Choose where a production build publishes with build.dest, as in projr 0.9 (SATVILab/projr@5f915ef, R/yml-dest.R:569-703). Archives are defined only under remotes; a registered remote that build.dest does not list receives nothing but stays available for restore. build.dest takes one of three forms:

Form Meaning
dest: archive One remote.
dest: [archive, {reports: {content: [output]}}] A list of names, each optionally a one-entry mapping with settings.
dest: {content: [output], cue: always, archive: {}, reports: {inspect: file}} A mapping of options that apply to every listed remote, plus one entry per remote.

Settings are content (the labels to publish; omitted means every declared non-cache label within the remote’s own content; content: [] sends nothing) and cue, inspect and strategy, which override the remote’s send values. Per-remote settings win over build.dest options. Options in a list, unknown settings and unknown or repeated remotes are errors; a null setting inherits the build.dest option, as projr’s list merge drops it. A title may be used for both a GitHub and a local remote: write github:reports or local:reports wherever the name would otherwise be ambiguous (build.dest, build.restrictions.not_behind_remote and proj restore --destination). The option words content, cue, inspect, strategy, conflict and version cannot be remote titles. When profiles are merged, the highest-precedence build.dest replaces lower ones whole rather than merging mappings.

Inline archives under build.local or build.github were removed in projr 0.9 and fail with its guidance: define each archive under remotes.<type>.<title> and list it under build.dest. projcli’s own earlier forms are not migrated.

Remotes also accept projr 0.9’s get fetch settings (version: latest, x, x.y or x.y.z; cue: if-empty, never, if-change, always; inspect: manifest, file, none; strategy: sync-diff, sync-purge, download-all, download-missing; conflict: error, local, remote). They are validated but not used yet: build.source fetching is a later slice. A remote’s source: field and directories.<label>.source were removed in projr 0.9 and are rejected with its guidance to select sources with build.source.

projcli writes its own .projcli-manifests metadata only when a remote sets manifest, manifest-style or manifest-format; a plain remote writes projr’s layout only.

remotes:
  local:
    shared:
      path: ../team-archives/@branch
  github:
    reports:
      repo: research-team/study-results
      tag: "figures-@version"
      branch: "@branch"
build:
  dest:
    shared: {}
    reports:
      content: [output]

GitHub destinations accept projr’s repo (an owner/name destination repository; defaults to the Git origin of the project), tag (release name used for both the Git tag and the release title; defaults to the remote’s title) and branch (the branch whose head a newly created release targets; "@branch" means the checkout’s branch, resolved only when the release is missing). When a release is missing, the build checks read-only that the branch exists in the destination repository and that no existing Git tag of that name points elsewhere, and stops otherwise. After every read-only check passes and before any hook, the build creates each missing release (as projr does), with a note that the build is pending; a successful publication replaces the note. If the build then fails, the release stays, possibly empty; it is never deleted. Creating it is not distribution: the error and the local failure diagnostic (.projr/logs/local-failures/, field created_releases) name each such release by repository and tag. An existing release keeps its target and note. These fields are rejected on local destinations.

Local destination names and paths and GitHub release names accept projr’s placeholders: @version (the build version with a leading v), @branch (the checkout’s branch, encoded as a path component, so feature/foo becomes feature_2ffoo; a detached checkout gives __detached- and the commit ID) and @uuid (a fresh UUIDv4 per build). A placeholder ends at the end of the text or before -, _, ., a space, / or \, so archive-@branching stays literal. Quote YAML values that begin with @. Values are resolved once before hooks; the build’s attempt record (.projr/attempts/<attempt>.json, field destinations) keeps the build UUID and each resolved GitHub repository/tag and local path (only paths inside the project; an absolute or .. path is reproduced from the configuration and the recorded UUID). Builds that publish nothing (previews and output_run: false) do not resolve placeholders. CAS and Xet store paths are not expanded. proj restore and proj get read these recorded destinations, so a build’s @version, @uuid and @branch archive is found again; see restore and get.

The detailed examples below explain content, comparison/upload controls, and manifest options. See shared-file GitHub backups and experimental Xet for their additional requirements and limits.

Build Configuration

The _projr.yml file can also contain a build block to configure the behavior of the proj build and proj build-dev execution engine. The build block supports the following sub-keys:

  • dest: The remotes a production build publishes to; see Remotes Configuration. Removing a name stops uploads without removing that remote as a restore source. build.local and build.github are rejected (projr 0.9).
  • scripts: An optional list of explicit script paths or glob patterns to execute during the build pipeline.
    • Globbing patterns are supported.
    • Prefix a pattern with ! to exclude matching files from execution, or write the entry as - exclude: scratch.R (as in projr). An empty entry fails with a hint to quote "!scratch.R", use - exclude:, or use scripts: [].
    • A list containing only exclusions means automatic discovery minus the matches, as in projr. With a Quarto or Bookdown project this is not yet supported and fails clearly.
    • The root README.Rmd is never run as analysis, even when listed.
    • Current source rejects malformed inclusion or exclusion syntax before execution, including hook patterns. The exclusion correction is included in preview.3; see the build reference.
    • When provided, this selects scripts instead of automatic discovery. Document targets may be grouped for rendering, so mixed script and document targets are not guaranteed to run in the exact listed order.
  • hooks: An optional map of lifecycle hook scripts to execute.
    • pre: Scripts executed before the actual build phase.
    • post: Scripts executed after analysis/promotion, before VERSION and publication.
    • both: Scripts executed during both pre and post phases.
  • pipeline: Named pipelines to run (see Pipelines): a name or glob, a list of them, or false/[] for none.
  • cite: projr’s citation-file selection, true/false or a mapping of codemeta, cff and inst-citation booleans. Accepted and validated, not yet acting: builds do not generate citation files (see proj init for an explicit CITATION.cff).
  • package: accepted and ignored. projr 0.9 lists it as a valid build key but has no reader for it.
  • git: An optional Git integration configuration. This can be a boolean toggle or an object mapping out detailed toggles:
    • commit: Defaults to false, including inside an existing Git repository. Explicit true requires initially clean Git state and commits once after successful local build; an unchanged staged index is a successful no-op.
    • push: Defaults to false. Explicit true publishes HEAD to the current branch’s configured upstream remote/reference. Missing upstream or custom push-only routing fails before build writes; origin/main is never invented.
    • add-untracked: projr’s boolean (default true). Accepted and validated, not yet acting: a projcli build always stages new files, because its attempt records and receipts are new files that must be committed. projr’s false would stage only already-tracked files (git add --update).
  • restrictions: Configuration block to enforce Git checks specifically during production builds: These are projr’s keys (SATVILab/projr@5f915ef:R/yml-restrictions.R).
    • branch: Omitted or true allows any branch. false or [] blocks production builds on every branch; a list (or a single name, branch: main) allows only the named branches. Outside a Git repository the restriction does not apply, as in projr; inside one, a detached HEAD fails.
    • not_behind_git: Whether to check that the current branch is not behind its tracking upstream before a production build. The earlier projr spelling not_behind is also accepted; setting both fails. Omitted means on, as in projr: when a tracking upstream exists the build fetches it and aborts if the branch is behind; without a tracking upstream the check is skipped, and a failed fetch only warns. Explicit true makes a missing upstream or failed fetch an error. Like projr, both restrictions are skipped (no Git process starts) outside a repository; projcli detects one from a .git entry at the project root or any ancestor. An upstream that cannot be compared (its remote branch was pruned) warns and skips unless the value is explicit true. false performs no fetch.
    • not_behind_remote: Archive version check before any hook or rendering (projr R/build-remote-versions.R). Omitted or true checks the ordinary local and GitHub destinations this production build publishes to; false skips the check; a name or list of names checks those registered remotes, even when the build does not publish to them; write github:reports for a title registered under both types (projr 0.9 rejects the earlier {github: [...]} mapping). For each archive the build reads its completed project version (the Project: line of its VERSION, or VERSION.zip on a GitHub release) with read-only lookups. A missing or empty archive passes; a populated archive without a readable version stops the build. The proposed version must be newer than the archive’s.
    • rule: base_version_not_behind (or base, the default) also requires the last completed local version to be at least the archive’s. That base is the most recent completed production attempt in .projr/attempts (projcli’s counterpart of projr’s BUILDLOG), else an existing VERSION file without a development component (never DESCRIPTION). target_version_not_behind (or target) checks only the proposed version, for publishing from an older checkout. Development builds and output_run: false skip the check; CAS and Xet stores are not checked.
  • clear_output: An optional string controlling workspace clearing routines for output directories. Can be set to "pre", "post", or "never". If omitted, defaults to evaluating the PROJR_CLEAR_OUTPUT environment variable.

Development Overrides

You can define a dev block to completely override specific configurations during development builds (proj build-dev).

  • scripts: A list of script paths or globs. During development builds, this array entirely overrides build.scripts. An explicitly empty array ([]) selects no analysis scripts. An absent dev.scripts inherits build.scripts. Hooks can still run.
  • scripts accepts the same - exclude: entries and exclusion-only lists as build.scripts.
  • hooks: A mapping identical to build.hooks. Development builds run only dev.hooks; build.hooks never run in a development build, even when dev.hooks is omitted (as in projr, because production hooks may publish or notify).
  • pipeline: As build.pipeline, for development builds. When omitted, a development build inherits build.pipeline’s scripts but not its hooks (a deliberate difference from projr, SATVILab/projr#1074); set dev.pipeline or pass --pipeline to run pipeline hooks in a development build.
  • old_dev_remove: Retained configuration field. The current preview protections skip CLI cleanup of prior caches during development builds, even when this is true. Scripts and hooks still control their own writes.

Pipelines

Top-level pipelines names ordered groups of scripts and hooks, as in projr 0.9 (SATVILab/projr@5f915ef:R/pipeline.R):

pipelines:
  prepare:
    scripts: [clean.R, {exclude: scratch.R}]
    hooks: {pre: [fetch.R]}
  report:
    scripts: [report.qmd]
    hooks: {post: [notify.R]}
build:
  scripts: [setup.R]
  pipeline: [prepare, report]
  • Each pipeline accepts only scripts (entries as in build.scripts) and hooks (pre, post, both). Names cannot contain : or ,.
  • build.pipeline (production) and dev.pipeline (development) select names or globs (* and ?; every other character is literal, unlike projr, where characters such as + and | act as regular expressions). Entries keep their order, a glob’s matches keep their order under pipelines, and each pipeline runs once. An entry that matches no pipeline fails before any hook.
  • The selected pipelines’ scripts and hooks combine with the inline scripts/hooks. Inline entries run first unless the highest-precedence configuration layer that sets pipeline puts scripts (or hooks) after pipeline; above, setup.R runs before clean.R. A development build checks the dev block before the build block. both hooks join pre and post, and a hook named more than once runs once, at its first position.
  • A pipeline with no scripts, and no inline scripts, runs no analysis (it does not fall back to automatic discovery); a list of only exclusions still means discovery minus the matches.
  • Hook files of every pipeline are excluded from automatic discovery.
  • Production attempt records list the selected pipeline names and placements.

Environment Variables

  • PROJR_AUTO_INSTALL: During the proj build pre-flight checks, if required R packages (like bookdown or rmarkdown) are missing, this environment variable controls remediation. If set to true, packages are automatically installed. If absent or set to false, the tool defaults to an interactive terminal prompt (if available) or fails hard.

Runtime settings and output clearing

build declares actions; settings controls how they run. Parameters are analysis inputs, not execution controls. This is an intentional extension beyond projr.

settings:
  output-clear-stage: none
  execution-directory: native
  path-representation: auto

Use none to preserve other existing final files, pre to clear immediately before analysis, or post to clear immediately after successful analysis and before output promotion/finalization. Preview never clears released outputs. Pre-hooks run before pre-clear; end hooks run after finalization immediately before the next-dev bump. The command’s explicit –output-clear-stage overrides merged settings; those override legacy build.clear_output, then PROJR_CLEAR_OUTPUT, then the new none default. Legacy never is accepted in the legacy field/environment. The canonical settings key accepts only none/pre/post, with invalid values/null rejected before merge or mutation. execution-directory accepts native/project; explicit --execution-dir wins over merged settings, then native is the fallback. Native scripts inherit launch cwd; native document execution remains renderer-defined. path-representation accepts auto/absolute/relative; explicit path-query --format wins over merged settings, then auto is the fallback. Auto is caller-relative ordinarily and absolute in a known managed renderer. Both settings reject null, booleans and unknown values in each active file before merging. Managed child queries retain the captured representation policy even if scripts change configuration, profiles or cwd. Safe is the default path target; final must be explicitly requested. Docs output handling and the R-data built-in remain separately modeled features.

projr’s own settings.hashing block is also accepted and validated (R/yml-check.R:43-71): approach is cpp (default) or legacy, and cores is a whole number of at least 1; other keys are errors. projr’s original settings.hash-engine spelling is read as hashing.approach. Accepted, not yet acting: both approaches produce the same MD5 digests, which projcli’s single native implementation already computes, and hashing stays sequential whatever cores says.

R package data

The built-in output-r-data lookup has fixed final destination project/data, even without YAML. Querying never activates build management or creates directories. Safe lookup needs the selected declared cache and active version.

To opt into ordinary output clearing and success-only promotion:

directories:
  cache:
    path: _tmp
  output-r-data:
    ignore: []

An empty output-r-data mapping also activates the role, with ordinary default ignore rules. Explicit ignore: [] includes package data in Git and R builds. The path may be omitted; if present it must resolve to project/data. Redirection is forbidden. settings.output-clear-stage applies normally: pre/post clears old package data; the default none preserves other final files. Preview never promotes final data.

Every layer accepts projr’s data label as an alias and normalizes it before merging, including remote content labels. Defining both aliases in one layer is an error. Generic data-* labels are unsupported; use raw-* inputs or ordinary output-* mappings.

Existing archive inventory coverage

CAS ingestion records the current recursive file paths and content hashes for the explicitly selected directory. The transition fixture compares exact inventories and stored bytes after a same-size/same-modified-time edit, an addition, a rename and a deletion. Earlier snapshots remain inspectable across those later ingestions. A renamed file appears under its new path in the current snapshot; this does not create a rename-event format.

This verifies existing archive machinery only. It does not automatically record all build inputs, code, configuration or dependencies, select a future build record format, or decide content-only identity and retention policy. Complete M2 provenance remains unfinished.

Production file inventory

Current source adds directory boolean hash. It defaults to true for declared raw/output/docs labels and false for cache labels. Set hash: false to omit a directory, or hash: true to include a cache. Each active layer must use a boolean; null, numbers and strings fail validation before hooks.

directories:
  raw-data: {path: inputs}
  cache: {path: _tmp, hash: false}
  output: {path: results}

A successful output-enabled production build records its inventory in projr’s manifest store, .projr/manifests/, without requiring Git or a remote. A projr-written root manifest.csv is imported once on the first write and left unchanged. Preview and build.output_run: false leave the store alone. See the inventory notes. This CSV capture is included in preview.3. See the compatibility log and PR175 for verification evidence.

Restore sources

proj restore reads the checkout’s manifest store and a registered remote: a GitHub title or concrete Release tag (archive by default), or local:<title>. proj get reads another analysis or a registered remote. Neither uses build.dest: a registered remote stays available whether or not a build uploads to it. See restore and get. directories.<label>.source was removed in projr 0.9 and is rejected:

directories.raw-data.source is no longer supported. Register the remote under
remotes and select it with build.source.

Restore uses the shared profile selection order: explicit profile, PROJR_PROFILE, then the local and base profile keys, with earlier profiles winning and local overrides last. Machine failures keep installation/recovery details on stderr, including retained original paths; stdout stays a structured failure.

Configured local publication candidate

A remotes.local.TITLE listed in build.dest accepts latest destinations with explicit send.inspect:file. See the remote command reference for the complete example and tested/pending control matrix. content:false/null disables a destination, true selects declared non-cache roles, and a list retains its explicit label order. Each selected role must have CSV hash capture enabled. The existing if-change/sync-diff defaults remain; omitted inspect does not silently change the projr manifest default to file.

Archive, manifest/none inspection, path-append-label:false, title-level cue and nonempty get/conflict controls are not executable in this bounded slice. Selected unsupported policy fails before hooks. Registry706 remains design-only.

For configured ordinary local latest publication, explicit send.inspect: none selects blind source-file planning and defaults send.strategy to upload-all. Explicit upload-missing/sync-diff then overwrite source filenames while retaining remote extras; sync-purge only purges when the source is nonempty. See the remote control matrix before choosing these combinations. Omitted inspection retains the projr manifest default, using matching recorded history or falling back to physical file comparison.

Configured ordinary local publication now follows the archive default when structure is omitted; latest remains explicit. The existing manifest inspection and sync-diff/if-change defaults apply. See archive publication for historical reuse, complete snapshots and unsupported append-label:false.

The first GitHub upload subset requires explicit send.inspect: none and upload-all (the none default), with archive as the existing structure default. Other decision combinations and existing current-version data fail explicitly. See the remote CLI page for credentials, metadata bounds and partial failure.

Ordinary named remotes and upload selection

Ordinary local latest/archive and GitHub Release definitions can now live under top-level remotes rather than build. A definition remains available to restore even when the build no longer uploads to it. These use the same executable definition/send fields already accepted by inline ordinary publication.

remotes:
  local:
    historical:
      path: ../historical-store
      structure: archive
      content: [raw-data]
    current:
      path: ../current-store
      structure: latest
      send:
        cue: if-change
        inspect: manifest
build:
  dest:
    current:
      content: [output]
  scripts: []
  git: false

A selected destination’s content list limits that build to declared labels allowed by the remote’s content, if specified. Omit the destination’s content to use all remote-eligible labels; if the remote also omits content, ordinary content:true selection applies (declared non-cache labels, with existing hash requirements). Explicit content:[] selects no labels. build.dest:{} selects no registered uploads. Flat history in local CAS

New local CAS remotes can save a readable CSV or JSON history instead of a directory-tree manifest:

remotes:
  local:
    snapshots:
      path: ../snapshot-store
      structure: cas
      manifest-style: flat
      manifest-format: csv
      manifest: remote
build:
  dest:
    snapshots:
      content: [raw, output]

The labels must already be declared. For flat style, csv is the default; json is also available. Both automatically reuse an earlier complete inventory for the same logical folder when later contents are identical, including a reversion to older contents. The later version points directly to that earlier complete version, never a chain. A changed version records all current file memberships, including additions, removals and renamed paths.

CSV is one rectangular table with a header and repeated label/version columns. In Excel, filtering a reference version shows the earlier ref_version to inspect; it does not automatically expand that earlier listing. All earlier complete rows remain in the same history file. Plain CSV/JSON retains literal full file hashes. Optional csv-dedupe-file/json-dedupe-file modes replace repeated hashes with a bundled file dictionary while retaining every file path. These modes are off by default. They are not omitted-file deltas, and no size/speed advantage is promised.

Files are stored once by their BLAKE3 content hash regardless of manifest format. Full history files live under catalogues/v1/manifest.csv or manifest.json; opt-in dictionary files use manifest-dedupe-file.csv/json. Existing root manifest.csv keeps its separate projr-compatible MD5 schema and is unchanged.

auto means remote for CAS. project/remote/both selects full history placement; a small project snapshot binding is always retained. Flat bindings connect the version and selected labels to inventory hashes, independently of serialization or dictionary IDs. They are not directory-tree object IDs. Full immutable refs use flat-snapshots/v1/<first2>/<rest62>.json; small project refs use references/flat-v1/<first2>/<rest62>.json. No unnecessary tree objects are written.

History replacement is atomic per file. Decoded previous label/version contents are never overwritten; divergent histories or conflicting same-version retries fail. Identical per-label retries do not duplicate rows, and missing labels can resume a partial write. Switching format preserves older files/readability and uses the longest compatible decoded history; dictionary IDs do not define it. Codec limits fail explicitly rather than truncating history.

The authoritative history read through replacement/reference publication holds the existing cooperative claim at <store>/.projr/build.lock. Unknown/stale claims fail closed and only an owned claim is removed; there is no automatic process killing or stale-claim cleanup. Raw immutable objects may be copied before that claim. Required history copies precede full snapshot refs, then the small project ref. both is not a cross-location transaction: errors can leave objects or an updated first history copy. Retry can finish the remaining copy.

Explicit verify/restore resolves version references/dictionaries, checks inventory hashes and actual raw bytes, and uses the existing guarded installer. The result reports snapshot_kind: flat-catalogue-v1. Old tree and legacy-flat IDs stay distinct and readable, regardless of the current write style. A small binding alone is not a backup. Empty directories are recorded by this new format, unlike legacy flat.

These manifest-format controls apply to local CAS and the ordinary local/GitHub flat histories described below. Ordinary providers retain compatible CSV/VERSION metadata alongside the new histories. CAS trees default to fixed v1 JSON; explicit manifest-format: json is valid there, while CSV/dictionary choices require flat style. Null/unknown modes fail instead of silently choosing a default.

This is separate from the project’s source CSV.

A cooperative destination claim covers history reads through publication. Required full catalogues precede immutable full bindings and the small project binding. Multiple copies are not a transaction: failure may leave earlier data or metadata installed, and is reported as partial publication.

Changing ordinary local placement reads compatible history from both fixed known locations, but writes complete history only to the newly selected locations. Old unselected files remain intact; changing placement or format cannot silently start a disconnected history.

R processes and executable

The M4 draft adds an R block under config (not settings):

config:
  r:
    session: isolated
    # Optional: a native executable file, not a shell command with arguments.
    # rscript: "tools/R installation/bin/Rscript"

session accepts isolated (default) or shared. Isolated starts a fresh Rscript for each plain R script. Shared lazily starts one child R process for the selected plain R analysis scripts in that build, preserving their objects, options, working directory and library changes across scripts, even with Python/document steps between them. It is not the R frontend caller’s live session. Source or shared-process shutdown failures stop the build; later scripts and end hooks do not run. Ordering is unchanged.

rscript is an optional path resolved against the captured project root; absolute paths also work. Omission uses Rscript on PATH. Spaces are literal path data, not shell quoting. Missing files, nonexecutables and Windows non-.exe files fail preflight. The selected executable serves plain R scripts, R hooks and Rmd/Bookdown R drivers. Quarto chooses its own engine; this setting does not rewrite its setup.

Hooks stay in separate processes, including in shared mode. Renderers retain native execution settings and do not receive the shared analysis workspace. The child starts with the existing controlled run environment, active libraries and captured root/profile/version context; later R state changes do not modify the Rust driver or other processes. The initial cwd follows execution-directory policy. Shared mode uses source(…, local=.GlobalEnv, chdir=FALSE), so Rscript commandArgs and stdin are worker controls, not per-script arguments or interactive input. Startup files/renv activation retain normal R behavior at worker launch; there is no automatic dependency restore, clean-room or sandbox guarantee.

Optional R project setup and build maintenance

These features are included in preview.5. They were added after preview.4; use the matching command and separately installed R task dependencies. Plain Markdown remains supported. To create an R Markdown README without replacing README.md:

proj init readme --rmd --title "My project"

This creates README.Rmd only. To start an empty renv project deliberately, with renv already installed in the selected R:

proj init renv

The command uses renv::init(bare=TRUE, restart=FALSE), then an initial snapshot(type=‘all’, prompt=FALSE) of its installed project library to create renv.lock. It does not discover/install missing analysis dependencies during init. It does not install renv, restore project packages, or run as part of normal init. Existing renv, renv.lock or .Rprofile is preserved by refusing this command; manage an existing project directly with renv. Failure restores the fixed project setup paths, including ignore files; effects in package caches or arbitrary startup code are not reversible. config.r.rscript chooses R for this command too.

Choose production build tasks independently under build, rather than config:

config:
  r:
    session: isolated
    # rscript: "tools/R installation/bin/Rscript"
build:
  r:
    document: true
    readme: true
    renv-snapshot: true

All three default to false, preserving existing projcli builds. document requires DESCRIPTION and R/ and runs devtools::document(). readme requires README.Rmd and renders it to root README.md using rmarkdown’s md_document format. renv-snapshot requires an existing renv.lock and runs renv::snapshot(prompt=FALSE); it never means restore. Missing packages are errors, with no framework dependency install. These are production actions; build-dev skips them even when selected.

Before start hooks, preflight checks fixed inputs/outputs and installed packages. After managed recovery is captured, snapshot runs before start hooks, matching original projr. Then start hooks/preparation, input inventory and analysis proceed. After successful analysis, post-clear, restoration of native artifacts and output promotion, snapshot runs again, followed by documentation and README. Then output inventory/history and distribution proceed. No housekeeping action runs between pre-clear and analysis, analysis and post-clear, or end hooks and the next development version. End hooks remain last.

The post actions share one short-lived R child rooted at the project. Preflight and the pre-analysis snapshot use separate children. This reuses package loads within the post batch, not across all build stages. It is not a daemon or the shared analysis session, and it does not inherit caller R objects. Normal project startup/renv activation still runs in each child. A persistent housekeeping worker would require a separate lifecycle/state-leakage design and is not implemented.

Fixed man/, NAMESPACE, DESCRIPTION, README.md, README_files/ and renv.lock effects join existing bounded build recovery, before distribution. Linked/special paths are rejected before launch; Unix additionally rejects multiply linked fixed files. Native R code, package loading/compilation, custom README output hooks and user-defined roxygen extensions can write elsewhere: there is no whole-project sandbox or rollback guarantee, and no new Windows hard-link guarantee. No citation generation or citation metadata update is included.

The existing named R build/version helpers retain their M4 DESCRIPTION restriction. Package projects can invoke these CLI tasks through proj_cli(“build”, “–patch”). This slice does not synchronize DESCRIPTION’s Version with VERSION or add legacy package-version authority; generated package documentation may reflect its existing DESCRIPTION. Use the original R backend when that broader behavior is required.

When migrating from projr, set renv-snapshot explicitly if you relied on its automatic snapshots for an existing renv project. Select document/readme explicitly if you want those maintenance tasks. Merely creating README.Rmd or initializing renv does not enable any build task.
