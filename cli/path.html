proj path get

Resolve a project resource independently of your current working directory.

proj path get --label <LABEL> [--target final|safe] [--format auto|absolute|relative] [--relative-to BASE] [--project <PATH>] [PART ...]

Declared directory paths

Ordinary labels must be declared in the active configuration with a nonempty path. ASCII case is ignored. Undeclared labels and suffixes are errors: declaring raw-data does not declare raw or raw-data-extra. Relative paths resolve against the captured project root; explicit external directories are allowed. Queries do not create directories. Safe lookup is the default and resolves generated output into the versioned cache. Use --target final for the configured released destination.

Explicit and inherited project root

--project PATH selects that exact existing directory, including a folder without configuration or VERSION. It overrides both ancestor discovery and an inherited run root. Invalid directories fail with a nonzero exit status.

The CLI captures an absolute root as PROJ_PROJECT_ROOT for the invocation and its child processes. A nested proj path get uses that root even after a script changes cwd. An invalid inherited root fails rather than falling back silently. Direct Rust build_project(root, ...) calls also pass their supplied root to children. See the discovery rules below for the recognized root markers.

This establishes CLI child-query behavior, not direct Quarto/RStudio parity or changes to the existing R frontend. Renderer configuration, execution cwd, resource links and output placement remain separate concerns. Path queries do not write ignore files or create the resolved target directories.

Nearest-root discovery

Without --project or an inherited run root, discovery walks upward from cwd and selects the first recognized directory. It does not search downward for projects. Recognized markers are VERSION, README.md, _quarto.yml, _proj.yml, legacy _projr.yml, Git/SVN metadata, a DESCRIPTION containing Package:, an RStudio .Rproj whose first line starts Version:, and a renv.lock with a Packages map.

pyproject.toml, Project.toml and JuliaProject.toml deliberately extend the projr marker set for Python/Julia. requirements.txt and Manifest.toml alone are not root markers. Standalone VERSION and README markers are retained, so a nested directory with one is the nearer project; explicit selection overrides it.

Marker recognition does not change shallow default script enumeration or prove that the corresponding language runner/frontend is implemented. Legacy config content handling is a separate compatibility change from recognizing its root.

If no recognized marker exists, discovery selects cwd. Discovery success does not mean a build is configured: the current product contract requires active root configuration and explicit used-directory mappings. Validation changes enforcing that newer contract are separate from this root-discovery slice.

Explicit safe lookup and file fragments

--target safe maps declared output/docs-class labels to <selected-cache>/projr/v<active-version>/<exact-declared-label>. One explicit safe: true cache wins; otherwise eligible exact label cache wins, then the first eligible cache in merged declaration order. safe: false excludes a candidate. The chosen label is captured for child queries. A release version has no dev suffix; dev cache keys use a hyphen, such as v1.2.3-4. Other roles retain their configured targets.

--target final addresses the explicitly configured destination, including an absolute external directory. The CLI defaults to safe; production promotion is a separate build step. Path queries do not promote anything.

Optional parts extend the selected role, for example:

proj path get --label output --target safe figures result.png

Queries do not create directories. Unknown labels, missing cache/version for safe lookup, absolute/drive-qualified parts and parent traversal fail clearly. Explicit directory mappings stay mandatory; output-model does not imply an output alias. Path representation and native execution cwd remain separate policies.

Representation and explicit renderer context

--format auto returns a caller-cwd-relative filesystem path in ordinary execution and an absolute target in an explicitly known managed render child. It never infers render context from a .qmd filename, project marker or cwd. absolute and relative override auto. Explicit --relative-to cwd|project|document|/absolute/base requires relative format; document requires an individually known render document. Project renders without a single document reject that base. A custom base must be absolute.

Strict relative conversion fails across roots/drives. Auto ordinary execution falls back to absolute when no relative path exists; the absolute target stays identical. The CLI defaults to safe targets and auto representation. Merged settings.path-representation may select auto/absolute/relative; an explicit --format overrides it. The default is frozen with managed child context, while relative paths are expressed against each query caller’s current cwd. Getters create no directories.

Renderer descriptors are private per-command snapshots created only when launching Quarto/rmarkdown/Bookdown, alongside unchanged root/profile/version/mapping inputs. Ordinary scripts and dependency probes keep ordinary context. Existing R helpers do not consume this descriptor; direct IDE rendering does not gain automatic parity. Absolute results are filesystem targets, not literal Markdown/LaTeX URL rewrites.

R package data lookup versus activation

proj path get --label output-r-data --target final
proj path get --label output-r-data result.rda

The first returns project/data even without YAML; the second derives a safe target from the selected declared cache and active version. Neither creates directories nor activates cleanup, recovery, promotion or publication of package data. Explicitly declare directories.output-r-data: {} to activate ordinary output management. Legacy _projr data declarations normalize before merging. Its final destination cannot be redirected. There is no special preservation policy: configured pre/post clearing applies normally; preview never promotes.

Built-in project lookup returns the selected root. No Python, Julia or inst role is introduced; use ordinary output mappings or proj path get –label project inst for a root-relative fragment.
