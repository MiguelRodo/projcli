Inspect local remote versions

The remote commands and configured publication described here are included in published preview.3; see delivery evidence. Earlier slice notes retain their original test scope. The command below provides ordinary local latest/archive inspection. This command does not upload, restore, verify artifact bytes or change configured remote definitions. It is separate from CAS and the deferred registry design.

proj --project . remote versions --path /physical/path/to/archive --label raw-data
proj --machine --project . remote versions --path /physical/path/to/latest --label raw-data --structure latest

Paths relative to the command’s selected project root are supported. Use physical paths: symlinked parents, candidate directories and VERSION files are rejected. No active project config, Git credentials or remote account are required.

Archive is the default layout: base/label/version directories. Numeric versions sort newest first, including empty variants. The actual directory path is retained even when version spellings differ. Multiple spellings or full/empty variants remain visible rather than silently selecting one for restore. Unrelated names are skipped; malformed numeric-looking version names and special candidates fail.

Latest reads the exact label entry from base/VERSION. It reports the trailing asterisk as metadata_untrusted, plus present and empty fields. A missing target is reported explicitly; an absent asterisk is not proof of verified content. Archive results do not infer trust from metadata and return null for that field. An absent base or VERSION yields no entries and creates nothing. Duplicate label entries and malformed advertised versions are errors.

Use –path-append-label false only when version directories or latest contents are directly at the supplied base. VERSION remains at that explicit base. For latest, reading that file means the base already exists, so present is true and empty is false: a sibling base-empty is not selected. This mode does not infer whether the base contains data files; directory presence is not integrity. This makes the inspected path explicit; it is not a new remote registry format.

Machine output retains protocol v1 and adds a versions query result. No byte verification, latest-source selection, credential discovery or publication occurs.

Download one ordinary local version

Current source work adds remote download. It is an explicit transfer, independent of configured source selection and build publication. For archive, supply the exact numeric directory spelling via –remote-version (for example v1.2.3-4). For latest, omit that option: the advertised VERSION label entry is required. A full archive directory wins over its corresponding -empty variant.

proj --project . remote download --path /physical/archive --label raw-data --remote-version v1.2.3 --destination downloaded-data
proj --project . remote download --path /physical/latest --label raw-data --structure latest --destination downloaded-data

The destination parent must exist. Private staging receives all source files (including nested and hidden files) before an existing destination changes. Matching files receive downloaded bytes; destination-only files survive by default. –clear explicitly discards those extras only after staging succeeds. An empty source marker preserves existing files normally, or produces an empty destination with –clear. A marker containing entries is rejected.

Project-root/ancestor, VCS/framework-state and overlapping destinations are rejected, along with symlinked paths and linked/special copied entries. Hard-linked external aliases keep their bytes. Copy/selection failure preserves the existing destination. If installation fails, restoration is attempted; a failed rollback reports where the original directory was retained. This is not crash atomicity or protection against concurrent writers. Post-install cleanup failure is reported as an installed download with incomplete private-staging cleanup.

The command does not authenticate metadata, compare downloaded bytes to CSV, choose configured restore sources or change local VERSION/manifest/configuration. A latest untrusted marker does not prevent this explicitly requested download; it remains a warning about metadata, not a verified-content claim. Machine mode returns completed: true only after successful completion.

Permission flags are preserved for newly downloaded entries. Merge mode retains existing file/directory permission flags, and an existing destination root keeps its flags even with –clear. Ownership, ACLs and extended attributes are outside this bounded guarantee; replacing a tree is not a full metadata-preserving backup.

Inspect and apply a concrete local file policy

Current source work adds remote store for file-inspected transfers to one explicit physical target. This is the file-policy layer, not configured build publication or archive/version metadata management. Supply –inspect file explicitly; manifest/none inspection are not accepted by this bounded command. The existing configuration default inspection is unchanged.

proj --machine --project . remote store --source generated --destination /physical/remote/output/v1.2.3 --inspect file --dry-run
proj --project . remote store --source generated --destination /physical/remote/output/v1.2.3 --inspect file --strategy sync-diff

The default strategy is sync-diff, matching projr. upload-all selects every source file and keeps destination-only files; upload-missing uploads only absent names; sync-diff uploads new/different files and removes destination-only files; sync-purge lists all existing files for removal and every source file for upload. A dry run reports uploads, overwrites, removals and same_bytes (informational even when those paths are re-uploaded). It creates nothing.

This command uses current streaming MD5 byte inventories, not modification time or a claim of authenticity. Hidden/nested files are included; empty subdirectories are not transfer records. The destination parent must exist. It stages selected source bytes, checks their hashes and rechecks source/target inventories before the shared guarded installer changes the target. Mirror execution builds a full replacement snapshot, so unchanged bytes may be copied privately too; do not interpret the plan as a syscall or disk-I/O count.

Source files stay unchanged. Retained paths of the same type keep existing permission flags; new paths use source flags. The download safeguards and limits above apply, including Windows read-only cleanup failures and partial cleanup residue. No crash/concurrent-writer isolation or ACL/ownership/xattr parity follows.

VERSION, manifest.csv, configured remotes, cue selection, historical comparison, empty remote naming and GitHub/CAS structures are untouched. Use the concrete version directory as destination; this command does not publish a complete discoverable remote snapshot by itself.

Native filename aliases (for example A.csv/a.csv on a case-insensitive target) are rejected before staging when the planned spelling differs from an existing entry. This includes directory components and keeps upload-missing from becoming an overwrite. Case-sensitive targets retain distinct names. Case-only migrations are not silently inferred by this bounded file-policy command.

Work with explicit GitHub Release assets

The source CLI provides remote github assets, remote github upload and remote github download. Each requires –repository owner/repo and –tag RELEASE_TAG. Upload also requires –source FILE and –name ASSET_NAME; –create-release explicitly permits a missing Release to be created. Existing names are rejected without deletion. Download requires –name, –destination FILE and –max-bytes N. Source/destination file paths are relative to the selected project root unless absolute. The destination parent must already exist.

Use an existing GITHUB_PAT, GH_TOKEN or GITHUB_TOKEN, in that order. Public list and download requests can be anonymous. GITHUB_API_URL supports an explicit Enterprise API endpoint including /api/v3. Tokens are never command arguments. No authentication setup or additional credential helper is installed.

Machine assets returns result.assets; machine upload/download returns completed through the existing worker. ZIP creation/extraction, projr metadata ZIP handling and configured restore are not yet provided by these explicit asset commands. An interrupted upload can have an uncertain remote result: inspect before retry. Downloads stage complete bytes before replacement, preserve existing permissions, and reject protected project state, links and special files. No archive integrity, crash atomicity or concurrent-writer isolation claim follows.

The CLI does not initialise HTTP wire logging and its own error messages omit tokens, response bodies and signed redirect URLs. Library embedders must avoid ureq DEBUG/TRACE logging for sensitive requests because dependency logging is not redacted. Redirects remove Authorization but do not confine network access to a provider host; this transport is not a network sandbox.

GitHub ZIP packaging and explicit directory transfer

Current source extends the native Release transport with projr flat names: prefix-label-vVERSION.zip for archive, prefix-label.zip for latest, and -empty before .zip for empty variants. With no prefix, the label is always used, including path_append_label=false. Metadata assets remain shared and unprefixed: manifest.zip contains manifest.csv, VERSION.zip contains VERSION, and CHANGELOG.zip contains CHANGELOG.md. Directory ZIP entries are relative to the selected source, without an enclosing folder. Nonempty parent-directory entries retain Unix permission modes; empty directory entries remain omitted. Empty sources contain the single zero-byte projr-empty sentinel; empty subdirectories are not archived.

The CLI adds remote github upload-directory (label/structure/remote-version, optional prefix/path-append-label), upload-metadata (kind manifest/version/ changelog and a source directory), and download-directory (exact asset name, destination, max-bytes, max-expanded-bytes, optional clear/empty). Uploads remain new-name-only; metadata is packaged byte-for-byte rather than silently merged. Download stages extraction privately and uses the existing guarded merge/clear installer. Explicit empty requires exactly the sentinel and consumes it before installation. Destination-only files survive unless clear is requested.

Safety changes from R’s direct utils::unzip: bounded expanded bytes and100000 members, CRC validation, reject links/special/encrypted entries, traversal, backslashes, device names, native aliases, duplicate members and parent/file collisions before project installation. Retain existing installer rollback and Windows backup-cleanup limits; no crash/concurrent-writer guarantee is added.

Ponytail full: one ZIP crate with only Deflate enabled, existing MD5 inventory, HTTP client and guarded installer. No backend interface, registry or new YAML policy. Independent tests cover exact metadata/Unicode/hidden/empty members, malicious names, CRC/expanded limits and mocked actual ZIP upload/download merge/clear. Remote exact-head platform/pinned/docs acceptance and independent review passed for the delivered slices; see delivery evidence.

Pinned sources: flat names, ZIP layout, empty sentinel, metadata assets. Configured single-label restore and explicit replacement are described below. Historical metadata merging and configured automatic publication are included in preview.3. Complete credential-helper fallback and CAS-structure integration remain outstanding.

Review amendments share the existing native directory-entry alias guard with file-policy transfers, validate empty-directory CRC with a bounded probe, and never persist an expanded-byte probe beyond each member’s advertised size. Directory modes apply deepest-first after extraction; an existing destination’s modes still follow the previously documented merge policy. File-only ZIPs from other writers have no directory privacy metadata to restore. Source root modes are not encoded as a new manifest field. No ACL/ownership/xattr claim follows. Temporary paths are created beneath the physical canonical system temp directory; macOS /var aliases are not an excuse to weaken external path guards.

Extraction also checks actual directory spelling immediately after creation, rejecting filesystems that rewrite it rather than merging distinct Unicode members. The extracted-tree owner restores directory owner access for cleanup; explicit close reports a retained path on cleanup failure. The directory-transfer command checks extraction and transfer cleanup on success and failure and distinguishes installed output from failed transfer. Readonly/zero-mode owned directory cleanup is exercised unprivileged in the pinned gate.

Explicit GitHub asset replacement

Current source adds –replace to upload, upload-directory and upload-metadata, and GithubReleaseClient::replace_asset. Default uploads still reject existing names. Explicit replacement follows the working projr delete-then-upload sequence: remote-github-httr.R554-662.

Before deletion, validate the regular source, stage its complete bytes privately, resolve the Release/unique asset and validate its trusted upload endpoint. An absent name uploads normally. A successful delete is followed by one upload; errors after deletion explicitly state that the previous asset was deleted. An interrupted deletion reports an uncertain old-asset state and does not start the upload. This is not atomic publication, backup retention or remote rollback. There is no automatic retry, new history/sealing policy or changed YAML default.

Ponytail full reuses the existing client and request/body fixtures, with a private file snapshot only for explicit replacement. Mocked end-to-end witnesses cover staged bytes despite source mutation after delete, exact DELETE/POST ordering, denied/interrupted delete, failed/malformed upload, untrusted endpoints, ambiguous names, unsafe sources and machine CLI output. These are mocked REST operations, not actual GitHub Release mutations. No live user data/credentials or local heavy tests. PR182 passed exact-head remote gates and independent review. Configured single-label restore follows below; full automatic publication remains open.

Configured single-label restore

remote restore –label LABEL –max-bytes N –max-expanded-bytes N resolves one declared final directory from merged active configuration. Optional –position source/dest, –provider local/github and –title restrict lookup; –profile follows existing earlier-profile/local precedence. –remote-version selects an exact archive version; otherwise numeric newest is selected. GitHub latest reads canonical VERSION.zip, then downloads its label ZIP. –repository owner/repo avoids requiring Git; otherwise origin is inspected locally and its host must match the API. GITHUB_API_URL and existing environment tokens retain the explicit transport contract. No credentials are installed.

Existing per-directory source.local/source.github title references or named inline definitions precede eligible build.local/build.github destinations. A shared referenced definition may be refined inline through the existing deep merge (null still inherits). Destination source:false excludes it; true or a matching label preference beats the first eligible fallback. content:null/false selects nothing, true selects declared non-cache roles, and lists select declared labels. Source/provider/title declaration order is preserved. No retry switches to another configured source after lookup/download fails.

A valid root manifest.csv is required, matching projr’s prior-build gate. Labels with no recorded files and advertised empty variants skip without clearing. CSV history is not used as an integrity/trust proof. Full sources stage before the existing merge/clear installer; –clear never removes files before a source has been found and copied. Default merge preserves destination-only files. Machine results disclose restored/skipped, selected provider/title/version and destination; failures keep protocol stdout structured with static error text. Stderr carries the operational diagnostic chain, including paths and parser details; it is not a general configuration-redaction boundary. HTTP errors omit credentials and response bodies.

This deliberately fixes R source-selection indexing/inline-definition bugs and clear-before-lookup data loss. It does not add R’s implicit hard-coded archive fallback: undeclared remotes/paths are errors under the agreed explicit mapping contract. Nonempty get policy mappings fail explicitly rather than pretending that R’s ineffective get.strategy/get.conflict controls work. Send policy is not executed by restore. Definitions retain local path versus GitHub title/tag id semantics, including spaces and @version tag normalization.

Restore reads ordinary inline remote/source definitions without executing send policies. Normal builds separately validate and execute supported configured publication, including cue/history integration. Unsupported controls fail rather than silently doing nothing. All-label default restore, complete credential-helper fallback and the issue706 registry remain subsequent work.

Pinned comparison: restore gate/selection/download, inline destination defaults, content eligibility. Ponytail full reuses merged YAML, typed core validation, CSV decoding, numeric version comparison and guarded local/ZIP installers. No backend trait, new registry or persistence schema. Filesystem and mocked REST actual CLI fixtures cover source priority, references/inline/profiles, destination preference, numeric archives, VERSION ZIP latest, clear/merge/empty and corrupt failure preservation. Configured restore uses the shared profile selection order: explicit profile, PROJR_PROFILE, QUARTO_PROFILE, then build.profile, with earlier profiles winning and local overrides last. Machine failures preserve installation/recovery details on stderr, including retained backup paths; stdout stays a structured failure. Configured local publication

Current source supports build.local archive (the default) and latest publication with manifest inspection by default, explicit file comparison, or explicit none comparison. This is included in preview.3 and is not complete projr remote parity. All selected namespace identities are checked before hooks; every current CSV-selected snapshot and existing remote metadata is staged/read before the first destination changes. Data precedes manifest.csv, VERSION and an existing project CHANGELOG.md. The build’s existing irreversible publication boundary preserves the successful local release on publication failure and skips its next-dev bump; remote effects may be partial.

build:
  scripts: []
  git: false
  local:
    delivery:
      path: ../delivery
      structure: latest
      content: [output]
      send:
        inspect: file
        cue: if-change
        strategy: sync-diff

Content false/null selects nothing, true selects declared non-cache labels, and a list selects exactly those declared labels. Selected labels require CSV hash capture. Explicit label lists retain order; true uses sorted declared labels. There is no implicit role/destination and no registry706 change. Previews and output_run:false skip publication.

No comparison during configured local publication

Set send.inspect to none to make planning ignore comparison hashes/history. The default strategy then becomes upload-all; both cues still upload nonempty sources. Explicit upload-missing and sync-diff also blindly overwrite selected filenames and retain remote-only files, matching projr rather than their file-inspected behavior. Existing destinations are marked untrusted with a star.

Explicit sync-purge replaces the entire file set when the source is nonempty. With an empty source it retains unknown remote extras: without comparison, projr does not discover extras to trigger a purge. New empty destinations are still advertised. These combinations are covered by actual CLI build/store/restore fixtures, including repeated same-byte builds and both cues.

None controls comparison decisions; guarded path/type checks, source CSV-byte validation, staging and physical installation safety still read files. It is not a promise of zero remote reads or hashing. The shared physical transfer remains guarded and may read destination bytes while installing. The archive and configured GitHub variants described below are also included in preview.3.

Manifest comparison for local latest publication

Manifest is the default inspection. The remote label VERSION must be unstarred, and the corresponding label/version CSV rows must exist and match project history exactly as filename/MD5 sets. Then current source rows are compared with those recorded rows. Otherwise comparison falls back to physical files. Missing, mismatched, duplicate or ambiguous rows cannot establish trust; malformed history still fails closed rather than being overwritten.

A matching history is a performance/decision trust convention, not proof of actual remote bytes. If bytes drift independently while history still agrees, unselected files are retained. Use inspect: file to compare actual bytes. Sync-purge still replaces the whole file set when triggered. Shared guarded staging checks physical paths/types/bytes during installation; this mode does not promise zero remote reads. Explicit upload-all ignores comparison like projr.

Projr strips the star before its latest-manifest helper checks history. Rust deliberately treats a starred label as untrusted and falls back to file comparison, consistent with the stated marker meaning. This is a source bug correction, not a new history/authenticity policy. Archive and configured GitHub publication use this shared planner and are described below.

Configured ordinary local archives

Omitting structure uses archive, matching projr. Each label stores complete snapshots at path/label/vVERSION (or vVERSION-empty), with shared metadata at path. Earlier versions are retained. Explicit path-append-label:false remains unsupported for configured publication; source lookup/explicit download support is separate.

For if-change, an older archive can be reused only when its newest catalog entry, unstarred VERSION label and matching project/remote history agree, and the version falls within the continuous unchanged suffix of project history. File inspection then compares that eligible directory’s bytes; manifest inspection compares its recorded rows. Missing/stale/future/mismatched/untrusted evidence forces the current version. Always with an absent current destination selects a fresh snapshot. None and upload-all do not select historical comparisons.

When a new snapshot is required it contains the complete current CSV-selected source, including when only one file differed from an older comparison. This avoids the native source’s potential partial-new-directory behavior after old comparison byte drift. Old snapshots are never patched as comparison sources. Shared metadata still advances when unchanged content reuses an older version. Empty transitions retain history; redundant unchanged empty snapshots are skipped.

Remote fixtures cover the 3 inspection x 4 strategy x 2 cue matrix through actual build/store/restore, default archive/manifest, empty transitions, reversion after an intervening change, and missing/untrusted/forward/drifted comparison evidence. Archive root/container identities and catalogs are validated before hooks; exact current-version spelling is checked during all-target preparation before any destination applies. No remote transaction or concurrent-writer guarantee. Configured GitHub publication and CAS policy remain separate.

GitHub file/manifest comparison and archive history

Omitting send uses the existing defaults: inspect: manifest, strategy: sync-diff, cue: if-change and structure: archive. Explicit file and none are also supported. Verify or restore an exact local CAS tree snapshot (development source)

These commands select a registered local CAS remote and an exact v1 snapshot ID:

proj remote verify --title snapshots --snapshot SNAPSHOT_ID
proj remote restore --title snapshots --snapshot SNAPSHOT_ID --label raw --clear

Replace SNAPSHOT_ID with the full 64-character snapshot ID. Automatic snapshot discovery/version selection is not part of this explicit command slice. verify returns the complete observed file paths/hashes and folder roots; it deeply checks metadata identities and file bytes without writing anything.

Snapshot restore requires a declared destination label and –title. It uses the exact saved label membership, not current build.dest/content upload choices or automatic source preferences. This lets an older saved raw folder be restored after uploads for raw have been disabled. Omit –clear to preserve destination- only files; with –clear, the selected folder has exactly the saved names/bytes, including a genuinely empty root. An optional –remote-version is a guard that must match the selected snapshot, rather than another selection mechanism.

Both full remote and project metadata locations are checked independently of the current manifest placement/style. Every present copy must verify; a corrupt present copy is not silently skipped in favour of another. Missing copies may be absent by design. A small project reference alone cannot reconstruct missing full metadata or missing file objects. A remote full snapshot can recover data into a fresh configured project without root manifest.csv or the project ledger. Project-only metadata must still exist to recover its snapshots.

Queries/restores do not change VERSION, root CSV, attempt evidence or store metadata, and do not contact GitHub, Git or a credential helper. The existing guarded installer stages and checks bytes before replacing a destination. Permissions and live consistency are not restoration guarantees. The ordinary installer’s documented post-install backup-cleanup limitation still applies.

For snapshot mode, ordinary archive download byte-limit flags are unnecessary; the tree reader retains its existing metadata/graph/entry bounds. GitHub repository and source/destination-position filters are rejected in this explicit mode, as are archive byte-limit flags. Ordinary restore without –snapshot retains its existing controls and required archive limits.

The initial command slice read v1 trees. Support for original flat snapshots is described below; their IDs are never reinterpreted as trees. Automatic CAS discovery and new flat CSV/JSON publication remain separately tracked work.

Recover existing flat CAS snapshots

The explicit remote verify / remote restore –snapshot commands also read the original flat JSON snapshots in manifests/<id>.json. Their IDs remain BLAKE3 of the original JSON bytes; they are never reinterpreted as pure content-tree IDs. Responses identify snapshot_kind as legacy-flat or tree-v1.

The reader validates metadata, portable names and every referenced object before using the same guarded staging/installer as trees. Old snapshots remain usable after the remote’s current write style changes, without a project CSV or legacy ledger. Stored metadata, IDs, objects, VERSION and history are never rewritten.

Legacy snapshots record files but not empty directories or permissions. Recovery does not invent that missing history. Unsafe path aliases, traversal, corrupt or missing content and conflicting same-ID namespace entries fail explicitly before destination changes. Metadata is bounded at 16 MiB and 100,000 file entries, with the existing portable path bounds. Ordinary root manifest.csv remains separate.

Automatic snapshot discovery and new flat CSV/JSON catalogue publication remain pending; this is compatibility recovery, not a format conversion or migration.

Verify and restore new flat CSV/JSON snapshots

The same named-store and exact-ID verify/restore commands now read the new flat-catalogue-v1 binding as well as tree-v1 and legacy-flat. They resolve complete version inventories, check all referenced bytes and keep VERSION, root CSV and store history unchanged. Current write format does not hide older snapshots. See the format/placement reference. Automatic snapshot selection is still separate; no newest-version policy is added.

Ordinary local file-list history

Configured local latest/archive builds can write flat CSV/JSON history; see placement, defaults and examples. These lists describe actual uploaded folders, including retained remote-only files, and preserve the physical location of reused archive data. Existing ordinary remote restore remains unchanged. Exact-ID CAS verify/restore does not interpret ordinary bindings as content-addressed file objects.
